# 🛡️ Log Analysis with SIEM — Reference Sheet

> **TL;DR:** A SIEM gives a SOC analyst two superpowers — **centralisation** (all logs in one place) and **correlation** (linking separate events into one attack story) — plus **historical search** to see how far back the activity goes. This room walks through the four log source families an L1 analyst lives in (**Host / Network / Web**, split into Windows, Linux, and Web) and gives ready-made **Splunk SPL** queries for each: Sysmon `EventCode=1` / `3` for process + network activity, Security `4720`/`4722` for account creation, System `7045`/`7036` for malicious services, Linux `auth.log` + `syslog` for brute force / privesc / cron persistence, and web `access.log` aggregation for brute force, web shells, and DDoS.

> ⚠️ **All IOCs in this sheet are defanged** (`10.10.114[.]80`). Re-fang before pasting into Splunk or a TryHackMe answer box.

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| Your clock ≠ the SIEM's clock | Logs arrive in UTC, local time, or no timezone at all. Working in UTC−2 while Splunk normalises to UTC+2 makes 5 PM look like 9 PM — **that's not ingestion delay**, it's a timezone offset. Always confirm which TZ you're reading. |
| Time range defaults will hide your evidence | The lab logs are historical. Splunk's default "Last 24 hours" returns nothing — set **All Time** on every search in this room. |
| Sysmon is not installed by default | WinEventLogs ship with Windows; **Sysmon must be installed and configured separately** before any of its telemetry reaches the SIEM. |
| Windows has far more than 3 log channels | Security / System / Application are the famous ones, but the OS has **200+ channels**. Don't assume "not in Security" means "not logged". |
| `4720` alone is an incomplete story | `4720` = account **created**, `4722` = account **enabled**. Search both, or you'll miss whether the backdoor account was actually usable. |
| `7045` vs `7036` are different questions | `7045` = service **installed** (the persistence act). `7036` = service **started/stopped** (the execution). Malicious-service hunts need both. |
| Normalisation ≠ correlation | **Normalisation** reformats different log formats into one schema. **Correlation** links events across sources. Exam questions use both words — read carefully. |
| Host-based is the answer for script execution | Script/process execution is seen on the endpoint, so the log-source-type answer is **Host-Based**, not Network-Based, even though the script later beacons out. |
| A single log line rarely answers the question | The MD5 hash question in Task 4 cannot be answered from the `EventCode=3` network event — you must **pivot to `EventCode=1`** for the same image. Correlation is mandatory, not optional. |
| `auth.log` can prove privesc happened but not *how* | `*su*` shows the attacker reached root; determining the exploit used needs additional logs (auditd, Sysmon-for-Linux, etc.). Don't over-claim in your escalation write-up. |
| `where count > 0` does nothing | Every group has ≥ 1 event, so that filter removes zero rows. It's copied from the lesson's threshold pattern (`> 25`, `> 100000`) — in practice you can drop it. |
| "Highest" means you must sort | `stats count by uri_path` returns unsorted groups. Add `| sort -count` (optionally `| head 1`) or click the column header — don't eyeball page 1. |
| Same tool name, different answer | The *lesson* brute-force example used **Hydra** as the User-Agent; the *practice* scenario's User-Agent is **WPScan**. Answer from your own search results, not the walkthrough. |
| `/tmp` + `cron` is almost never legitimate | A script executing from `/tmp` on a 5-minute cron schedule is a persistence red flag on sight. |
| Perl/Python/Bash/`nc` in a cron line = reverse shell hunt | Interpreters inside cron entries are the cheap way to find reverse shells — that's exactly what the `syslog` search filters for. |
| DDoS ≈ `503`, not `500` | Look for **HTTP 503 Service Unavailable** with an absurd request count. `500` is a generic server error and is not the DDoS signal taught here. |

## 📊 Task 2 — Benefits of SIEM for Analysts

### The three core benefits

| Benefit | What it means | Analyst payoff |
|---|---|---|
| **Centralisation** | Collecting and storing log data from many systems/sources into a single unified location | No switching between IPS, EDR, cloud consoles mid-investigation — one search bar |
| **Correlation** | Linking data from multiple sources to identify relationships between individual events | Turns an orphan IDS alert into "who, where, which tool" |
| **Historical events** | Search past activity, not just live alerts | Spot patterns that started before the alert fired (e.g. has this user ever logged in from this IP?) |

Other SIEM value mentioned in passing: **visualisation**, **detection rules**, **automation paths**.

### Ted vs Emily — why centralisation wins

| | **Ted** (has a SIEM) | **Emily** (no SIEM) |
|---|---|---|
| Same two alerts | Network activity spike + malicious command on a host | Same |
| Where she/he looks | One platform holding IPS + endpoint + other logs | Logs into IPS, then EDR, then each system separately |
| Result | Sees the bigger picture fast | Burns the shift just *gathering* data |

### Correlation process (enrichment chain)

| Step | Source | What it adds |
|---|---|---|
| 1 | **Alert received** (IDS log) | Only a source IP — not much to go on |
| 2 | **Identity Provider** | User info — who triggered it |
| 3 | **System logs** | Host info — which device the IP belongs to |
| 4 | **Network logs** | IP address context — how it communicated |
| 5 | **Windows Event Logs / Sysmon** | Which tool was used → malicious or noise? |

## 🌲 Task 3 — Log Sources Overview

Think of the org as a **tree**: the organisation is the tree, and the resources (workstations, servers, network gear, identity providers, cloud, apps) are the roots feeding it. Logs from some or all of those roots ship into the SIEM.

### Log source types

| Type | Comes from | Detects | Example |
|---|---|---|---|
| **Host-Based** | Workstations, servers (web / SQL / DNS) | Process creation, file activity, user logins, **script execution**, malware execution | PowerShell or Bash script run on a workstation |
| **Network-Based** | Firewalls, routers, switches, **IDS/IPS** | Traffic, connections, device-to-device communication | Suspicious outbound connection / network attack |
| **Web-Based** | Web servers + web applications | Attacks against the web app | SQL injection, XSS, unauthorised access, web shell, DDoS |
| *(Out of scope here)* | Cloud (AWS, Azure), identity providers (Entra ID), third-party apps | — | Left for future rooms |

### Two cross-cutting concepts

| Concept | Problem | Fix / key point |
|---|---|---|
| **Time pitfalls** | Sources log in UTC, local time, or no TZ; your local time ≠ SIEM time | Always verify the SIEM's configured timezone before building a timeline. UTC−2 analyst + UTC+2 Splunk = 4-hour visual offset, **not** late ingestion |
| **Log normalisation** | Logs arrive as JSON, XML, plain text, each with its own field names | Convert everything into **one consistent structure** so search / filter / correlation works the same way across sources. Without it, every log source is a different puzzle |

## 🪟 Task 4 — Windows Logs

Two primary Windows data sources: **Sysmon** and **WinEventLogs**. Sysmon must be installed separately; combined, they give clear visibility into endpoint behaviour.

### Sysmon vs WinEventLogs

| | **Sysmon** | **WinEventLogs** |
|---|---|---|
| Availability | Installed + configured separately | Built into Windows |
| Depth | Deep endpoint telemetry | Broad OS/security coverage |
| Detects | Process creation, network connections, file creation, registry modification, process injection, DLL loading | Authentication, account management, services, policy changes, log clearing, restarts |
| Channels | `Microsoft-Windows-Sysmon/Operational` | Security, System, Application (+200 more) |

### Important Event IDs

| Event ID | Log | Meaning | Hunt use |
|---|---|---|---|
| **1** | Sysmon | Process Creation | Malicious execution, encoded PowerShell, parent/child chains, **Hashes** field |
| **3** | Sysmon | Network Connection | C2 / suspicious outbound, `DestinationIp`, `DestinationPort` |
| **4720** | Security | User Account **Created** | Backdoor account persistence |
| **4722** | Security | User Account **Enabled** | Confirms the new account is usable |
| **7045** | System | Service **Installed** | Service-based persistence / privesc |
| **7036** | System | Service **Started/Stopped** | Execution of that service |

### Detect malicious encoded PowerShell (Sysmon EventCode 1)

**Purpose:** Find process-creation events where PowerShell was launched with `-EncodedCommand`.

```spl
index=winenv EventCode=1 *powershell* AND *EncodedCommand*
| table _time ComputerName ParentUser ParentImage ParentCommandLine Image CommandLine
```

```text
# EventCode=1        → Sysmon process creation
# *powershell*       → wildcard match anywhere in the raw event
# *EncodedCommand*   → the -EncodedCommand / -enc obfuscation argument
# ParentImage/ParentCommandLine → who launched it (the real story)
#
# Example finding (host WINHOST05):
#   C:\Users\Public\update_config.js  → executed
#   cmd.exe                           → launched PowerShell
#   PowerShell                        → ran an encoded command
```

### Detect suspicious network connections (Sysmon EventCode 3)

**Purpose:** Show every outbound/inbound connection logged by Sysmon on a host of interest.

```spl
index=winenv EventCode=3 ComputerName=WINHOST05
| table _time ComputerName Image SourceIp SourcePort DestinationIp DestinationPort Protocol
```

```text
# Example finding:
#   Process: PPn423.exe  (running from the Temp folder → suspicious location)
#   Destination: 83.222.191[.]2 on port 9999  (unusual port)
#   Next step: check that IP against Threat Intelligence platforms
```

### Detect account-creation persistence (Security 4720 / 4722)

**Purpose:** Catch a backdoor/"backup" user account being created and enabled.

```spl
index=winenv EventCode=4720 OR EventCode=4722
| table _time EventCode ComputerName Subject_Account_Name Target_Account_Name New_Account_Name Keywords
```

```text
# Subject_Account_Name → WHO performed the action
# New_Account_Name / Target_Account_Name → the account that was created
#
# Example finding: ted-admin created AND enabled a new account on WINHOST05
#   → persistence via a backup user account, attacker still present
```

### Detect malicious service install / privesc (System 7045 / 7036)

**Purpose:** Find services created and started from suspicious paths, especially running as SYSTEM.

```spl
index=winenv EventCode=7045 OR EventCode=7036 ComputerName=WINHOST05
| table _time EventCode ComputerName Service_Name Service_Account Service_File_Name Message
```

```text
# Example finding:
#   Service_Name       = "User Updates"
#   Service_File_Name  = RNSfnsjdf.exe  (from the Temp directory)
#   Service_Account    = SYSTEM
#   → privilege escalation: attacker previously only had ted-admin
```

### Practice scenario — `index=task4`

Alert: suspicious network connection on **port 5678** on host **WIN-105**.

```spl
index=task4 ComputerName=WIN-105 DestinationPort=5678
```

```text
# Result: 1 event, EventCode=3, LogName=Microsoft-Windows-Sysmon/Operational
#   Image           = C:\Windows\Temp\SharePoint.exe
#   User            = WIN-105\Ben Foster
#   DestinationIp   = 10.10.114[.]80      DestinationPort = 5678
#   Protocol        = tcp                 ProcessId  = 1460
#   ProcessGuid     = {c5d2b969-c41e-689d-dc02-000000002101}
```

**Pivot for the hash — this requires correlation** (the network event has no `Hashes` field):

```spl
index=task4 EventCode=1 ComputerName=WIN-105 Image="C:\\Windows\\Temp\\SharePoint.exe"
```

```text
# EventCode=1 carries the Hashes field:
#   MD5=770D14FFA142F09730B415506249E7D1, SHA256=..., IMPHASH=...
# Note the doubled backslashes in the quoted Windows path
```

**Find the scheduled task (behaviour *after* execution):**

```spl
index=task4 EventCode=1 ComputerName=WIN-105 Image="C:\\Windows\\System32\\schtasks.exe"
| table _time CommandLine ParentImage
```

```text
# 4 events — the schtasks command lines reveal the task name:
#   schtasks /create /sc once /st 15:30 /tn "Office365 Install" /tr "C:\Windows\Temp\SharePoint.exe"
#   schtasks /create /sc onlogon    /tn "Office365 Install" /tr "C:\Windows\Temp\SharePoint.exe" /ru "Ben Foster"
#   schtasks /query
# ParentImage = C:\Windows\System32\cmd.exe
```

### 🔁 Generic SIEM investigation workflow

| Step | Action | Fields / example |
|---|---|---|
| 1 | Start with the alert — identify the initial IOC | IP, port, process, user, host → `index=task4 DestinationPort=5678` |
| 2 | Identify the suspicious process | `Image`, `ProcessGuid`, `ComputerName` |
| 3 | Pivot / correlate across other events | `index=task4 SharePoint.exe` or `index=task4 ProcessGuid="{GUID}"` |
| 4 | Build the timeline | sort by `_time` |
| 5 | Investigate behaviour after execution | child processes, network connections, registry, file creation, scheduled tasks, services |
| 6 | Display only useful fields | `\| table _time Image CommandLine ParentImage` |
| 7 | Extract the answer | MD5 → `Hashes`; scheduled task → `CommandLine`; IP → `DestinationIp`; process → `Image` |

**Flow:** Alert → Find IOC → Identify Process → Correlate Related Events → Build Timeline → Analyse Behaviour → Extract Evidence → Answer

**Five questions to ask about any suspicious process**

| Question | Field |
|---|---|
| Who started it? | `ParentImage` |
| What did it start? | `Image` |
| Where did it connect? | `DestinationIp`, `DestinationPort` |
| What did it change? | registry, files, services, scheduled tasks |
| What evidence do I need? | `Hashes`, `CommandLine`, `User`, `ProcessGuid` |

## 🐧 Task 5 — Linux Logs

| Source | Records | Detects |
|---|---|---|
| **`auth.log`** | Authentication activity | SSH logins (success/fail), `sudo`, `su`, privilege escalation |
| **`syslog`** | General system-level events | Service activity, restarts, **cron jobs**, background processes → persistence |

*Also common in the real world but out of scope here: **auditd** and **osquery**.*

### Detect SSH brute force

**Purpose:** Show successful and failed SSH logins for a specific user.

```spl
index=linux source="auth.log" *ubuntu* process=sshd
| search "Accepted password" OR "Failed password"
```

```text
# Example finding: 97 events — a long run of "Failed password" ending in
# "Accepted password" for the ubuntu user → successful brute force → escalate to L2
```

### Detect privilege escalation

**Purpose:** Track `su` (switch user) activity in chronological order.

```spl
index=linux source="auth.log" *su*
| sort + _time
```

```text
# sort + _time → ascending (oldest first) — builds the timeline in attack order
# Example finding: attacker moved from ubuntu → root.
# Caveat: auth.log alone can't tell you HOW root was obtained.
```

### Detect cron persistence / reverse shells

**Purpose:** Find interpreters and scripts being launched by cron.

```spl
index=linux sourcetype=syslog ("CRON" OR "cron")
| search ("python" OR "perl" OR "ruby" OR ".sh" OR "bash" OR "nc")
```

```text
# Example findings (3 interesting events):
#   pnr5433sw.sh in /tmp executed via cron every 5 minutes
#   Perl reverse shell connecting to 10.10.101[.]12 on port 9999
#   → persistence + Command-and-Control (C2)
```

### Practice scenario — `index=task5`

Alert: possible persistence via creation of a new **remote-ssh** user on an Ubuntu server.

```spl
index=task5 source="auth.log"
index=task5 source="auth.log" "useradd remote-ssh"
index=task5 jack-brown
index=task5 "jack-brown" "failed password"
index=task5 sourcetype=syslog cron
```

```text
# 1. Base index query first (62 events) to see what's there
# 2. "useradd remote-ssh" → 1 event, sudo by root, PWD=/home/jack-brown,
#    COMMAND=/usr/sbin/useradd remote-ssh   → timestamp 2025-08-12 09:52:57
#    (answer format YYYY-MM-DD HH:MM:SS)
# 3. index=task5 jack-brown → "Accepted password for jack-brown from 10.14.94[.]82 port 54446 ssh2"
# 4. "failed password" for jack-brown → 4 failures before the success
# 5. syslog cron → the persistence mechanism's callback port (7654)
```

### Linux investigation workflow

| Step | Action |
|---|---|
| 1 | Start with the alert (new user, persistence, unusual login) |
| 2 | Search `auth.log` for successful/failed logins, `sudo`, `su` |
| 3 | Search `syslog` for cron jobs, suspicious scripts, reverse shells |
| 4 | Build the attack timeline |
| 5 | Correlate the authentication events with the persistence mechanism |

## 🌐 Task 6 — Web Application Logs

| Log source | Contents |
|---|---|
| **Access logs** (most useful) | HTTP requests — URL/URI, method, status code, client IP, User-Agent |
| **Error logs** | Server errors and failures — useful context on what broke |

Servers seen: **Apache**, **Nginx**, **IIS**.

### Attack signatures in access logs

| Attack | Indicators | Threshold used in the lesson |
|---|---|---|
| **Brute Force** | Many repeated **POST** requests to a login page (`/wp-login.php`), same source IP, tooling User-Agent (Hydra, WPScan) | `count > 25` per **5 min**, grouped by `clientip` |
| **Web Shell** | Requests to `.php` / `.phtm` / `.asp` / `.aspx` / `.jsp` / `.exe` with **status 200**, odd filenames (`505.php`), few requests in a short window | `count > 2`, grouped by `referer_domain` |
| **DDoS** | Huge request volume in a short window, **HTTP 503 Service Unavailable**, one or few source IPs hammering the same URI | `count > 100000` per **10 min** |

### Brute force detection query

**Purpose:** Group POST requests to the login page into 5-minute buckets per client IP and keep only noisy ones.

```spl
index=* method=POST uri_path="/wp-login.php"
| bin _time span=5m
| stats values(referer_domain) as referer_domain values(status) as status values(useragent) as UserAgent values(uri_path) as uri_path count by clientip _time
| where count > 25
| table referer_domain clientip UserAgent uri_path count status
```

```text
# bin _time span=5m → buckets events into 5-minute windows
# count by clientip _time → per-IP, per-window request count
# Example finding: 167.172.41[.]141 made 160 requests to /wp-login.php,
#   User-Agent = Hydra → brute-force tooling
```

### Web shell detection query

**Purpose:** Surface successful requests to script/executable file types.

```spl
index=*
| search status=200 AND uri_path IN (*.php, *.phtm, *.asp, *.aspx, *.jsp, *.exe) AND (method=POST AND method=GET)
| stats values(status) as status values(useragent) as UserAgent values(method) as method values(uri) as uri values(clientip) as clientip count by referer_domain
| where count > 2
| table referer_domain count method status clientip UserAgent uri
```

```text
# status=200 → the request actually succeeded (the shell responded)
# Example finding: 505.php stood out among the URIs → candidate web shell
```

### DDoS detection query

**Purpose:** Find 503-heavy 10-minute windows with absurd request counts.

```spl
index=* status=503
| bin _time span=10m
| stats values(referer_domain) as referer_domain values(status) as status values(useragent) as UserAgent values(uri_path) as uri_path count by clientip _time
| where count > 100000
| table _time referer_domain clientip UserAgent uri_path count status
```

```text
# Example finding: resource unavailable for 10 minutes, >1.5 million requests
#   → confirmed possible DDoS
```

### Practice scenario — `index=task6`

Alert: spike in activity on the organisation's web server.

```spl
index=task6
| stats count by uri_path
| sort -count
| head 1
```

```text
# 1369 events / 179 distinct URIs. Top URI = /wp-login.php (907)
# | sort -count → descending, so the highest lands on top
# | head 1      → keep only the top row
```

```spl
index=task6 uri_path="/wp-login.php"
| stats count by clientip
```

```text
# 907 events across 4 client IPs:
#   10.10.243[.]134 → 586   ← the attacker
#   167.172.41[.]141 → 319
#   10.14.94[.]82 → 1,  205.210.31[.]27 → 1
```

```spl
index=task6 uri_path="/wp-login.php" clientip="10.10.243.134"
```

```text
# 586 events, raw log line:
#   10.10.243.134 - - [11/Aug/2025:10:17:35 +0000] "POST /wp-login.php HTTP/1.1" 200 2388
#   "http://10.10.28.135" "WPScan v3.8.28 (https://wpscan.com/wordpress-security-scanner)"
# → repeated POSTs to a login page = Brute Force; User-Agent names the tool = WPScan
```

### SPL anatomy — why each line exists

| Line | Command | What it does |
|---|---|---|
| 1 | `index=task6` | Tells Splunk **where** to search (which dataset/"folder"). Without it, Splunk doesn't know what to read |
| 2 | `\| stats count by uri_path` | The pipe passes previous results onward; `stats` calculates (`count`, `sum`, `avg`, `max`, `min`); `by` **groups** identical values so you see per-URI totals instead of one grand total |
| 3 | `\| where count > 0` | Filters **after** `stats`, like an `if`. With `> 0` it removes nothing — it only mirrors the lesson's threshold pattern (`> 25`, `> 100000`) |
| + | `\| sort -count` | Descending sort — required to answer "highest" |
| + | `\| head 1` | Keep only the top row |

### Web log fields worth checking every time

| Field | Why |
|---|---|
| `uri_path` | What was targeted |
| `clientip` | Who sent it |
| `method` | GET vs POST (POST → credential submission / upload) |
| `status` | 200 = success, 503 = overloaded |
| `useragent` | Tooling fingerprint (Hydra, WPScan) |
| `count` | Volume = the whole basis of brute force / DDoS detection |

**Tool note:** **WPScan** is a black-box WordPress security scanner used to find vulnerabilities in WordPress core, plugins, and themes, and to enumerate users and other attack-surface details.
