## ⚠️ Gotchas — Read Before Searching

| Problem / pitfall | Why it happens | Fix / analyst action |
|---|---|---|
| **No Splunk results** | Lab data is historical; default time range may be recent | Set **All Time** (explicit instruction in this room). Confirm lab is running and the **index** is correct. |
| **Wrong index** | Tasks use distinct datasets: `linux-alert`, `win-alert`, `web-alert` | Start with the exact task's index, then search its documented sourcetype/fields. |
| **Source study notes disagree about attempts** | Summary says **503** failures for `john.smith`; specific Q&A answer says **500** | **Preserve both source statements**; rerun the exact search and count matching events. Do not assert a reconciliation without logs. |
| **`sort + _time` vs newest first** | Results often display newest first | Explicit `sort 0 + _time` to see earliest → latest; use `stats earliest(_time) latest(_time)` for duration. |
| **Time zones differ** | Alert times, Splunk UI, and formatted timestamps can use different zones | Check Splunk user's timezone and `_time` conversion. Do **not** assume two differing times mean separate attacks or a timezone offset. |
| **“Failed password” ≠ “Accepted password”** | An attack can fail or succeed | Search failed **and** accepted events, and compare user, source IP, and timestamps. |
| **Internal IP does not prove prior compromise** | Private addresses can belong to legitimate systems | `10.10.x.x` in the scenario is a clue; verify device ownership and expected activity before claiming lateral movement. |
| **`sudo` / `su` may be legitimate** | Administrators use them routinely | Correlate successful suspicious login, subsequent elevated commands, identity, time, and host baseline. |
| **User account created ≠ attack proven by itself** | Admins also create service users | Correlate creation with attacker session and surrounding events. |
| **Task name looks safe** | `AssessmentTaskOne` and `DataCollector.exe` can camouflage persistence | Read the full scheduled task `Message` (triggers, command/actions, principal), not just its name. |
| **4698 PID vs parent PID** | `ClientProcessId=5816` identifies process that registered task; `ParentProcessId=4128` is an ID, not the parent **name** | Query **Sysmon EventCode 1 where `ProcessId=5816`**, then read `ParentImage`. Filtering 4128 and reading `ParentImage` climbs one level too far. |
| **Wrong field/case or unnecessary term** | `ParentCommandLine`, `ParentCommandline`, `ProcessId` and `ProcessID` may not resolve equally | Open raw event, inspect extracted field names, and remove `AssessmentTaskOne` when pivoting to unrelated process-create event. |
| **Hydra is not the web-shell user agent** | The attacker can use different clients at different stages | Exclude `Mozilla/5.0 (Hydra)` when examining the later `b374k.php` interaction. |
| **Threat intelligence is supporting context** | Reputation may be incomplete or outdated | Corroborate malicious IP/domain reputation with recorded requests, response status, and host artifacts. |
| **POST/HTTP 200 alone ≠ shell execution proven** | Ordinary applications accept POST and return 200 | In this lab, repeated interactions with a known web-shell path plus the attack sequence support a TP. Actual executed commands require further evidence. |
| **ProcessId can be reused** | Windows PIDs are not globally unique over time | Time-bound your pivot and prefer Sysmon `ProcessGuid` where available. |
| **Saved VM URLs expire** | TryHackMe ephemeral reverse-proxy hosts change | Use the current **LAB_WEB_URL** from the launched room, not previously recorded IP-specific links. |

## 🧭 SOC L1 Investigation Decision Flow

```text
Alert received
   ↓
Read alert: source IP / destination host / user / time / rule
   ↓
Confirm asset identity and user context
   ↓
Open correct Splunk index, set All Time (historical lab)
   ↓
Search broad → filter relevant activity → pivot to related events
   ↓
Build chronology (UTC/timezone checked)
   ↓
Identify what evidence supports or contradicts maliciousness
   ├── Confirmed malicious → True Positive → document + escalate
   ├── Expected authorized behavior → False Positive → document reason
   └── Uncertain → collect more evidence / escalate per SOC procedure
```

**Triage handoff essentials:** detection/alert, affected assets and users, indicators and exact evidence, first/last event times and timezone, event IDs/source indexes, investigation queries, impact/scope, confidence, and recommended next checks.

### Important SPL vocabulary

| SPL term | Meaning | Example | When to use |
|---|---|---|---|
| `index=...` | Select a Splunk event index | `index=linux-alert` | Always scope to the task dataset |
| `sourcetype=...` | Filter by source format | `sourcetype="linux_secure"` | Linux auth records |
| `"literal string"` | Search exact text phrase | `"Failed password for"` | Authentication failure hunt |
| `search` | Filter a current result set | `| search useragent="Mozilla/5.0 (Hydra)"` | Narrow to tool-specific events |
| `stats` | Aggregate events / calculate counts | `| stats count by clientip` | Measure volume and scope |
| `earliest(_time)` | Earliest event timestamp | `| stats earliest(_time) as Start` | Establish first sighting |
| `latest(_time)` | Latest event timestamp | `| stats latest(_time) as End` | Establish final sighting |
| `sort` | Order results | `| sort 0 + _time` | Reconstruct timeline |
| `table` | Display selected fields | `| table _time host user` | Reduce noise, preserve evidence |
| `eval` | Calculate a field | `| eval duration_min=round((End-Start)/60,2)` | Time difference |
| `where` | Apply condition to fields | `| where count > 25` | Frequency threshold |

**[Added technique]** Useful discovery commands when uncertain about available event fields:

```spl
index=linux-alert
| head 10
| table _time host source sourcetype _raw

index=win-alert
| stats count by EventCode
| sort -count

index=web-alert
| stats count by sourcetype
```

These commands are starting points only; check whether the assigned index contains data and whether fields were extracted.

### Investigation B — Calculate duration

**Original SPL from your notes:**

```spl
index=linux-alert sourcetype="linux_secure" "Failed password for" "john.smith"
| sort + _time
```

**Improved computation [Added technique]:**

```spl
index=linux-alert sourcetype="linux_secure" "Failed password for" "john.smith"
| stats earliest(_time) as Start latest(_time) as End count as Attempts
| eval DurationMinutes=round((End-Start)/60,2)
| eval FirstEvent=strftime(Start,"%Y-%m-%d %H:%M:%S"),

```

### Investigation A — Task creation Event ID 4698

```spl
index="win-alert" EventCode=4698 AssessmentTaskOne
| table _time EventCode user_name host Task_Name Message
```

**Explanation:** 4698 is a Windows Security scheduled-task creation event. Inspect the message's **Triggers**, **Actions/Exec**, and **Principals**. The task name alone is not a malicious verdict. **Initial search without a host restriction** can help reveal whether it appears on more than one endpoint.

**Source finding:** the XML shows a daily trigger and an action that downloads an executable into a Temp location and launches it. This supports a persistence assessment.

### Investigation B — Client PID ≠ parent name

**From the task-creation record [Source/lab]:**
- `ClientProcessId = 5816` — process that registered the task.
- `ParentProcessId = 4128` — a parent PID seen in the task evidence.
- **Documented answer to parent-process-name question: `cmd.exe`.**

```spl
index=win-alert host=WIN-H015 EventCode=1 ProcessId=5816
| table _time Image CommandLine ParentImage ParentProcessId ParentCommandLine
```

**How to interpret:** filter on the **child process** `5816` and read its `ParentImage` to identify the parent process. Filtering `ProcessId=4128` instead would retrieve the parent's own process record, so `ParentImage` refers to the **grandparent** and produces the wrong answer. The process tree is:

```text
cmd.exe                 ← ParentImage of ProcessId 5816
   └── ProcessId 5816   ← ClientProcessId in 4698
          └── created scheduled task AssessmentTaskOne
```

**Important field gotcha:** The recorded notes warn that `ParentCommandLine` capitalization matters in this dataset. If a pivot fails, inspect extracted fields in the actual Sysmon event; do not force a guessed field name.

### Investigation C — Group enumeration & originating workstation

```spl
index="win-alert" "localgroup"

index="win-alert" host="WIN-H015" EventCode=4624
| table _time WorkstationName Source_Network_Address Logon_Type
```

**Lab findings:**
- Local group enumerated: **Administrators**.
- Workstation shown as origin of logon: **DEV-QA-SERVER**.
- Notes place relevant logon activity at approximately **09:50:30–09:50:32**, before the task creation around **10:06**.

**Analyst caution:** an originating workstation name is a pivot for scope expansion; it is not proof that the workstation itself is compromised. Confirm ownership, logon type, identities, and surrounding events before stating lateral movement is confirmed.

## 🛠️ Troubleshooting Playbook — When You Get Stuck

| Symptom | Likely cause | Next action |
|---|---|---|
| No events returned | Wrong time range or index | Set **All Time**, query only `index=...`, then progressively add predicates |
| Missing field/blank table | Different extraction, field name/case, or no such event | Expand raw event, inspect available fields; simplify the query |
| You see 4698 but no `ParentImage` | 4698 is a task record, not the matching process-create event | Pivot `ClientProcessId` into Sysmon `EventCode=1` |
| Wrong parent process | Filtered the parent PID instead of the child | Search `ProcessId=5816` and read **its** `ParentImage` |
| Count differs from notes | Search terms/time range/scope may differ; source itself inconsistent | Save exact query, earliest/latest, and count; compare documented 500 vs 503 |
| “Attack duration” unclear | Sorted wrong or used the first/last result rather than event times | `stats earliest(_time) latest(_time)` and calculate minutes |
| Can't find web shell | Still filtering only Hydra user-agent | Remove or exclude Hydra, pivot on `b374k.php` and `referer` |
| Wrong web user agent | Used scanner traffic instead of web-shell requests | Search shell filename; inspect `useragent` on those events |
| Missing earlier logon | Only searched task creation time/host | Expand time; investigate 4624 and `WorkstationName` |
| True/false positive uncertain | Only one IOC or alert title | Corroborate the activity chain, account and asset context; document uncertainty |
| Chronology inconsistent | Splunk display timezone or alert timestamp mismatch | Record exact `_time`, UI time zone, source event time, and conversion |

**Exam revision tip:** Be able to explain *why* each query answers the question, not merely reproduce it. For instance, **4698 → ClientProcessId 5816 → EventCode 1 → ParentImage=cmd.exe** is a correlation procedure you can reuse in future Windows investigations.
