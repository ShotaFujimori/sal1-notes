# 🕵️ Detecting Web Attacks — Reference Sheet

> **TL;DR:** Web attacks split into **client-side** (XSS, CSRF, clickjacking — hard for SOC to see) and **server-side** (brute-force, SQLi, command injection — leave evidence in logs/traffic). Detection uses two main lenses: **access logs** for fast pattern review and **network packet captures** for full payload visibility. WAFs sit in front of all of this as the active mitigation layer, blocking malicious requests before they reach the server.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| Client-side attacks are mostly invisible to SOC | Server logs and packet captures don't see what happens inside a user's browser — no HTTP requests means no SOC telemetry. Endpoint or browser-side controls are needed. |
| Access logs don't record POST bodies | Login attempts show the path and status code, but **never the actual credentials**. To see what was submitted, you need network captures. |
| GET query strings may or may not be logged | Depends entirely on the server software and log configuration — never assume completeness. |
| HTTPS limits packet visibility | Without TLS decryption keys, packet payloads are encrypted. WAFs can decrypt and inspect, regular packet captures cannot. |
| 302 redirect after login = success | In brute-force log analysis, a 302 response after a string of 401/200s usually signals a **successful** login + redirect to authenticated area. |
| 200 ≠ benign | A 200 OK during directory fuzzing means a **valid find** for the attacker — it's how they map the app's attack surface. |
| User-Agent strings are the first giveaway | Tools like `sqlmap`, `wpscan`, `FFUF`, `nikto` often leave their name in the User-Agent. Default tool UAs are a free win for defenders. |
| Decoded vs raw payloads | URL-encoded payloads (`%27` for `'`) need decoding before pattern matching. `%27 OR %271%27=%271` decodes to `' OR '1'='1`. |
| WAFs can challenge, not just block | CAPTCHA challenges are useful for rules with high false-positive risk — verify human vs bot without dropping legit traffic. |
| Malicious bots = 37% of global web traffic | The case for WAF rate-limiting and bot challenges isn't theoretical — bots are now the majority of "non-human" traffic. |
| WAFs decrypt TLS, packet captures don't | This is a major advantage of WAFs over passive network monitoring for HTTPS sites. |
| Logs lose; packets see | Logs = fast triage and high-level patterns. Packets = full forensic detail (credentials, payloads, response bodies). Use both. |

## 🌐 Attack Categories

### Client-Side vs Server-Side

| Aspect | Client-Side | Server-Side |
|---|---|---|
| **Target** | User's browser / device | Web server, app code, database, backend |
| **Evidence trail** | Minimal — happens in browser | Strong — leaves logs + network traces |
| **SOC visibility** | Often impossible without endpoint/browser monitoring | High — logs and packet captures both work |
| **Common examples** | XSS, CSRF, Clickjacking | Brute-force, SQLi, Command Injection |
| **Detection approach** | Browser-side security controls, EDR | Log analysis, network traffic analysis, WAF |

---

## 🎯 Common Client-Side Attacks

| Attack | What It Does | Example |
|---|---|---|
| **XSS** (Cross-Site Scripting) | Inject malicious script into trusted site, executes in victim's browser | Comment box: `Hello <script>alert('hacked');</script>` — runs for every page viewer |
| **CSRF** (Cross-Site Request Forgery) | Trick browser into sending unauthorized requests on behalf of trusted user | Hidden form auto-submits a fund transfer while user is logged in |
| **Clickjacking** | Overlay invisible elements on legitimate content | User thinks they're clicking "Play"; actually clicking "Allow camera access" |

> **XSS is the most common client-side attack.**

---

## 🎯 Common Server-Side Attacks

| Attack | What It Does | Real-World Example |
|---|---|---|
| **Brute-Force** | Repeated login attempts with credential lists | T-Mobile 2021 — 50M+ customers' PII |
| **SQL Injection (SQLi)** | Inject SQL into form inputs to manipulate queries | MOVEit 2023 — 2,700+ orgs affected (US gov, BBC, British Airways) |
| **Command Injection** | User input passed to system shell without sanitization | Run OS commands with web app privileges |

### SQLi Root Cause
Apps build queries via **string concatenation** instead of **parameterized queries** — letting attackers escape the intended query and append their own SQL.

## 📜 Log-Based Detection

### Access Log Format — Field Reference

| # | Field | Malicious Indicator |
|---|---|---|
| 1 | Client IP Address | Known malicious source or outside expected geo range |
| 2 | Timestamp & Requested Page | Unusual hours, or repeated requests in short period |
| 3 | Status Code | Repeated 404s (page enumeration) or unusual 500s |
| 4 | Response Size | Significantly smaller/larger than baseline |
| 5 | Referrer | Pages that don't fit normal navigation flow |
| 6 | User-Agent | Outdated browsers, or known attack tools (sqlmap, wpscan, FFUF) |

### Sample Log Entry

```
10.10.10.100 [12/Aug/2025:14:32:10] "POST /login HTTP/1.1" 200 532 "/home.html" "Mozilla/5.0"
```

| Field | Value |
|---|---|
| Client IP | `10.10.10.100` |
| Timestamp | `12/Aug/2025:14:32:10` |
| Method + Path | `POST /login` |
| Status | `200` |
| Size | `532` bytes |
| Referrer | `/home.html` |
| User-Agent | `Mozilla/5.0` |

### Typical Attack Sequence in Logs

| Step | Activity | Log Signature |
|---|---|---|
| 1 | **Directory fuzz** to map endpoints | Many requests with varying paths; `200`s = valid finds; attack-tool User-Agents (FFUF, gobuster) |
| 2 | **Brute-force** the discovered login form | Repeated POSTs to same path in quick succession |
| 3 | **Successful login** | `302 Found` redirect to authenticated page (e.g. `/account`) |
| 4 | **SQLi attempts** on internal forms | Suspicious query strings (`' OR '1'='1`, `1' OR 'a'='a`) on form-handling endpoints |

### Log Limitations

| Limitation | Why It Matters |
|---|---|
| POST body not logged | Submitted credentials/payloads invisible — only "the request happened" is recorded |
| GET query strings inconsistent | Some configurations strip them; never assume full URL is logged |
| Format varies by server/config | Apache, Nginx, IIS all log differently; custom formats add more variance |
| No response body content | You see size, but not the data returned |

## 📡 Network-Based Detection

### What Network Captures Reveal (vs Logs)

| Visibility | Logs | Network Capture |
|---|---|---|
| Request method + path | ✅ | ✅ |
| Status code | ✅ | ✅ |
| POST body (credentials) | ❌ | ✅ |
| Full HTTP headers | Partial | ✅ |
| Cookies | ❌ | ✅ |
| Uploaded/downloaded files | ❌ | ✅ |
| Response body | ❌ | ✅ |
| Encrypted (HTTPS) content | ❌ | ❌ (without keys) |

> **Key tradeoff:** Network captures are far more verbose but harder/slower to analyze at scale. Logs are great for triage, packets for deep-dive forensics.

### Useful Wireshark Filters

```
http
# Show only HTTP traffic
```

```
http.user_agent
# Filter on User-Agent field — great for spotting attack tools
```

```
ip.dst == 10.10.20.200
# Filter by destination IP
```

```
http.request.method == "POST"
# Show only POST requests (login attempts, form submissions)
```

### Wireshark Workflow Tips

| Action | How |
|---|---|
| **Follow HTTP Stream** | Right-click any HTTP packet → Follow → HTTP Stream → reconstructs full request+response |
| **Filter combinations** | Combine with `and`/`or`: `http and ip.src == 10.10.10.100` |
| **Find successful login** | Look for the final POST before a redirect, or the response containing a session cookie |
| **Inspect SQLi result** | Follow the stream to see if dumped data (e.g., user records) appears in the response body |

### Encrypted Protocols — Visibility Limits

| Protocol | Network Visibility |
|---|---|
| HTTP | ✅ Full payload visible |
| HTTPS | ❌ Encrypted (need TLS keys or WAF/proxy decryption) |
| SSH | ❌ Encrypted |
| MySQL (cleartext) | ✅ Payloads + query results visible |

## 🚧 Web Application Firewall (WAF)

### How WAFs Differ from Passive Tools

| Tool | Inspect Requests | Decrypt TLS | Block in Real-Time |
|---|---|---|---|
| Access Logs | After the fact | N/A | ❌ |
| Wireshark / pcap | After the fact | Only with keys | ❌ |
| **WAF** | ✅ In-line | ✅ Yes | ✅ Yes |

### WAF Rule Categories

| Rule Type | Description | Example |
|---|---|---|
| **Block common attack patterns** | Match known malicious payloads/indicators | Block User-Agent `sqlmap` |
| **Deny known malicious sources** | Use IP reputation, threat intel, geo-blocking | Block IPs from recent botnet campaigns |
| **Custom-built rules** | Tailored to specific application needs | Allow only GET/POST to `/login` |
| **Rate-limiting & abuse prevention** | Limit request frequency | Cap login attempts at 5/min per IP |

### Custom Rule Syntax (Generic)

```
IF User-Agent CONTAINS "sqlmap"
THEN BLOCK
```

```
IF User-Agent CONTAINS "BotTHM"
THEN BLOCK
```

```
IF requests_per_minute > 5 AND path == "/login"
THEN BLOCK
```

### Challenge-Response (Not Just Block)

| Action | When to Use |
|---|---|
| **Block outright** | High-confidence malicious indicators |
| **CAPTCHA challenge** | Rules with higher chance of false positives — verify human vs bot |
| **JS challenge** | Validate browser-like behavior (filters out simple bots) |

> **Why this matters:** Malicious bots account for ~37% of global web traffic. Pure block lists would over-block legitimate users; challenge-response balances security and accessibility.

### Threat Intelligence Integration

| Source | What It Provides |
|---|---|
| **OWASP Core Rule Set (CRS)** | Built-in rules for OWASP Top 10 mitigations |
| **Cloudflare curated IP lists** | Botnets, VPNs, anonymizers, malware infrastructure |
| **CVE feeds** | Block exploitation attempts for recent vulnerabilities |
| **APT group indicators** | Block known nation-state attacker infrastructure |

## 🔍 Investigation Walkthroughs (from Tasks 4 & 5)

### Log-Based Investigation (TryBankMe)

| Question | Where to Look | Answer Pattern |
|---|---|---|
| Attacker's User-Agent during fuzzing | User-Agent field on fuzz requests | Tool string (e.g. `FFUF v2.1.0`) |
| Brute-force target page | Path with repeated POSTs in short window | e.g. `/login.php` |
| SQLi payload | Query string on form submission | URL-decode it: `%27 OR %271%27=%271` → `' OR '1'='1` |

### Network-Based Investigation (traffic.pcap)

| Question | How to Find | Notes |
|---|---|---|
| Successful brute-force password | Follow HTTP stream of last POST before redirect | Look at the POST body's password field |
| SQLi-dumped data | Follow stream of SQLi request, check response body | Returned database content / flag is visible in cleartext |
