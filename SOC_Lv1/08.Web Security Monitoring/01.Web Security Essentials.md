# 🛡️ Web Security Essentials — Reference Sheet

> **TL;DR:** Web applications have replaced desktop apps as the primary target for attackers because they are always online, always exposed, and connected to back-end data. Defense relies on protecting **three layers** — application, web server, and host machine — using best practices like input validation, WAFs, CDNs, logging, hardening, and least privilege.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| WAF ≠ Antivirus | WAFs inspect HTTP traffic at the application layer; AVs scan files at the host layer. They protect different things. |
| AV is for hosts, not web attacks | Most web attacks target the application layer (SQLi, XSS), which AVs do **not** inspect. AV still helps catch dropped web shells/malware. |
| CDN is also security, not just speed | CDNs hide origin IP, absorb DDoS, enforce HTTPS, and often integrate WAFs. Security is half the value. |
| GET vs POST in logs | GET requests retrieve resources; POST submits data (e.g., login forms). Login attempts show as POST in access logs. |
| Web App Owner is responsible for user data | Even if data is "in the cloud," legal and security responsibility falls on the app owner — not the cloud provider or the user. |
| Patch Management is cross-cutting | Patching applies to **all three layers** (app, server, host) — not just the OS. |
| Signature-based detection has a blind spot | It only catches *known* attacks. Zero-days and obfuscated payloads bypass it — that's why heuristic and behavioral analysis exist. |
| WAF placement matters | Cloud-based WAFs sit in front of the server (reverse proxy); host-based run on the server itself; network-based sit at the perimeter. The choice affects scope and scalability. |
| A misconfigured WAF can be worse than none | Capital One's 2019 breach happened because of a **misconfigured WAF** — gave attackers internal access. WAFs need correct rules, not just deployment. |
| Web servers are exposed by design | Public-facing exposure is unavoidable for web apps — that's why hardening + monitoring matters more than for internal services. |

## 🌐 Web Service Components

| Component | Description | Examples |
|---|---|---|
| **Application** | Code, images, styles, icons — what users see and interact with | HTML, JS, CSS, backend code |
| **Web Server** | Listens for HTTP requests and returns responses | Apache, Nginx, IIS |
| **Host Machine** | OS and environment that runs the web server | Linux, Windows Server |

### Common Web Servers

| Server | Use Case | Notable Users |
|---|---|---|
| **Apache** | Most popular for simple websites and blogs (esp. WordPress) | WordPress hosting |
| **Nginx** | High-performance web apps, reverse proxy, load balancing | Netflix, Airbnb, GitHub |
| **IIS** (Internet Information Services) | Microsoft web server in enterprise environments | Windows-based enterprises |

## 🔁 Request–Response Cycle

| Step | Action |
|---|---|
| 1 | Browser sends a **request** to the web server |
| 2 | Server processes the request and verifies access |
| 3 | Server returns a **response** (webpage, image, data) |

### How Attackers Abuse the Cycle

| Attack Type | Description |
|---|---|
| **DDoS / Flooding** | Overwhelm the server with massive request volume |
| **Access Bypass** | Skip authentication or authorization checks |
| **Command Injection** | Trick the server into executing harmful commands |

## 🛡️ Defense by Layer

### Protecting the Application

| Control | Purpose |
|---|---|
| **Secure Coding** | Avoid insecure functions, handle errors properly, remove sensitive info |
| **Input Validation & Sanitization** | Prevent injection attacks (SQLi, XSS, command injection) |
| **Access Control** | Restrict access based on user roles |

### Protecting the Web Server

| Control | Purpose |
|---|---|
| **Logging** (Access Logs) | Track every interaction for detection and forensics |
| **Web Application Firewall (WAF)** | Filter and block harmful traffic based on rules |
| **Content Delivery Network (CDN)** | Reduce direct exposure, absorb traffic, integrate WAFs |

### Protecting the Host Machine

| Control | Purpose |
|---|---|
| **Least Privilege** | Run services as low-privilege users; limit blast radius if compromised |
| **System Hardening** | Disable unnecessary services, close unused ports |
| **Antivirus** | Endpoint-level protection against known malware |

### Cross-Cutting (All Layers)

| Control | Purpose |
|---|---|
| **Strong Authentication** | Restrict access to code, admin panels, host machine |
| **Patch Management** | Keep app dependencies, web server, and host OS up to date |

## 📜 Web Server Access Logs

### Logged Fields

| Field | Description |
|---|---|
| Client IP | Source of the request |
| Timestamp | When the request was made |
| Requested page/data | What resource was asked for |
| Response status | HTTP status code returned (200, 404, 500, etc.) |
| User Agent | Browser/tool string identifying the client |

### GET vs POST

| Method | Purpose | Example |
|---|---|---|
| **GET** | Retrieve a resource | Loading `/index.html` |
| **POST** | Submit data | Submitting login credentials |

### Example Log Sequence (Benign Login Flow)

| Step | Method | Path | Notes |
|---|---|---|---|
| 1 | GET | `/index.html` | User visits homepage |
| 2 | GET | `/login.html` | Navigates to login page |
| 3 | POST | `/login.html` | Submits credentials |
| 4 | GET | `/myaccount.html` | Accesses authenticated page |

> **Why this matters:** This same sequence with anomalies (e.g. 50 POSTs to `/login` in 30 seconds = brute force) is what SOC analysts look for in logs.

## 🌍 Content Delivery Network (CDN)

| Benefit | Description |
|---|---|
| **IP Masking** | Hides origin server IP, harder for attackers to target directly |
| **DDoS Protection** | Absorbs large traffic volumes via distributed edge servers |
| **Enforced HTTPS** | Most CDNs default to TLS-encrypted communication |
| **Integrated WAF** | Cloudflare, CloudFront, Azure Front Door include WAF capability |

### Common CDN Providers

| Provider | Notes |
|---|---|
| **Cloudflare CDN** | Most widely used, free tier available |
| **Amazon CloudFront** | AWS-integrated, common in cloud environments |
| **Azure Front Door** | Microsoft equivalent, integrates with Azure WAF |

## 🚧 Web Application Firewall (WAF)

### Analogy
A **bouncer at a club** — every request must pass inspection; suspicious ones are turned away.

### WAF Types

| Type | Description | Best For |
|---|---|---|
| **Cloud-based** (Reverse Proxy) | Sits in front of the web server | Easy deployment, great scalability |
| **Host-based** | Software installed directly on the web server | Per-application control |
| **Network-based** | Physical/virtual appliance on network perimeter | Enterprise environments |

### WAF Detection Methods

| Method | How It Works | Example |
|---|---|---|
| **Signature-Based** | Matches known attack patterns/payloads | Blocking User-Agent `sqlmap/1.8.1` |
| **Heuristic-Based** | Analyzes context and behavior of requests | Long query string with special characters: `search?q=%3Cscript%20(1)` |
| **Anomaly & Behavioral** | Flags deviations from normal traffic patterns | One IP making repeated login attempts |
| **Location & IP Reputation** | Uses geo and threat intel feeds | Block IPs from outside business region |

> **Key insight:** Detection methods evolve constantly. Custom rules can be created based on the specific app's needs.

## 🦠 Antivirus (AV) on Web Servers

| Misconception | Reality |
|---|---|
| AV blocks web attacks | AV is for **endpoints** (files), not the application layer |
| AV alone is enough | AV is one layer in **defense-in-depth** — needs WAF, hardening, etc. |
| AV only matters on workstations | AV on web servers can catch uploaded **web shells** and post-exploitation tools |

### What AV Catches on Web Servers
- Malicious file uploads (e.g., `shell.php`)
- Web shells dropped after exploitation
- Post-exploitation tools (Mimikatz, Cobalt Strike beacons, etc.)

### Detection Method
**Signature-based** — compares files against a database of known malware patterns.

## 🏰 System Hardening — Limits

> **Hardening limits** = constraints set during system/app/network hardening to minimize vulnerabilities and attack surface.

### Hardening Limits by Layer

| Layer | Example Limits |
|---|---|
| **Application** | Block macros or JavaScript in office apps unless essential |
| **OS** | Enforce least privilege; disable legacy protocols (e.g., SMBv1) |
| **Network** | Allow only required ports through firewalls; segment traffic |

### Why It Matters
- Reduces breach risk by blocking common attack paths
- Limits malware deployment and lateral movement
- Aligns with frameworks like **Australia's Essential Eight** and **NIST** guidelines

## 📰 Real-World Breaches

| Breach | Year | Cause | Impact |
|---|---|---|---|
| **Equifax** | 2017 | Apache Struts vulnerability (CVE-2017-5638) — patch missed | ~150 million Americans' sensitive data exposed |
| **Capital One** | 2019 | Misconfigured WAF allowed internal access | 100+ million customers' personal/financial data |

> **Lesson:** Both highlight the importance of **patch management** (Equifax) and **proper WAF configuration** (Capital One). Security tools deployed incorrectly can be worse than none.

## 🔄 Shift: Desktop → Web

| Era | Application Model |
|---|---|
| **1990s** | Desktop apps dominated (speed/connectivity limits) |
| **2000s** | Dynamic web apps for email, social media, banking |
| **2010s** | Cloud computing & SaaS rise |
| **Today** | Nearly everything runs in the browser |

### Risks From the Shift

| For Web App Owners | For Web App Users |
|---|---|
| Always online, must be secured 24/7 | User data stored in apps, potentially insecurely |
| Anyone worldwide can access at any time | One browser breach risks all accounts |
| Hard to keep up with emerging threats | Breaches → identity theft, financial loss |
| Responsibility to secure user data | Privacy can be permanently compromised |
