# 🌐 IP & Domain Threat Intel — Reference Sheet

> **TL;DR:** L1 IP/domain enrichment runs on **verify → enrich → decide**. Pivot across DNS records, WHOIS/RDAP (domain age), ASN, geolocation, exposed services (Shodan/Censys), TLS certificates, and VPN/proxy/Tor labeling to decide whether an indicator is malicious — and **correlate multiple sources** instead of trusting any single verdict.

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| CDN IP ≠ verdict | One Cloudflare/Akamai/Fastly IP fronts thousands of legit + malicious sites. If an A record is in a CDN range, the IP alone tells you little. |
| Typosquat can be benign | Brands defensively register their own obvious typos, so a look-alike resolving to the real brand isn't automatically malicious (still treat as high-risk). |
| IDN homoglyphs | Cyrillic/Greek letters mimic Latin (e.g. Cyrillic "а" in tryhасkme[.]com). Convert to Punycode; if it renders as `xn--…`, it holds non-ASCII chars → investigate. |
| GeoIP city is unreliable | Trust only approximate **country**; city-level geolocation is generally inaccurate. |
| VPN/proxy invalidates GeoIP | A "matching" country/city can still be a VPN/Tor exit — exactly what attackers count on. Label the IP first. |
| 1 detection can matter | If the IP is **not** in a CDN range, even a single VirusTotal vendor flag is a real risk indicator. |
| Attacker infra is short-lived | Malicious domains often live only days; online tools frequently return nothing because the infra is already down. A ~10-year-old domain is reassuring. |
| Online intel goes stale | IP/domain ownership changes fast — for graded answers use the **attached PDF / exported reports**, not live lookups. |
| Shodan/Censys retention | Both keep data only a few weeks; use saved screenshots for historical exposure. |
| crt.sh availability | Often down under load — fall back to **Censys** or **SSL Shopper** for certificate data. |
| Suspicious TLS certs | Self-signed = investigate; newly-created **or** unusually long-lived validity can signal malware infra; Subject on self-signed certs may reveal the software (e.g. pfSense). |
| TXT record smell test | Legit domains carry SPF/DKIM; attack infra often has empty TXT or faked DKIM / suspicious SPF (abused in phishing). |

## 🧭 Core Enrichment Model

| Step | Meaning |
|---|---|
| Verify | Confirm the indicator and context from the alert. |
| Enrich | Add DNS, WHOIS/RDAP, ASN, GeoIP, exposure, and VPN/proxy context. |
| Decide | Malicious or not? Avoid **overreacting** (blocking legit infra) and **underreacting** (missing real C2). |

## 🔎 Domain Enrichment

**Tools:** nslookup.io, dnschecker.org, dnsdumpster.com

### DNS Records
| Record | Tells the analyst |
|---|---|
| A / AAAA | Domain → IPv4 / IPv6. Resolved IP may reveal hosting (AWS, GCP) or a CDN/proxy (e.g. Vercel). Pivot to the IP for known APT infra. |
| TXT | Mail security (SPF/DKIM) and third-party tools in use. Empty/suspicious TXT or faked DKIM = red flag. |
| NS | Authoritative nameservers (e.g. `*.ns.cloudflare.com`). |
| SOA | Start of Authority — primary NS, serial, refresh/retry/expiry. |

### WHOIS / RDAP
| Field | Value |
|---|---|
| Purpose | Registrar, registration & expiry dates, and **domain age** (most important). |
| Age heuristic | New domain (days) = suspicious; long-registered (years) = reassuring. |
| WHOIS → RDAP | WHOIS is being replaced by RDAP for structured data (entity roles, timestamps). |
| Tools | whois.domaintools.com, client.rdap.org, bash.ws |

### Attack Techniques Using DNS
| Technique | Description |
|---|---|
| CDN Abuse | Malicious traffic routed through legit CDNs (Cloudflare/Akamai/Fastly) to hide the real origin. |
| Typosquatting | Visual look-alikes (`tryhakme[.]com`, `micros0ft[.]net`). High-risk, but a typo resolving to the real brand may be defensive. |
| IDN Attacks | Non-ASCII homoglyphs; convert to Punycode (`xn--`) to detect. |

### DNS Lookups (dig)
**Purpose:** Resolve records directly against a chosen resolver.

```bash
dig @1.0.0.1 advanced-ip-sccanner.com A
# Query A (IPv4) records via the Cloudflare resolver 1.0.0.1
# Example answer: 172.67.189.143 , 104.21.9.202
```
```bash
dig @1.0.0.1 advanced-ip-sccanner.com AAAA   # IPv6 (AAAA) records
dig @1.0.0.1 advanced-ip-sccanner.com NS     # Nameservers (e.g. jaziel.ns.cloudflare.com)
```
**Punycode check:** paste the domain into punycoder.com → if the output starts with `xn--`, it contains non-ASCII characters (possible IDN attack).

## 🖧 IP Enrichment

### Reputation
| Tool | Use |
|---|---|
| AbuseIPDB | Was the IP seen in port scans / brute-force attacks? |
| VirusTotal | Overall reputation, community comments, and **Relations** (communicating files, passive DNS). Outside a CDN range, even 1 detection is notable. |

### Autonomous Systems (ASN)
An **AS** is a set of IP prefixes under one organization's control, identified by an **ASN**. Look it up on **BGP.Tools**.

| ASN type | Role / risk | Example |
|---|---|---|
| Residential | VPN usage or compromised consumer devices | AS124888 (Vodafone) |
| Server Hosting | **Highest risk** — often used to distribute malware | AS215439 (PLAY2GO) |
| Cloud / CDN | Used by legit and malicious alike — needs deeper analysis | AS16509 (Amazon AWS) |

### Geolocation (GeoIP)
**Tools:** ipinfo.io, iplocation.net — approximate **country** only (city unreliable).

| Use case | Signal |
|---|---|
| User logon analysis | US employee logging in from the Netherlands may indicate intrusion. |
| Network analysis | For a European company, traffic to e.g. Vietnam is suspicious. |

## 🚪 Service Exposure

**Why:** On a victim IP, exposed SSH is a likely entry point; on an attacker IP, outdated services or exposed RDP suggest a compromised jump host.

| Tool | Use |
|---|---|
| Shodan | Open ports + service banners (old versions ≈ vulnerable). |
| Censys (search.censys.io) | Blue-team alternative; finds services on **non-standard** ports; some features need an account. |
| crt.sh / SSL Shopper / Censys | TLS certificate details. |

### TLS Certificate — Key Fields
| Field | Why it matters |
|---|---|
| Issuer | Self-signed = strong "investigate" signal. |
| Validity | Newly-created **or** very long-lived certs can indicate malware infra. |
| Subject | On self-signed certs, may reveal the software behind HTTPS (e.g. pfSense). |

## 🕵️ VPN Detection

Scenario: an M365 login outside working hours with a "normal" location can still be a VPN — commercial VPNs (ProtonVPN, NordVPN, Mullvad) make faking location trivial. The SOC's job: **real user or VPN?**

| Tool | Use |
|---|---|
| IP2Proxy | Label VPN / proxy / Tor exit nodes. |
| Spur | Same, plus infrastructure type & IP behavior (e.g. "Anonymizing", VPN tunnels, exit location). Integrate with SIEM. |

**Decision logic:** A location match behind a confirmed VPN still warrants raising the alert; failing to match a VPN provider does **not** justify auto-closing as a false positive.

## 🔁 SOC Analyst Workflow

| Investigate the domain | Investigate the IP |
|---|---|
| Does it "look" legit (typosquatting)? | Is it a CDN range? If yes, usually no need to dig further. |
| Known-malicious reputation? | Reputation via VirusTotal, AbuseIPDB, etc. |
| Registration age (new = suspicious)? | Location / VPN node? Does it fit the alert? |
| Resolve to IP, then investigate the IP. | ASN type — does it fit the alert (e.g. employees shouldn't log in from cloud hosting)? |

*Steps may be skipped or reordered depending on the alert.*
