# Pyramid of Pain Cheat Sheet

Based on **63.SLA1 Note_ Cyber Defence Frameworks - Pyramid Of Pain.pdf**. The document explains the **Pyramid of Pain** as a way to evaluate how difficult it is for an adversary to change a given indicator once defenders start detecting it. Lower layers are easy for attackers to change; higher layers hurt them much more. 

---

## TL;DR

The **higher you detect, the more pain you cause**:

* **Hash Values** → trivial for attackers to change
* **IP Addresses** → easy to rotate
* **Domain Names** → somewhat harder to replace
* **Host Artifacts** → annoying to rework
* **Network Artifacts** → also annoying, especially when tied to traffic patterns
* **Tools** → costly for attackers to replace or rewrite
* **TTPs** → most painful, because defenders are detecting the attacker’s behavior, not just one indicator

The core lesson from the PDF is: **focus less on fragile IOCs and more on durable attacker behavior**. 

---

## 1) Hash Values (Trivial)

### What it is

A hash value is a fixed-length value produced by a hashing algorithm such as **MD5**, **SHA-1**, or **SHA-256**. Security teams use hashes to identify suspicious or malicious files. The PDF also notes that **MD5 is not cryptographically secure**, and **SHA-1 is deprecated**; stronger SHA-2 / SHA-3 family hashes are recommended. 

### Why it is low on the pyramid

Attackers can change a file hash by modifying even **one bit** of the file, which makes this indicator very weak for long-term detection. The PDF explicitly demonstrates this by appending a string to a file and producing a new MD5 hash. 

### Execution Commands

#### PowerShell: calculate a file hash

```powershell
Get-FileHash .\OpenVPN_2.5.1_I601_amd64.msi -Algorithm MD5
```

**Explanation:**
Computes the file’s hash using MD5.

**Example output concept:**
Before modification:

```text
MD5 D1A008E3A606F24590A02B853E955CF7
```

#### PowerShell: modify the file slightly

```powershell
echo "AppendTheHash" >> .\OpenVPN_2.5.1_I601_amd64.msi
```

**Explanation:**
Appends text to the file, changing its contents.

#### PowerShell: hash again after modification

```powershell
Get-FileHash .\OpenVPN_2.5.1_I601_amd64.msi -Algorithm MD5
```

**Example output concept:**
After modification:

```text
MD5 9D52B46F5DE41B73418F8E0DACEC5E9F
```

### Practical Example

A malware sample initially matches a known IOC hash. The attacker repacks the malware, changing the hash while keeping the same malicious purpose. Your simple hash-based block now misses it.

### Gotchas

* **MD5 and SHA-1 are weak choices** for trust decisions.
* Hashes are excellent for **exact-match identification**, but poor for detecting modified malware families.
* A hash tells you **what file this exact sample is**, not necessarily **what behavior it will perform**.

## 2) IP Addresses (Easy)

### What it is

An IP address identifies a device on a network. From a defensive perspective, malicious IPs can be blocked on firewalls or other controls. The PDF explains that this is useful, but attackers can often recover quickly by switching to a new public IP. 

### Why it is still low on the pyramid

Rotating infrastructure is usually not that hard for an experienced attacker.

### Important Concept: Fast Flux

The PDF highlights **Fast Flux**, where many IPs are rapidly associated with a domain, often through compromised hosts acting as proxies. This makes blocking infrastructure harder and obscures the real backend. 

### Execution Commands

#### Firewall-style example (Linux)

```bash
iptables -A INPUT -s 50.87.136.52 -j DROP
```

**Explanation:**
Drops inbound traffic from a known malicious IP.

#### Firewall-style example (Windows)

```powershell
New-NetFirewallRule -DisplayName "Block Malicious IP" -Direction Inbound -RemoteAddress 50.87.136.52 -Action Block
```

**Explanation:**
Creates a Windows Firewall rule to block traffic from that IP.

### Concrete Example from the PDF

The first IP address contacted by the malicious process in the report was:

```text
50.87.136.52
```

This was identified by reviewing the malware analysis networking results. 

### Gotchas

* Blocking one IP is often just a speed bump, not a wall.
* Cloud services, proxies, VPNs, and Fast Flux make IP-only defense brittle.
* Some IPs may host mixed content or shared infrastructure, so blind blocking can create false positives.

## 3) Domain Names (Simple)

### What it is

Domain names map to IP addresses and are easier for humans to read. The PDF explains that domains are somewhat harder for attackers to replace than IPs because they may need to purchase, register, and update DNS records. But in practice, many providers and APIs make that easier than defenders would like. 

### Important Concepts

#### Punycode attack

The PDF shows a lookalike domain example:

* deceptive display: `adıdas.de`
* encoded version: `xn--addas-o4a.de`

This is a **Punycode / Unicode spoofing** technique used to impersonate legitimate sites. 

#### URL shorteners

The PDF also explains that attackers often hide malicious destinations using URL shorteners such as:

* `bit.ly`
* `goo.gl`
* `ow.ly`
* `tinyurl.com`

It notes that appending `+` to some shortened URLs can reveal a preview / redirect target. 

### Execution Commands

#### DNS lookup

```bash
nslookup craftingalegacy.com
```

**Explanation:**
Resolves the domain to its IP address.

#### Alternative DNS lookup

```bash
dig craftingalegacy.com
```

**Explanation:**
Queries DNS records in a more detailed way.

#### Preview shortened URL pattern

```text
https://tinyurl.com/bw7t8p4u+
```

**Explanation:**
Adding `+` can show where the shortened URL redirects, depending on the shortening service.

### Concrete Example from the PDF

The first suspicious domain request in the report was:

```text
craftingalegacy.com
```

The PDF also gives the redirected website preview example:

```text
https://tinyurl.com/bw7t8p4u  ->  https://tryhackme.com/
```



### Gotchas

* Domains are more durable than IPs, but still replaceable.
* Punycode attacks can fool users visually even when the domain is technically different.
* Shortened URLs are tiny chaos grenades; always expand or preview them before trusting them.

## 4) Host Artifacts (Annoying)

### What it is

Host artifacts are traces left on a system by attacker activity, such as:

* registry values
* suspicious process execution
* dropped files
* attack patterns
* host-based IOCs

The PDF describes these as more painful for attackers because changing them may require changing tooling or methodology. 

### Why it hurts more

If defenders detect a malware family by the files it drops, registry changes it makes, or unusual process trees it creates, attackers have to change the actual mechanics of the attack.

### Execution Commands

#### List suspicious processes (Windows)

```powershell
Get-Process | Select-Object ProcessName, Id, Path
```

**Explanation:**
Enumerates running processes and their executable paths.

#### Search for dropped executable files

```powershell
Get-ChildItem -Path C:\ -Recurse -Include *.exe -ErrorAction SilentlyContinue
```

**Explanation:**
Searches recursively for executable files that may have been dropped.

#### Review registry persistence example

```powershell
reg query HKCU\Software\Microsoft\Windows\CurrentVersion\Run
```

**Explanation:**
Checks a common persistence location for suspicious autorun entries.

### Concrete Examples from the PDF

The document’s sample report identified:

* process `regidle.exe` making a POST request to:

  ```text
  96.126.101.6
  ```
* dropped malicious executable:

  ```text
  G_jugk.exe
  ```
* VirusTotal vendors flagging the host:

  ```text
  9
  ```



### Gotchas

* Host artifacts are stronger than basic network indicators, but they can still be altered.
* Overfitting on one filename or one path can be fragile.
* Better detections look for **patterns**, such as Office spawning suspicious child processes or unsigned binaries appearing in temporary folders.

## 5) Network Artifacts (Annoying)

### What it is

Network artifacts include:

* unusual **User-Agent** strings
* C2 traffic traits
* URI patterns
* suspicious HTTP POST behavior

The PDF notes that these can be found in **Wireshark / PCAPs**, **TShark**, or **IDS logs** such as **Snort**. 

### Why it hurts more

Attackers can change IPs and domains, but changing traffic fingerprints or protocol behavior may require deeper changes to malware or infrastructure.

### Execution Commands

#### Extract HTTP host and User-Agent from a PCAP

```bash
tshark --Y http.request -T fields -e http.host -e http.user_agent -r analysis_file.pcap
```

**Explanation:**
Filters HTTP requests in a packet capture and prints the destination host plus the User-Agent string.

#### Count HTTP POST requests

```bash
tshark -r analysis_file.pcap -Y "http.request.method == POST"
```

**Explanation:**
Shows POST requests, which are often useful for spotting callbacks, exfiltration, or beaconing.

#### Display only DNS requests

```bash
tshark -r analysis_file.pcap -Y "dns"
```

**Explanation:**
Helps reveal suspicious domain resolution behavior.

### Concrete Examples from the PDF

* Browser using the shown User-Agent:

  ```text
  Internet Explorer
  ```
* Number of POST requests in the screenshot:

  ```text
  6
  ```



### Gotchas

* Legitimate apps can also have weird User-Agents. Weird does not always mean evil.
* TLS encryption can hide payload details, so context matters.
* One suspicious request is interesting; repeated patterned traffic is where the monster starts to become visible.

## 6) Tools (Challenging)

### What it is

At this layer, defenders are detecting the **attacker’s tools themselves**:

* malicious macro builders
* backdoors
* EXEs / DLLs
* payloads
* password crackers

The PDF explains that once defenders detect tools effectively, attackers may need to build or obtain new tools, which is expensive and disruptive. 

### Key Defensive Methods Mentioned in the PDF

* **Antivirus signatures**
* **Detection rules**
* **YARA rules**
* **Fuzzy hashing**
* **SSDeep**

The PDF emphasizes that fuzzy hashing can identify file similarity even if two files differ slightly. It also states that the alternative name for fuzzy hashes is **context triggered piecewise hashes**. 

### Execution Commands

#### Example: SSDeep fuzzy hashing

```bash
ssdeep sample1.exe sample2.exe
```

**Explanation:**
Compares files using fuzzy hashing to measure similarity rather than exact equality.

#### Example: YARA rule scan

```bash
yara suspicious_rule.yar sample.exe
```

**Explanation:**
Applies a YARA rule to detect known malware patterns or tool characteristics.

#### Example: file signature scan

```bash
clamscan sample.exe
```

**Explanation:**
Checks a file against antivirus signatures.

### Concrete Examples from the PDF

* Similarity method:

  ```text
  Fuzzy Hashing
  ```
* Alternative name:

  ```text
  context triggered piecewise hashes
  ```



### Gotchas

* Signature-only detection can be bypassed by packing, obfuscation, or recompilation.
* Fuzzy hashing is powerful, but similarity is not proof of maliciousness by itself.
* YARA rules that are too broad turn into alert confetti.

## 7) TTPs (Tough)

### What it is

**TTPs = Tactics, Techniques, and Procedures.**
This is the top of the pyramid and includes the attacker’s overall operational behavior, aligned with ideas such as the **MITRE ATT&CK Matrix**. The PDF describes this as the most painful level for the adversary because if defenders detect behavior such as credential abuse, persistence, lateral movement, or exfiltration, the attacker may need to redesign their whole operation. 

### Why it is the strongest level

TTP-based detection is not tied to one file, one IP, or one domain. It detects **how the attacker operates**.

### Execution Commands

#### Windows Event Log: failed / suspicious auth review

```powershell
Get-WinEvent -LogName Security | Select-Object -First 20
```

**Explanation:**
Pulls recent security log events that can help identify suspicious logon or lateral movement behavior.

#### Search process creation events (Sysmon / Windows logs environment dependent)

```powershell
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" | Select-Object -First 20
```

**Explanation:**
Useful for spotting behaviors such as abnormal parent-child process chains, credential dumping tools, or persistence activity.

#### MITRE ATT&CK mapping workflow

```text
Observe behavior -> map to ATT&CK technique -> create detection logic -> validate against real logs
```

**Explanation:**
This is not a shell command, but it is the practical execution pattern defenders actually use when operating at the TTP level.

### Concrete Examples from the PDF

* Number of techniques under **Exfiltration** in ATT&CK:

  ```text
  9
  ```
* Chimera’s commercial remote access tool used for C2 and exfiltration:

  ```text
  Cobalt Strike
  ```



### Gotchas

* TTP detections are powerful, but they require context-rich telemetry.
* Poorly designed behavioral detections can create noisy alerts.
* Behavior beats indicators, but only when logs are complete, tuned, and actually reviewed by humans with functioning coffee supplies ☕️

## Practical Analyst Workflow

A sensible progression inspired by the PDF looks like this:

```text
Hash lookup
-> IP/domain review
-> sandbox/network inspection
-> host artifacts
-> network artifacts
-> tool detection
-> TTP mapping
```

This mirrors the logic of the Pyramid of Pain: start with quick triage, then move upward toward more durable detections. The PDF’s conclusion also reinforces the idea that the amount of pain caused to an adversary depends on the type of indicators defenders can use. 

---

## Final Takeaway

The Pyramid of Pain teaches a deliciously cruel truth for defenders: **not all detections are equal**.

* Hashes and IPs are useful for fast triage.
* Domains are a bit better.
* Host and network artifacts are stronger.
* Tooling and TTPs are where defenders start forcing attackers to spend real time, money, and effort.

That is the whole game: **move from detecting things attackers can swap easily, to detecting behaviors they cannot change without breaking their operation**.
