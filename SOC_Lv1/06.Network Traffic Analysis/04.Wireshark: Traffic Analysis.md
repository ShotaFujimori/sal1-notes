# 🦈 Wireshark: Traffic Analysis — Reference Sheet

> **TL;DR:** This room covers big-picture network traffic analysis using Wireshark — detecting Nmap scans, ARP poisoning/MITM, host identification (DHCP/NetBIOS/Kerberos), tunnelling (ICMP/DNS), cleartext protocol analysis (FTP/HTTP), HTTPS decryption, and credential hunting. The analyst mindset is: spot anomalies → correlate → escalate. Wireshark filters are your primary weapon.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| TCP Connect vs SYN scan — key difference | Connect completes the 3-way handshake (window size > 1024); SYN does NOT (window size ≤ 1024) |
| Closed UDP port response is ICMP, not UDP | UDP scan closed ports reply with ICMP Type 3, Code 3 — use `icmp.type==3 and icmp.code==3` |
| ARP Wireshark only flags the 2nd duplicate | The expert info tab only shows the second occurrence of a duplicate ARP response; the first is the legitimate one |
| DHCP hostname is in Request packets, not ACK | Use `dhcp.option.dhcp == 3` to filter DHCP Requests and find hostnames (Option 12) |
| Kerberos CNameString includes hostnames with `$` | Filter `!(kerberos.CNameString contains "$")` to isolate usernames only |
| ICMP tunnelling can match normal 64-byte packet size | Adversaries can craft custom ICMP packets matching normal size — volume and payload content are better indicators |
| DNS tunnelling uses encoded subdomain addresses | Queries like `encoded-commands.maliciousdomain.com` are not real subdomains — they carry encoded C2 commands |
| HTTPS key log must be captured during the session | SSL/TLS key pairs are per-session; a key log file generated after the fact cannot decrypt earlier traffic |
| User-agent alone is insufficient for anomaly detection | Never whitelist a user-agent; adversaries can spoof natural-looking values — use it as a supplemental signal |
| Log4j starts with a POST request | The attack entry point is a POST with `jndi:ldap` or `Exploit.class` in the payload — check user-agent for `$` or `==` patterns too |
| FTP response 530 = failed login, 230 = success | Use `ftp.response.code == 530` to count brute-force attempts |
| Wireshark Credentials tool only covers specific protocols | FTP, HTTP, IMAP, POP, SMTP — not all cleartext protocols; manual verification required |

## 🔍 Task 2: Nmap Scans

### TCP Flag Reference

| Flag | Value (exact) | Value (partial) |
|---|---|---|
| SYN only | `tcp.flags == 2` | `tcp.flags.syn == 1` |
| ACK only | `tcp.flags == 16` | `tcp.flags.ack == 1` |
| SYN + ACK | `tcp.flags == 18` | `(tcp.flags.syn==1) and (tcp.flags.ack==1)` |
| RST only | `tcp.flags == 4` | `tcp.flags.reset == 1` |
| RST + ACK | `tcp.flags == 20` | `(tcp.flags.reset==1) and (tcp.flags.ack==1)` |
| FIN only | `tcp.flags == 1` | `tcp.flags.fin == 1` |

### Scan Type Comparison

| Scan Type | Command | Handshake | Window Size | Open Port Response | Closed Port Response |
|---|---|---|---|---|---|
| TCP Connect | `nmap -sT` | Full 3-way | > 1024 | SYN → SYN/ACK → ACK (then RST/ACK) | SYN → RST/ACK |
| SYN (Stealth) | `nmap -sS` | Half (no ACK) | ≤ 1024 | SYN → SYN/ACK → RST | SYN → RST/ACK |
| UDP | `nmap -sU` | None | N/A | No response | ICMP Type 3, Code 3 |

### Scan Detection Filters

| Scan Type | Wireshark Filter |
|---|---|
| TCP Connect scan | `tcp.flags.syn==1 and tcp.flags.ack==0 and tcp.window_size > 1024` |
| SYN scan | `tcp.flags.syn==1 and tcp.flags.ack==0 and tcp.window_size <= 1024` |
| UDP scan (closed ports) | `icmp.type==3 and icmp.code==3` |

## 🕸️ Task 3: ARP Poisoning & MITM

### ARP Filter Reference

| Purpose | Filter |
|---|---|
| Global ARP search | `arp` |
| ARP requests (opcode 1) | `arp.opcode == 1` |
| ARP responses (opcode 2) | `arp.opcode == 2` |
| ARP scanning detection | `arp.dst.hw_mac==00:00:00:00:00:00` |
| Duplicate address / poisoning | `arp.duplicate-address-detected or arp.duplicate-address-frame` |
| ARP flooding from specific MAC | `((arp) && (arp.opcode == 1)) && (arp.src.hw_mac == target-mac-address)` |

### MITM Investigation Workflow

```
Step 1: Filter arp → look for duplicate-address-detected alerts
Step 2: Identify IP claimed by 2 different MACs → likely gateway spoofing
Step 3: Find MAC sending flood of ARP requests (opcode 1) to broadcast
Step 4: Add MAC address columns to packet list pane
Step 5: Check HTTP traffic — if attacker MAC is destination, MITM confirmed
Step 6: Build IP-to-MAC mapping table
```

### ARP Case Study — IP to MAC Mapping

| Role | MAC Address | IP Address |
|---|---|---|
| Attacker | `00:0c:29:e2:18:b4` | `192.168.1.25` |
| Router/Gateway | `50:78:b3:f3:cd:f4` | `192.168.1.1` |
| Victim | `00:0c:29:98:c7:a8` | `192.168.1.12` |

## 🖥️ Task 4: Identifying Hosts — DHCP, NetBIOS, Kerberos

### Protocol Purpose Summary

| Protocol | Use Case | Key Wireshark Filter |
|---|---|---|
| DHCP | IP assignment; contains hostname, MAC, domain info | `dhcp` or `bootp` |
| NetBIOS (NBNS) | Windows hostname broadcasting on local network | `nbns` |
| Kerberos | Windows domain authentication; reveals usernames | `kerberos` |

### DHCP Filter Reference

| Purpose | Filter |
|---|---|
| DHCP Request (hostname here) | `dhcp.option.dhcp == 3` |
| DHCP ACK (accepted) | `dhcp.option.dhcp == 5` |
| DHCP NAK (denied) | `dhcp.option.dhcp == 6` |
| Hostname search | `dhcp.option.hostname contains "keyword"` |
| Domain name search | `dhcp.option.domain_name contains "keyword"` |

### DHCP Key Options

| Option | Content |
|---|---|
| Option 12 | Hostname |
| Option 50 | Requested IP address |
| Option 51 | IP lease time |
| Option 61 | Client MAC address |
| Option 15 | Domain name (in ACK) |

### NetBIOS (NBNS) Filter

| Purpose | Filter |
|---|---|
| Global search | `nbns` |
| Name search | `nbns.name contains "keyword"` |

### Kerberos Filter Reference

| Purpose | Filter |
|---|---|
| Global search | `kerberos` |
| Username search | `kerberos.CNameString contains "keyword"` |
| Usernames only (no hostnames) | `kerberos.CNameString and !(kerberos.CNameString contains "$")` |
| Protocol version | `kerberos.pvno == 5` |
| Domain name | `kerberos.realm contains ".org"` |
| Service name | `kerberos.SNameString == "krbtg"` |

> ⚠️ Kerberos `CNameString` values ending with `$` are **hostnames**; values without `$` are **usernames**.

## 🚇 Task 5: Tunnelling Traffic — ICMP and DNS

### Tunnelling Concept

| Type | Protocol Abused | Indicator | Filter |
|---|---|---|---|
| ICMP Tunnel | ICMP | Oversized payload (> 64 bytes), no response seen | `data.len > 64 and icmp` |
| DNS Tunnel | DNS | Long subdomain queries, encoded commands, high volume | `dns.qry.name.len > 15 and !mdns` |

### DNS Tunnel Patterns

```
Normal DNS query:   www.google.com
Tunnel DNS query:   ZXhjb21tYW5kZXhlYw==.maliciousdomain.com
                    ↑ base64/encoded C2 command as subdomain
```

### Known Tunnel Tool Filters

| Tool | Filter |
|---|---|
| dnscat | `dns contains "dnscat"` |
| General long DNS | `dns.qry.name.len > 15 and !mdns` |
| ICMP oversized | `data.len > 64 and icmp` |

|---|---|

## 📁 Task 6: Cleartext Protocol Analysis — FTP

### FTP Response Code Reference

| Code | Meaning | Series |
|---|---|---|
| 220 | Service ready | x2x |
| 227 | Entering passive mode | x2x |
| 230 | User login successful | x3x |
| 331 | Valid username (password required) | x3x |
| 430 | Invalid username or password | x3x |
| 530 | Login failed (wrong password) | x3x |

### FTP Filters

| Purpose | Filter |
|---|---|
| Global | `ftp` |
| Username | `ftp.request.command == "USER"` |
| Password | `ftp.request.command == "PASS"` |
| Failed logins (brute force) | `ftp.response.code == 530` |
| Successful login | `ftp.response.code == 230` |
| Specific password | `ftp.request.arg == "password"` |
| Target username in failed logins | `(ftp.response.code == 530) and (ftp.response.arg contains "username")` |
| Password spray | `(ftp.request.command == "PASS") and (ftp.request.arg == "password")` |

## 🌐 Task 7: Cleartext Protocol Analysis — HTTP

### HTTP Filter Reference

| Purpose | Filter |
|---|---|
| Global HTTP | `http` |
| HTTP/2 | `http2` |
| GET requests | `http.request.method == "GET"` |
| POST requests | `http.request.method == "POST"` |
| All requests | `http.request` |
| 200 OK | `http.response.code == 200` |
| 401 Unauthorized | `http.response.code == 401` |
| 403 Forbidden | `http.response.code == 403` |
| 404 Not Found | `http.response.code == 404` |
| Apache server | `http.server contains "apache"` |
| Host keyword | `http.host contains "keyword"` |
| URI keyword | `http.request.uri contains "admin"` |
| Full URI | `http.request.full_uri contains "admin"` |
| Cleartext body | `data-text-lines contains "keyword"` |

### User-Agent Anomaly Detection

| Signal | Filter |
|---|---|
| Scanning tools | `(http.user_agent contains "sqlmap") or (http.user_agent contains "Nmap") or (http.user_agent contains "Wfuzz") or (http.user_agent contains "Nikto")` |
| All user agents | `http.user_agent` |

> ⚠️ Subtle spelling differences (e.g. `Mozlilla` vs `Mozilla`) are a key indicator. Never whitelist a user-agent.

### Log4j Detection Filters

| Purpose | Filter |
|---|---|
| Attack entry point | `http.request.method == "POST"` |
| JNDI/Exploit patterns | `(ip contains "jndi") or (ip contains "Exploit")` |
| Frame-level search | `(frame contains "jndi") or (frame contains "Exploit")` |
| Encoded payload in user-agent | `(http.user_agent contains "$") or (http.user_agent contains "==")` |

## 🔒 Task 8: Encrypted Protocol Analysis — Decrypting HTTPS

### TLS/HTTPS Filter Reference

| Purpose | Filter |
|---|---|
| All HTTP requests | `http.request` |
| All TLS | `tls` |
| TLS Client Hello | `tls.handshake.type == 1` |
| TLS Server Hello | `tls.handshake.type == 2` |
| SSDP (exclude local) | `ssdp` |
| Client Hello (exclude SSDP) | `(http.request or tls.handshake.type == 1) and !(ssdp)` |
| Server Hello (exclude SSDP) | `(http.request or tls.handshake.type == 2) and !(ssdp)` |

### HTTPS Decryption Workflow

```
Step 1: Capture traffic while browser is open
Step 2: Set environment variable SSLKEYLOGFILE=<path>
        → Chrome and Firefox will write session keys to this file
Step 3: In Wireshark: Edit → Preferences → Protocols → TLS
        → Set (Pre)-Master-Secret log filename to the key log file
Step 4: Traffic decrypts → HTTP2 packets become visible
Step 5: Available data formats after decryption:
        Frame | Decrypted TLS | Decompressed Header | Reassembled TCP | Reassembled SSL
```

> ⚠️ Key log file MUST be created during the capture session. Post-capture key logs cannot decrypt earlier traffic.

## 🔑 Task 9: Bonus — Hunt Cleartext Credentials

### Wireshark Credentials Feature

```
Tools → Credentials
```

- Supported protocols: **FTP, HTTP, IMAP, POP, SMTP**
- Shows: Packet number, Protocol, Username, Additional Info
- Clicking packet number → selects password packet
- Clicking username → selects username packet
- Available from Wireshark **v3.1+**

> ⚠️ Do not rely solely on this feature — manual checking is always required.

## 🔥 Task 10: Bonus — Actionable Results (Firewall ACL Rules)

### Wireshark Firewall Rule Generation

```
Tools → Firewall ACL Rules
```

Supported rule formats:
- Netfilter (iptables)
- Cisco IOS (standard/extended)
- IP Filter (ipfilter)
- IPFirewall (ipfw)
- Packet filter (pf)
- Windows Firewall (netsh new/old format)

> Rules are generated for implementation on an **outside firewall interface**.
