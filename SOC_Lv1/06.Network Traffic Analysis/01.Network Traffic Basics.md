# 🌐 Network Traffic Basics — Reference Sheet

> **TL;DR:** Network Traffic Analysis (NTA) = capturing + inspecting + analyzing packets across all TCP/IP layers to detect threats, reconstruct attacks, and verify alerts. Logs alone are insufficient — full packet capture (TAP or port mirroring) and flow statistics (NetFlow/IPFIX) are needed to see payloads and patterns logs miss. Key attack techniques visible only in full packets: DNS tunneling, session hijacking, fragmentation attacks, ARP poisoning.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| NTA ≠ Wireshark | NTA is a process combining logs, packet capture, and flow stats; Wireshark is one tool |
| Logs ≠ full packets | Logs capture selected fields only — payloads and full headers are not logged |
| Firewall logs miss DNS payload | DNS queries are logged; TXT record content (C2 commands) is not |
| HTTP logs miss ZIP file contents | GET request and 200 response are logged; the downloaded file contents are not |
| SPANs can impact performance | Port mirroring adds processing load on the switch; physical TAPs do not |
| TAP operates only at Link layer | No IP/MAC address needed; copies electrical/light signals directly |
| Fragmentation attacks bypass IDS | Tiny fragments or overlapping offsets evade signature-based detection |
| Session hijacking needs sequence numbers | Firewall logs rarely include TCP sequence numbers — full packet capture required |
| ARP poisoning needs full packet context | Logs show MACs, but gratuitous ARP storms and MAC-from-multiple-interfaces are invisible in logs |
| NetFlow ≠ full packet capture | NetFlow captures metadata (flow stats), not packet payload |
| 1 Gbps line for 1 day ≈ 10.8 TB storage | Plan storage capacity carefully before deploying full packet capture |

## 1. What Is Network Traffic Analysis?

### Definition
| Term | Definition |
|---|---|
| **NTA (Network Traffic Analysis)** | Process of capturing, inspecting, and analyzing data flowing through a network |
| **Goal** | Complete visibility into what is communicated inside and outside the network |
| **NOT a synonym for** | Wireshark (Wireshark is one tool; NTA is a broader process) |

### NTA Use Cases
| Category | Examples |
|---|---|
| **Performance monitoring** | Detect sudden bandwidth spikes, slow network segments |
| **Anomaly detection** | Identify unusual protocols, unexpected hosts, high query rates |
| **Threat detection** | C2 beaconing, data exfiltration, lateral movement, malware download |
| **Incident response** | Reconstruct attack timeline, extract malicious payloads |
| **Alert validation** | Verify whether a SIEM/IDS alert reflects a real threat |

### Q&A
| Question | Answer |
|---|---|
| Technique used to smuggle C2 commands via DNS? | **DNS tunneling** |

## 2. TCP/IP Stack — What Can Be Observed

### TCP/IP Layer Overview
| Layer | TCP/IP Name | Header Contains | What Logs Typically Show | What Requires Full Packet Capture |
|---|---|---|---|---|
| 4 | **Application** | Protocol headers + payload | HTTP method, URL, status code, DNS query | Payload content (file contents, DNS TXT data, credentials) |
| 3 | **Transport** | TCP/UDP header (ports, flags, seq/ack) | Source/dest ports, TCP flags | Sequence numbers (session hijacking detection) |
| 2 | **Internet (IP)** | IP header (src/dst IP, TTL, fragment offset) | Src IP, dst IP, TTL | Fragment offset, total length (fragmentation attack detection) |
| 1 | **Link** | MAC addresses, frame type | Src/dst MAC | Gratuitous ARP, conflicting MACs (ARP poisoning detection) |

## 3. Layer-by-Layer Analysis Examples

### Application Layer — HTTP Example
```
# What logs capture:
GET /downloads/suspicious_package.zip HTTP/1.1
Host: www.tryhackrne.thm
→ Logged: method, URL, host, response code (200 OK), Content-Length

# What logs MISS (requires full packet capture):
[binary ZIP file bytes — 10,485,760 bytes]
→ Actual file contents are NOT logged
```

| HTTP Field | Logged? | Notes |
|---|---|---|
| Request method (GET/POST) | ✅ Yes | Visible in proxy/web logs |
| URL path | ✅ Yes | Visible in proxy/web logs |
| Host header | ✅ Yes | Visible in proxy/web logs |
| Response code | ✅ Yes | 200, 404, 403 etc. |
| Content-Type | ✅ Yes | `application/zip` etc. |
| Content-Length | ✅ Yes | `10485760` bytes |
| **File payload / body** | ❌ No | **Requires full packet capture** |

### Application Layer — DNS Tunneling Example
```
# DNS log entries (what firewall logs):
2025-10-03 09:15:23 SRC=192.168.1.16 QUERY=aj39skdm.malicious-tld.com QTYPE=A
2025-10-03 09:15:31 SRC=192.168.1.16 QUERY=msd91azx.malicious-tld.com QTYPE=A
2025-10-03 09:15:45 SRC=192.168.1.16 QUERY=cmd01.malicious-tld.com QTYPE=TXT

# What logs provide:
# - Query name + type
# - Source host IP
# - Timestamp

# What logs MISS (requires full packet capture):
# DNS TXT reply content:
TXT: "SSBsb3ZlIHlvdXIgY3VyaW91c2l0eQ=="
# → Base64-encoded C2 command — INVISIBLE in logs
```

| DNS Log Field | Logged? | Use |
|---|---|---|
| Query name (FQDN) | ✅ Yes | Check domain reputation (VirusTotal, AbuseIPDB) |
| Query type (A, TXT, MX) | ✅ Yes | TXT = suspicious for C2 |
| Source host IP | ✅ Yes | Identify compromised host |
| Destination IP | ✅ Yes | Check IP reputation |
| Timestamp | ✅ Yes | Build attack timeline |
| **TXT record content (payload)** | ❌ No | **Requires full packet capture** |

### Transport Layer — Session Hijacking Detection
```
# Wireshark output showing session hijacking:
No. 1  192.168.1.45  → 172.217.22.14  TCP  SYN       Seq=0
No. 2  172.217.22.14 → 192.168.1.45   TCP  SYN,ACK   Seq=0
No. 3  192.168.1.45  → 172.217.22.14  TCP  ACK        Seq=1
No. 4  192.168.1.45  → 172.217.22.14  TCP  PSH,ACK    Seq=1
No. 5  172.217.22.14 → 192.168.1.45   TCP  ACK
No. 6  192.168.99.200→ 172.217.22.14  TCP  PSH,ACK    Seq=34567232 ← HIJACK
#                                                      ^^ Massive seq jump = attacker injecting
```

| TCP Header Field | Attack Detected | How |
|---|---|---|
| **Sequence number** | Session hijacking | Sudden large jump in sequence number |
| Source IP | IP spoofing | IP mismatch in session |
| Flags (SYN/ACK/RST) | Scan, flood | Unusual flag combinations |

### Internet Layer — Fragmentation Attack Detection
```
# Overlapping fragment example:
No. 1  203.0.113.45 → 192.168.1.10  Offset=0,    Len=1480  [MF]
No. 2  203.0.113.45 → 192.168.1.10  Offset=1480, Len=1480  [MF]
No. 3  203.0.113.45 → 192.168.1.10  Offset=1480, Len=64    ← OVERLAP (same offset as No. 2)
# → Attacker creates ambiguous reassembly to evade IDS
```

| IP Header Field | Needed For | Attack Detected |
|---|---|---|
| Src/dst IP | Most use cases | IP spoofing |
| TTL | Traceroute, hop count | TTL manipulation |
| Fragment offset | Fragmentation analysis | IDS evasion via overlapping fragments |
| Total length | Fragment size analysis | Tiny fragment attacks |

### Link Layer — ARP Poisoning Detection
```
# ARP poisoning packet capture:
No. 1  192.168.1.1   → Broadcast     ARP  Who has 192.168.1.10?
No. 2  192.168.1.10  → 192.168.1.1   ARP  192.168.1.10 is at 00:11:22:33:44:55
No. 3  192.168.1.200 → 192.168.1.1   ARP  192.168.1.10 is at aa:bb:cc:dd:ee:ff ← Spoof
No. 4  192.168.1.200 → 192.168.1.10  ARP  192.168.1.1  is at aa:bb:cc:dd:ee:ff ← Spoof
# → Attacker poisons ARP cache of both parties; traffic relayed through attacker
```

| Indicator | What It Means |
|---|---|
| Unsolicited ARP replies | Attacker proactively poisoning ARP cache |
| Same MAC for different IPs | One device claiming multiple IP addresses |
| Multiple MACs for same IP | Conflicting ARP entries — possible poisoning |
| Gratuitous ARP storm | Mass ARP broadcast — attacker claiming network addresses |

| Question | Answer |
|---|---|

## 4. Network Traffic Sources and Flows

### Traffic Sources
| Category | Description | Examples |
|---|---|---|
| **Intermediary** | Devices traffic passes through; generate less traffic | Firewalls, switches, routers, web proxies, IDS/IPS, access points, WLC |
| **Endpoint** | Devices where traffic originates/ends; **bulk of bandwidth** | Servers, workstations, IoT, printers, VMs, cloud resources, mobile devices |

### Protocols by Source Type
| Source Type | Protocols Generated |
|---|---|
| Intermediary | EIGRP, OSPF, BGP (routing); SNMP, PING (management); Syslog (logging); ARP, STP, DHCP (support) |
| Endpoint | HTTP/S, DNS, SMB, SSH, RDP, SMTP, Kerberos, SQL, REST APIs, NetFlow, Syslog |

### Traffic Flows
| Flow | Direction | Description | Monitoring Priority |
|---|---|---|---|
| **North-South (NS)** | LAN ↔ WAN | Traffic crossing the firewall (external communication) | High — all passes firewall |
| **East-West (EW)** | LAN ↔ LAN | Internal traffic between hosts/servers | Often lower — but critical for lateral movement detection |

### North-South Traffic — Common Protocols
| Protocol | Port | Direction | Notes |
|---|---|---|---|
| HTTPS | 443 | Both | Encrypted web traffic — inspect via TLS proxy |
| DNS | 53 | Both | External name resolution; check for tunneling |
| SSH | 22 | Both | Remote management; check for unusual destinations |
| VPN | Various | Both | Encrypted tunnel; verify authorized endpoints |
| SMTP | 25/587 | Outbound | Email; watch for data exfiltration |
| RDP | 3389 | Both | Remote desktop; watch for external RDP |

### East-West Traffic — Common Services
| Category | Protocol/Service | Port | Notes |
|---|---|---|---|
| **Directory & Auth** | Kerberos | 88 | AD authentication; watch for Pass-the-Ticket |
| **Directory & Auth** | LDAP | 389/636 | AD queries |
| **Directory & Auth** | RADIUS / TACACS+ | 1812/49 | Network access control |
| **File Shares** | SMB/CIFS | 445 | Network drives; lateral movement vector |
| **File Shares** | IPP/LPD | 631/515 | Printing protocols |
| **Infrastructure** | DHCP | 67/68 | IP assignment |
| **Infrastructure** | ARP | — | Layer 2 address resolution |
| **Infrastructure** | Internal DNS | 53 | Internal name resolution |
| **App Communication** | SQL over TCP | 1433/3306 | Database connections |
| **App Communication** | REST/gRPC | Various | Microservices APIs |
| **Backup & Replication** | File replication | Various | Data center sync |
| **Monitoring** | SNMP | 161 | Device health metrics |
| **Monitoring** | Syslog | 514 | Centralized logging |
| **Monitoring** | NetFlow/IPFIX | 2055/4739 | Traffic flow telemetry |

### Flow Examples
| Flow | Mechanism | Key Points |
|---|---|---|
| **HTTPS with TLS Inspection** | Web proxy acts as MITM between client and server | Two separate TCP sessions; client sees proxy as web server |
| **External DNS** | Host → Internal DNS → Firewall → External DNS → reply back | Internal DNS caches; forwards cache misses externally on port 53 |
| **SMB with Kerberos** | Host → KDC (TGT) → KDC (service ticket) → SMB session | Authentication must succeed before SMB session is established |

### Q&A
| Question | Answer |
|---|---|
| Which device category generates the most traffic? | **endpoint** |
| Which service must be contacted before SMB can connect? | **Kerberos** |
| What does TLS stand for? | **Transport Layer Security** |

## 5. How to Observe Network Traffic

### Three Observation Methods
| Method | What It Provides | Limitations |
|---|---|---|
| **Logs** | Selective fields (src/dst IP, port, method, status) from each device | No payload; vendor-defined; no universal standard |
| **Full Packet Capture** | Complete packet content at every layer | High storage cost; requires TAP or port mirror placement |
| **Network Statistics (NetFlow/IPFIX)** | Flow metadata (who talked to whom, how much, when) | No payload — metadata only |

### Full Packet Capture — Two Methods
| Method | Type | How It Works | Performance Impact |
|---|---|---|---|
| **Network TAP** | Physical (hardware) | Placed inline; copies electrical/light signals at Link layer; no IP/MAC needed | Near zero — passive copy |
| **Port Mirroring (SPAN)** | Software (config) | Switch duplicates packets from source port to destination port | Can impact performance at high traffic volumes |

### Port Mirroring (SPAN) — Cisco Config
```bash
# Configure SPAN on Cisco switch
# Copy traffic from fastEthernet0/1 → fastEthernet0/2 (monitoring device)

Switch(config)# monitor session 1 source interface fastEthernet0/1
Switch(config)# monitor session 1 destination interface fastEthernet0/2

# Verify session
Switch# show monitor session 1
```

### Full Packet Capture — Best Practices
| Factor | Guidance |
|---|---|
| **Placement** | TAP/mirror must be positioned where target traffic passes |
| **Duration** | 1 Gbps line for 24 hours ≈ **10.8 TB** storage required |
| **Mirror vs TAP** | TAP = zero performance impact; SPAN = potential performance hit |
| **Virtual environments** | VMware vSwitch supports port mirroring; AWS offers VPC Traffic Mirroring |

### Storage Calculation Reference
| Line Speed | Duration | Approximate Storage Needed |
|---|---|---|
| 1 Gbps | 1 hour | ~450 GB |
| 1 Gbps | 24 hours | ~**10.8 TB** |
| 10 Gbps | 24 hours | ~108 TB |
| 40 Gbps | 24 hours | ~432 TB |

### Packet Capture & Analysis Tools
| Tool | Type | Use Case |
|---|---|---|
| **Wireshark** | GUI packet analyzer | Deep packet inspection, filtering, protocol decoding |
| **tcpdump** | CLI packet capture | Lightweight capture on Linux; scripting-friendly |
| **Snort** | IDS/IPS | Signature-based detection on captured traffic |
| **Suricata** | IDS/IPS | Multi-threaded; supports rules and file extraction |
| **Zeek (Bro)** | Network analysis framework | Generates structured logs from packet data |

### Network Statistics Protocols
| Protocol | Origin | Standard? | Key Features |
|---|---|---|---|
| **NetFlow** | Cisco (proprietary) | Partial (v9 added templating) | Flow metadata: src/dst IP, ports, bytes, packets, timestamps |
| **IPFIX** | IETF (based on NetFlow v9) | ✅ Vendor-neutral standard | Same as NetFlow + flexible field configuration |

### NetFlow Output Fields
| Field | Description |
|---|---|
| IPV4 SOURCE ADDRESS | Origin IP of the flow |
| IPV4 DESTINATION ADDRESS | Destination IP of the flow |
| TRNS SOURCE PORT | Source transport port |
| TRNS DESTINATION PORT | Destination transport port |
| IP PROTOCOL | Protocol number (1=ICMP, 6=TCP, 17=UDP) |
| counter bytes | Total bytes transferred in the flow |
| counter packets | Total packets in the flow |
| timestamp first / last | Flow start and end times |
| FLOW DIRECTION | Input or Output |

## 6. Attack Detection — Summary Table

| Attack | Layer | What Logs Show | What Full Packet Capture Reveals | Detection Method |
|---|---|---|---|---|
| **DNS Tunneling** | Application | Query name, type, source IP | TXT record payload (Base64-encoded C2) | Inspect DNS TXT content; high query rate to same TLD |
| **Data Exfiltration via HTTP** | Application | GET URL, response code, Content-Length | ZIP/binary file payload | Extract and analyze file bytes |
| **Session Hijacking** | Transport | Src/dst ports, flags | Sequence number jump | Monitor seq numbers for large discontinuities |
| **Fragmentation Attack (IDS evasion)** | Internet | Src/dst IP | Fragment offset overlap | Inspect fragment offset + total length fields |
| **ARP Poisoning** | Link | Src/dst MAC | Gratuitous ARPs, conflicting MACs | Detect same MAC claiming multiple IPs |
| **C2 Beaconing** | Application | DNS query rate | Periodic outbound connection pattern | NetFlow + full packet for content |
| **Lateral Movement** | Transport/App | SMB/RDP connections | Kerberos ticket abuse, credential reuse | East-West traffic monitoring |
