# 🐧 Linux Logging for SOC — Reference Sheet

> **TL;DR:** Linux logs most events as **plain text in `/var/log/`** (no Event Viewer needed), but the logs are less structured than Windows. The top three SOC sources are **`auth.log`** (logins, user management, sudo), **app-specific logs** (web/mail/DB), and **runtime logs**. Linux does **not** record process/file/network activity by default — you add that with **`auditd`** (read it via `ausearch -i -k <key>`) or alternatives like Sysmon for Linux, Falco, or Osquery. Everything ultimately hangs off **system calls** (e.g. `execve`), which attackers can't bypass.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| Plain text ≠ easy | Linux logs are readable text, but **less structured** than Windows — no event IDs, no strict format. Parsing is harder, not easier. |
| `auth.log` ≠ only auth | Despite the name it also stores **user management** (`useradd`/`usermod`/`userdel`/`passwd`) and **sudo command** events. |
| Distro path differences | RHEL/CentOS use **`/var/log/secure`** (not `auth.log`) and **`/var/log/dnf.log`/`yum.log`** (not `dpkg.log`). Match the log file to the distro. |
| `\[` must be escaped in grep | `[` starts a regex character class. `grep 'passwd['` → *Invalid regular expression*. Use `grep 'passwd\['` to match the literal `[` in `commandname[PID]`. |
| Bash history misses a lot | It does **not** log non-interactive commands (cron jobs, OS-initiated, web servers), so it's unreliable for SOC. |
| Leading space hides commands | A command typed with a **leading space** is not saved to `~/.bash_history` (default `HISTCONTROL`). |
| History writes on logout | Commands live in **memory** during the session and are flushed to `~/.bash_history` only at logout — the file lags the live session. |
| Other shells dodge history | Running `sh` (or another shell) instead of `bash` means commands are **not** written to `.bash_history`. |
| No runtime logging by default | Linux does **not** record process creation, file changes, or network events out of the box — add `auditd` / Sysmon for Linux / Falco / Osquery / EDR. |
| `auid` vs `uid` | `auid` = the account **originally used to log in**; `uid` = who **actually ran** the command. They differ after `sudo`/`su`. |
| auditd output is SIEM-unfriendly | Verbose and hard to read/ingest. Use `ausearch -i` for human-readable output, or switch to an alternative. |
| Renamed tools beat keyword grep | A scanner can be renamed (`./scanner`, `naabu`, etc.). **Correlate by `exe=/path` and `pid`/`ppid` lineage**, not by tool name. |
| More logs ≠ better detection | An attack buried in a terabyte of noise is still invisible. Build **balanced, high-risk-focused** rulesets. |

## 1️⃣ Working With Text Logs (Task 2)

| Concept | Detail |
|---|---|
| Where logs live | Most logs are under **`/var/log/`**, stored as plain text. |
| `/var/log/syslog` | Aggregated stream of various system events (RHEL equivalent: `/var/log/messages`). |
| Why filter | A real `syslog` has thousands of lines; only a few matter — narrow your search aggressively. |
| Logging caveats | Linux lets you change log format, verbosity, and location freely. Across 100s of distros, logs may look different or not exist. |

### View the start of syslog

**Purpose:** Quick peek at the consolidated event stream.

```bash
cat /var/log/syslog | head
# Shows the first ~10 lines, e.g. systemd-timesyncd clock sync, CRON jobs, dbus activity
```

### Filter / exclude a keyword

**Purpose:** Isolate (or remove) one event type.

```bash
cat /var/log/syslog | grep CRON
# Only cronjob lines, e.g.:
# thm-vm CRON[1048]: (root) CMD (date > mycrondebug.log)

cat /var/log/syslog | grep -v CRON
# Everything EXCEPT CRON lines (-v = invert match)
```

### Discover what's being logged

**Purpose:** Find which file holds the events you want when you don't know where to look.

```bash
ls -l /var/log
# Lists log files: apt/ audit/ auth.log dpkg.log journal/ kern.log syslog ...

grep -R -E "auth|login|session" /var/log
# -R recurses all files in /var/log; -E enables extended regex (alternation with |)
# Surfaces files that mention logins so you can narrow your next search
```

### Task 2 answer commands

```bash
cat /var/log/syslog | grep timesync   # → time server domain (ntp.ubuntu.com)
cat /var/log/syslog | grep Yama        # → kernel Yama message ("becoming mindful.")
```

## 2️⃣ Authentication Logs (Task 3)

**File:** `/var/log/auth.log` (Debian/Ubuntu) — `/var/log/secure` on RHEL-based systems.
Contains login/logout, user management, and sudo command events.

### Login / logout events

| Source keyword | Meaning | Example log fragment |
|---|---|---|
| `login:session` | Local, on-keyboard login | `login[1138]: pam_unix(login:session): session opened for user bob(uid=1001)` |
| `sshd:session` | Remote login via SSH | `sshd[839]: pam_unix(sshd:session): session opened for user alice(uid=1002)` |
| `samba:session` | Remote login via SMB | `smbd[1795]: pam_unix(samba:session): session opened for user alice` |
| `cron:session` | Cron job session as root | `CRON[41925]: pam_unix(cron:session): session opened for user root(uid=0)` |
| `sudo:session` | Privilege escalation | `sudo: pam_unix(sudo:session): session opened for user root by carol(uid=1003)` |

**Purpose:** List every session open/close.

```bash
cat /var/log/auth.log | grep -E 'session opened|session closed'
```

### SSH-specific events

SSH daemon writes its own success/failure lines to `auth.log` in a different format.

**Format:** `<is-successful> <auth-method> for <user> from <ip>`

```bash
cat /var/log/auth.log | grep "sshd" | grep -E 'Accepted|Failed'
# Failed password for root  from 222.124.17.227 port 50293 ssh2   <- brute-force / spray
# Accepted publickey for bob from 10.19.92.18  port 55050 ssh2    <- successful key login
```

> **Detection tip:** One source IP failing across **multiple usernames** = password spraying / user enumeration.

### User management events

The log prefixes each event with `commandname[PID]`, so grep for the command name + escaped `[`.

| Command in log | Event |
|---|---|
| `passwd[…]` | Password change — `password for 'ubuntu' changed by 'root'` |
| `userdel[…]` | User deletion — `delete user 'oldbackdoor'` |
| `useradd[…]` | User creation — `new user: name=backdoor, UID=1002, GID=1002, shell=/bin/sh` |
| `usermod[…]` | Group/attribute change — `add 'backdoor' to group 'sudo'` |

**Purpose:** Catch account tampering (a classic persistence/privesc trail).

```bash
cat /var/log/auth.log | grep -E '(passwd|useradd|usermod|userdel)\['
```

#### Why the `\[` ? (key syntax point)

- In logs the pattern is **`commandname[PID]`** → `useradd[12345]`, `passwd[12347]`.
- In regex, `[` opens a **character class** (`[abc]`, `[0-9]`), so unescaped it errors out.
- `\[` tells grep to match a **literal `[`**.

```bash
grep 'passwd[' /var/log/auth.log    # ❌ Invalid regular expression
grep 'passwd\[' /var/log/auth.log   # ✅ Matches passwd[12345], passwd[67890], ...
```

### Commands run with sudo

**Purpose:** Reconstruct what a user did with elevated rights — often the heart of an incident.

```bash
cat /var/log/auth.log | grep -E 'COMMAND='
# ubuntu : TTY=pts/0 ; COMMAND=/usr/bin/systemctl stop edr   <- disabling EDR (suspicious!)
# ubuntu : TTY=pts/0 ; COMMAND=/usr/bin/ufw status numbered  <- recon of firewall state
# ubuntu : TTY=pts/0 ; COMMAND=/usr/bin/su                   <- escalating to root
```

## 3️⃣ Common Linux Logs (Task 4)

### Generic system logs

| File (Debian) | RHEL equivalent | Contents |
|---|---|---|
| `/var/log/kern.log` | — | Kernel messages and errors (advanced investigations) |
| `/var/log/syslog` | `/var/log/messages` | Consolidated stream of Linux events |
| `/var/log/dpkg.log` / `/var/log/apt` | `/var/log/dnf.log` / `/var/log/yum.log` | Package manager logs |

> Valuable in **DFIR**, but noisy and hard to parse — rarely part of the daily SOC routine.

**Quick distro check:** prompt `ubuntu@` → Debian-based → use `dpkg.log`; `centos@`/`redhat@` → RHEL-based → use `dnf.log`/`yum.log`.

### App-specific logs

Monitor the program you care about: **DB logs** (queries), **mail logs** (phishing), **container logs** (anomalies), **web server logs** (who hit which page, when).

```bash
cat /var/log/nginx/access.log
# Each line = one web request:
# 10.0.1.12 - - [11/08/2025:14:33:09 +0000] "POST /login HTTP/1.1" 302 112
# 10.0.5.21 - - [11/08/2025:17:56:23 +0000] "GET /admin HTTP/1.1" 403 104   <- blocked admin probe
```

### Package manager log (Task 4 answer command)

**Purpose:** Find **when/what version** of software was installed during an investigation.

```bash
cat /var/log/dpkg.log | grep unzip
# 2025-08-12 16:41:24 install unzip:amd64 <none> 6.0-28ubuntu4.1
#                              ^package                ^version
```

### Bash history

| Fact | Detail |
|---|---|
| What it is | Records each command after you press Enter, per user, in `~/.bash_history`. |
| When written | Held in **memory** during the session, flushed to file at **logout**. |
| View past sessions | `cat /home/<user>/.bash_history` |
| View current + past | `history` |
| SOC value | **Low** — misses non-interactive commands and is trivially evaded. |

**Evasion techniques (why it's unreliable):**

```bash
 echo "You will never see me in logs!"   # leading space → not recorded
nano legit.sh && ./legit.sh              # commands hidden inside a script
sh                                       # /bin/sh doesn't save Bash history
$ echo "I am no longer tracked by Bash!"
```

## 4️⃣ Runtime Monitoring & System Calls (Task 5)

| Concept | Detail |
|---|---|
| Runtime events | Process creation, file changes, network events — **not logged by default** on Linux. |
| Parallel to Windows | Windows has the same gap → solved with **Sysmon**; Linux uses **auditd** (and friends). |
| System call (syscall) | The mechanism every program uses to ask the OS for a service (open file, create process, etc.). |
| Scale | **300+** syscalls in Linux; **`execve`** executes a program. |
| Why it matters | EDRs/logging tools hook syscalls and render them readable. Attackers **can't bypass** syscalls, so monitoring them is reliable. |

> **Coverage mindset:** "The broader you log, the more threats you can detect." Auth-only < +web/bash history < +runtime events.

## 5️⃣ Using Auditd (Task 6)

| Element | Detail |
|---|---|
| What it is | Built-in **Audit Daemon** for runtime monitoring. |
| Rules location | `/etc/audit/rules.d/` — defines which syscalls to watch + filters. |
| Raw log | `/var/log/audit/audit.log` (hard to read directly). |
| Reader tool | **`ausearch`** — formats output and supports filtering. |
| Tuning principle | Focus on **highest-risk** events; build balanced rulesets (volume ≠ value). |

### auditd record structure

A single event is split into ~4 line types:

| Line type | Shows |
|---|---|
| `PROCTITLE` | The full process command line |
| `CWD` | Current working directory |
| `PATH` | File/path touched (for file events) |
| `SYSCALL` (+ `EXECVE`) | Syscall details and arguments |

### Key SYSCALL fields

| Field | Meaning / use |
|---|---|
| `pid` / `ppid` | Process ID & Parent PID — **link events / build a process tree** |
| `auid` | Audit user = account **originally logged in** (keyboard or SSH) |
| `uid` | User who **actually ran** the command (differs from `auid` after `sudo`/`su`) |
| `tty` | Session identifier — separate concurrent users on one host |
| `exe` | **Absolute path** to the executed binary — strong basis for detection rules |
| `key` | Optional tag set in audit rules — lets you filter (`-k <key>`) |

### Search by key (process execution)

**Purpose:** Pull events tagged with a specific audit rule key.

```bash
ausearch -i -k proc_wget
# -i = interpret (human-readable: timestamps, names instead of numeric IDs)
# PROCTITLE : proctitle=wget https://files.tryhackme.thm/report.zip
# SYSCALL   : syscall=execve ... ppid=3752 pid=3888 auid=ubuntu uid=root exe=/usr/bin/wget key=proc_wget
```

### Search by key (file access)

**Purpose:** Detect changes to critical files (SSH config, cron, system settings).

```bash
ausearch -i -k file_sshconf
# PATH    : name=/etc/ssh/sshd_config
# SYSCALL : syscall=openat ... exe=/usr/bin/nano key=file_sshconf
```

### Task 6 answer commands

```bash
sudo ausearch -i -k file_thmsecret | grep secret.thm
# → first-access time of secret.thm (PROCTITLE proctitle=cat /secret.thm)

sudo ausearch -i -k proc_wget | grep github
# → wget download from GitHub; original filename in the command line
# proctitle=wget https://github.com/projectdiscovery/naabu/.../naabu_2.3.5_linux_amd64.zip -O /tmp/naabu.zip

sudo ausearch -m EXECVE -i | tail -n 50
# -m EXECVE = filter by message type; reveals command-line args, incl. the scanned CIDR
```

### Reconstructing the attack chain (worked example)

The naabu scan was rebuilt purely from auditd EXECVE/PROCTITLE records:

```
wget  → unzip → chmod +x → ./naabu -host 192.168.50.0/24 -top-ports 100
(download)  (extract)  (make exec)  (run scan against the target range)
```

**Cleaner ways to find the range next time** (no dedicated key existed for the scan):

```bash
sudo ausearch -m EXECVE -i | grep -A3 -B2 naabu        # context around the tool name
sudo ausearch -m EXECVE -i | grep 192.168              # find the CIDR argument directly
sudo ausearch -i -m EXECVE,PROCTITLE | grep -iE 'naabu|[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+'
# Bound the window to reduce noise (just after the wget event):
sudo ausearch -m EXECVE -i --start 08/13/25 18:25:00 --end 08/13/25 19:00:00
```

> **Triage method (from the debrief):** prioritize **argument-rich** records (`EXECVE`/`PROCTITLE`), correlate by `exe=`/`pid`/`ppid` rather than tool name (tools get renamed), and **bound `ausearch` with `--start`/`--end`** to the incident window.

### Auditd alternatives

| Tool | Best for |
|---|---|
| **Sysmon for Linux** | Teams already on Sysmon who want XML output |
| **Falco** | Modern, open-source; great for **containerized** systems |
| **Osquery** | Broad security use cases (SQL-style host querying) |
| **EDRs** | Most can track Linux runtime events |

> All four (and auditd) work on the **same principle: monitoring system calls**. Learn syscalls once and the rest follow.

## ✅ Key Takeaways (Task 7)

- Linux logging can be chaotic, but usually stores enough detail to detect the threat.
- Logs default to **`/var/log/`**, mostly plain text.
- Top 3 SOC sources: **`auth.log`**, **app-specific logs**, **runtime logs**.
- Bash history is unreliable — prefer **`auditd`** or an alternative.
