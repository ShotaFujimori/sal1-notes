# 🛡️ Phishing Prevention — Exam Prep Reference Sheet

> **TL;DR:** Email authentication relies on three DNS-based standards — SPF (authorized senders), DKIM (cryptographic signature), DMARC (policy enforcement) — plus S/MIME for end-to-end encryption. SMTP traffic analysis with Wireshark reveals how servers handle, flag, and reject suspicious mail. Organizations layer technical controls with user training to reduce phishing risk.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| SPF `SoftFail` ≠ blocked | Email is still delivered — just flagged as suspicious |
| DKIM survives forwarding; SPF does not | Forwarded mail breaks SPF but keeps DKIM signature intact |
| DMARC requires both SPF **and** DKIM alignment | Neither alone is sufficient for full DMARC protection |
| `p=none` is the weakest DMARC policy | Monitor-only; no emails are blocked or quarantined |
| `p=reject` is the strongest | Failing emails are completely blocked at the gateway |
| S/MIME encryption uses recipient's **public** key | Only the recipient's **private** key can decrypt it |
| S/MIME signature uses sender's **private** key | Verified by the recipient using sender's **public** key |
| `permerror` in DKIM ≠ spoofing | Could be misconfiguration — check "no key for signature" |
| Wireshark `smtp` filter ≠ `imf` filter | `smtp` shows transport; `imf` reveals email content/attachments |
| SMTP response codes are 3-digit | 2xx = success, 4xx = temporary fail, 5xx = permanent fail |

## 📬 Email Authentication Stack — Overview

| Protocol | Layer | What It Does | DNS Record Type |
|---|---|---|---|
| **SPF** | Transport | Authorizes which IPs/domains can send on behalf of a domain | TXT |
| **DKIM** | Content | Adds cryptographic signature to verify message integrity | TXT |
| **DMARC** | Policy | Aligns SPF+DKIM results; defines what to do on failure | TXT |
| **S/MIME** | Application | Encrypts and digitally signs email content end-to-end | Certificate (not DNS) |

## ✉️ Task 2 — SPF (Sender Policy Framework)

### What SPF Does
Receiving mail server checks the sender domain's DNS TXT record to verify the sending IP is authorized. Based on the result, it takes an action.

### SPF Record Syntax
```
v=spf1 ip4:127.0.0.1 include:_spf.google.com -all
```

| Component | Meaning |
|---|---|
| `v=spf1` | Start of SPF record (required) |
| `ip4:127.0.0.1` | Specific IPv4 address authorized to send |
| `ip6:` | Specific IPv6 address authorized to send |
| `include:_spf.google.com` | Authorize all IPs covered by another domain's SPF |
| `a` | Authorize the domain's A record IP |
| `mx` | Authorize the domain's MX record IPs |
| `~all` | SoftFail — unauthorized senders flagged but allowed |
| `-all` | Fail — unauthorized senders rejected (recommended) |
| `?all` | Neutral — no policy enforced |
| `+all` | Pass — allow all (insecure; avoid) |

### SPF Verification Results
| Result | Action | Meaning |
|---|---|---|
| `Pass` | ✅ Accept | Sending IP is authorized |
| `Neutral` | ✅ Accept | No policy statement for this IP |
| `None` | ✅ Accept | No SPF record found |
| `SoftFail` | ⚠️ Flag | IP not authorized but message accepted and flagged |
| `PermError` | ⚠️ Flag | Permanent SPF record error (syntax issue) |
| `Fail` | ❌ Reject | IP explicitly not authorized — discard |
| `TempError` | ❌ Reject | Temporary DNS lookup failure |

### Tools
| Tool | Purpose | URL |
|---|---|---|
| SPF Surveyor (dmarcian) | Visual DNS record inspection + syntax check | dmarcian.com/spf-survey |
| Google Messageheader | Shows SPF result from raw email header | toolbox.googleapps.com |

| Question | Answer |
|---|---|
| How many domains authorized to send for TryHackMe? | **3** |
| Intended action for `SoftFail`? | **Flag** |

## 🔑 Task 3 — DKIM (DomainKeys Identified Mail)

### What DKIM Does
Sending server signs the email with a **private key**. Receiving server retrieves the **public key** from DNS to verify the signature. If matched → authentic.

### DKIM vs SPF
| Feature | SPF | DKIM |
|---|---|---|
| Checks | Sending IP authorization | Message content integrity |
| DNS record | TXT (IP list) | TXT (public key) |
| Survives forwarding | ❌ No — IP changes | ✅ Yes — signature travels with message |
| Protects against | IP spoofing | Message tampering |

### DKIM Record Syntax
```
v=DKIM1; k=rsa; p=<public_key>
```

| Tag | Meaning |
|---|---|
| `v=DKIM1` | DKIM version (optional but common) |
| `k=rsa` | Key type — RSA is standard |
| `p=` | Public key used to verify the digital signature |
| `s=` | Selector — identifies which DKIM key to use |
| `h=` | Header fields included in the signature |
| `bh=` | Hash of the email body |
| `b=` | The actual DKIM signature |

### DKIM Verification Results
| Result | Meaning |
|---|---|
| `pass` | Signature valid — message is authentic |
| `fail` | Signature invalid — message may be tampered |
| `permerror` | Permanent error (e.g., "no key for signature", misconfiguration) |
| `temperror` | Temporary DNS lookup error |
| `neutral` | DKIM present but no policy implication |
| `none` | No DKIM signature found |

### Tools
| Tool | Purpose | URL |
|---|---|---|
| DKIM Record Checker (dmarcian) | Inspect published DKIM record | dmarcian.com/dkim-inspector |
| DKIM Validator (dmarcian) | Validate DKIM signature in an email | dmarcian.com/dkim-validator |

| Question | Answer |
|---|---|
| Reason for `permerror` in sample header? | **no key for signature** |

## 🏛️ Task 4 — DMARC (Domain-Based Message Authentication, Reporting, and Conformance)

### What DMARC Does
Ties SPF and DKIM results together via **alignment** — verifies that the domain in the `From:` header matches the SPF/DKIM authenticated domain. If alignment fails, the DMARC policy determines what happens.

### DMARC Record Syntax
```
v=DMARC1; p=quarantine; rua=mailto:postmaster@website.com
```

| Tag | Meaning |
|---|---|
| `v=DMARC1` | Version — required |
| `p=` | Policy — what to do on failure (see table below) |
| `rua=` | Aggregate report destination (optional) |
| `ruf=` | Forensic/failure report destination (optional) |
| `pct=` | Percentage of emails subject to policy (default: 100) |
| `sp=` | Policy for subdomains |
| `adkim=` | DKIM alignment mode: `r` (relaxed) or `s` (strict) |
| `aspf=` | SPF alignment mode: `r` (relaxed) or `s` (strict) |

### DMARC Policies — Strength Comparison
| Policy | Action | Protection Level |
|---|---|---|
| `p=none` | No action — monitor only; reports sent if configured | ⭐ Weakest |
| `p=quarantine` | Move to spam/junk folder | ⭐⭐ Medium |
| `p=reject` | Completely block and discard the email | ⭐⭐⭐ Strongest |

### SPF + DKIM + DMARC Combined Logic
| SPF Result | DKIM Result | DMARC Alignment | DMARC Outcome |
|---|---|---|---|
| Pass | Pass | Aligned | ✅ Pass |
| Pass | Fail | Aligned on SPF | ✅ Pass |
| Fail | Pass | Aligned on DKIM | ✅ Pass |
| Fail | Fail | Neither aligned | ❌ Fail → apply `p=` policy |

### Tools
| Tool | Purpose | URL |
|---|---|---|
| Domain Checker (dmarcian) | Inspects DMARC, SPF, DKIM in one view | dmarcian.com/domain-checker |

### Q&A
| Question | Answer |
|---|---|
| Which DMARC policy provides the greatest protection? | **p=reject** |

## 🔐 Task 5 — S/MIME (Secure/Multipurpose Internet Mail Extensions)

### What S/MIME Does
Standard protocol for **digitally signing** and **encrypting** email messages using public key cryptography.

### S/MIME Two Components
| Component | Key Used | Security Properties Provided |
|---|---|---|
| **Digital Signature** | Sender signs with **private key** → recipient verifies with sender's **public key** | Authentication, Non-repudiation, Data Integrity |
| **Encryption** | Sender encrypts with recipient's **public key** → recipient decrypts with own **private key** | Confidentiality |

### S/MIME Security Properties
| Property | Component | Meaning |
|---|---|---|
| **Authentication** | Digital Signature | Confirms sender's identity via certificate |
| **Non-repudiation** | Digital Signature | Sender cannot deny sending the message |
| **Data Integrity** | Digital Signature | Detects any post-send modification |
| **Confidentiality** | Encryption | Only intended recipient can read the content |

### S/MIME Key Usage Summary
| Action | Who | Key Used |
|---|---|---|
| Sign email | Sender (Bob) | Bob's **private** key |
| Verify signature | Recipient (Mary) | Bob's **public** key |
| Encrypt email | Sender (Bob) | Mary's **public** key |
| Decrypt email | Recipient (Mary) | Mary's **private** key |

### S/MIME Workflow (Bob → Mary)
```
Bob                                        Mary
 │                                           │
 ├─ Signs with Bob's PRIVATE key ──────────► Verifies with Bob's PUBLIC key
 │                                           │
 ├─ Encrypts with Mary's PUBLIC key ───────► Decrypts with Mary's PRIVATE key
 │                                           │
 └─ Shares public key openly                 └─ Shares public key openly
```

### Q&A
| Question | Answer |
|---|---|
| Which S/MIME component ensures only the intended recipient can read the email? | **Encryption** |

## 📡 Task 6 — Analyzing SMTP Responses (Wireshark)

### Key Wireshark Filters for SMTP
| Filter | Purpose | Example |
|---|---|---|
| `smtp` | Show all SMTP traffic | — |
| `smtp.response.code` | Filter by response code field | — |
| `smtp.response.code == 220` | Show only "Service Ready" packets | — |
| `smtp.response.code == 553` | Show rejected mailbox packets | — |
| `smtp.response.code == 552` | Show security-blocked messages | — |
| `smtp.req.command == "EHLO"` | Show EHLO handshake packets | — |
| `smtp.req.command == "MAIL"` | Show MAIL FROM commands | — |
| `imf` | Internet Message Format — email content/headers/attachments | — |

### SMTP Response Code Reference
| Code | Category | Meaning |
|---|---|---|
| `220` | 2xx Success | Service ready |
| `250` | 2xx Success | Requested action OK |
| `354` | 3xx Intermediate | Start mail input |
| `421` | 4xx Temp Fail | Service not available (try again) |
| `450` | 4xx Temp Fail | Mailbox unavailable (try again) |
| `451` | 4xx Temp Fail | Local error — action aborted |
| `452` | 4xx Temp Fail | Insufficient storage |
| `500` | 5xx Perm Fail | Syntax error |
| `501` | 5xx Perm Fail | Syntax error in parameters |
| `503` | 5xx Perm Fail | Bad sequence of commands |
| `550` | 5xx Perm Fail | Mailbox unavailable / action not taken |
| `552` | 5xx Perm Fail | Exceeded storage; **potential security issue** |
| `553` | 5xx Perm Fail | Mailbox name not allowed (spamhaus block) |
| `554` | 5xx Perm Fail | Transaction failed |

### Task 6 Workflow
```bash
# 1. Open PCAP file in Wireshark
# 2. Filter by response code
smtp.response.code

# 3. Find specific code
smtp.response.code == 220   # Service ready
smtp.response.code == 553   # Blocked by spamhaus
smtp.response.code == 552   # Security issue
```

### Q&A
| Question | Answer |
|---|---|
| Wireshark filter for SMTP response codes? | **`smtp.response.code`** |
| Packets with response code 220? | **19** |
| Response code for spamhaus.org block? | **553** |
| Full response message for code 553? | **Requested action not taken: mailbox name not allowed (553)** |
| Messages blocked for security issues (code 552)? | **6** |

## 📨 Task 7 — Inspecting Emails and Attachments (IMF)

### IMF vs SMTP in Wireshark
| Filter | Layer | What It Shows |
|---|---|---|
| `smtp` | Transport | Server commands, response codes, routing |
| `imf` | Content | Email headers (From, To, Subject), body, attachments |

### IMF Analysis — What to Look For
| Field | Purpose |
|---|---|
| `From:` | Sender address |
| `To:` | Recipient address |
| `Subject:` | Email subject line |
| `Content-Type:` | Body type (text/html, multipart, application/zip, etc.) |
| `Content-Transfer-Encoding:` | How attachment is encoded (base64, quoted-printable) |
| `X-Mailer:` | Email client used to send the message |
| Attachment filename | Name of attached file |

### Common Content-Transfer-Encoding Types
| Encoding | Description | Used For |
|---|---|---|
| `base64` | Binary-to-text encoding | Attachments, binary files |
| `quoted-printable` | Text encoding for special chars | Text emails with special characters |
| `7bit` | Plain ASCII | Simple text emails |
| `8bit` | Extended ASCII | Internationalized text |

## 🏢 Task 8 — How Organizations Stop Phishing

### Technical Defenses
| Control | What It Does | Example Products |
|---|---|---|
| **Email Filtering** | Blocks/quarantines based on IP and domain reputation | Spamhaus, Barracuda |
| **Secure Email Gateways (SEGs)** | Scans for impersonation, spoofing, phishing patterns | Proofpoint, Mimecast, Cisco SEG |
| **Link Rewriting** | Replaces unknown URLs with safe proxied versions for real-time scanning | Microsoft Safe Links |
| **Sandboxing** | Isolates suspicious attachments/URLs in virtual environment to detect malicious behavior | Microsoft Safe Attachments, ANY.RUN |

### User-Facing Controls
| Control | What It Does |
|---|---|
| **Trust & Warning Indicators** | Visual banners: "External Sender", "Suspicious Link", trusted org badge |
| **Phishing Reporting** | One-click in-email reporting for suspicious messages |
| **User Awareness Training** | Education on phishing, social engineering, safe email practices |
| **Phishing Simulation Exercises** | Controlled phishing campaigns to test and reinforce training |

### Defense Layers — Summary
| Layer | Type | Examples |
|---|---|---|
| DNS / Authentication | Technical | SPF, DKIM, DMARC |
| Gateway | Technical | SEG, Email Filtering |
| URL Protection | Technical | Link Rewriting (Safe Links) |
| Attachment Protection | Technical | Sandboxing (Safe Attachments) |
| End-to-End Security | Technical | S/MIME |
| Visual Cues | User-facing | External sender banners, warning labels |
| Human Layer | User-facing | Awareness training, simulations, reporting |

### Q&A
| Question | Answer |
|---|---|
| Which technique safely analyzes suspicious attachments without risking infection? | **Sandboxing** |

## 🔁 Email Authentication Flow Summary

```
Sender sends email
        │
        ▼
Receiving Server Checks:
┌──────────────────────────────────────────────────┐
│ 1. SPF  — Is sending IP authorized by DNS TXT?   │
│    Pass/Neutral/None → Accept                    │
│    SoftFail/PermError → Flag                     │
│    Fail/TempError → Reject                       │
├──────────────────────────────────────────────────┤
│ 2. DKIM — Does signature match DNS public key?   │
│    pass → Authentic                              │
│    fail/permerror → Flag or Reject               │
├──────────────────────────────────────────────────┤
│ 3. DMARC — Do SPF+DKIM align with From: domain?  │
│    p=none → Monitor only                         │
│    p=quarantine → Move to spam                   │
│    p=reject → Block completely                   │
└──────────────────────────────────────────────────┘
        │
        ▼
    Email delivered / flagged / blocked
```
