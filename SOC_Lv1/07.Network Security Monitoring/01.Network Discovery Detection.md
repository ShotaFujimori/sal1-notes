# 🔍 Network Discovery Detection — Reference Sheet

> **TL;DR:** Network discovery is the reconnaissance phase where attackers (and defenders) scan networks to identify hosts, open ports, services, and vulnerabilities. SOC analysts must distinguish between external scanning (low severity, Reconnaissance phase) and internal scanning (high severity, Discovery/lateral movement phase). Key tools: Zeek logs, Kibana/Elasticsearch, firewall CSV logs, `head`, `cut` commands.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| Defenders also scan | Legitimate internal vulnerability scanners, web crawlers, and research orgs perform the same actions as attackers — always check allowlists before alerting |
| External scan = LOW severity | Attacker has NO foothold yet; block the IP but they may return with a masked IP |
| Internal scan = HIGH severity | Attacker IS already inside; blocking the firewall IP is NOT enough — escalate and do root cause analysis |
| ICMP (ping sweep) can be blocked | Many orgs block ICMP, so ping sweeps may return no results even if hosts are online — don't assume a host is offline |
| TCP SYN scan blends in | SYN scans mimic normal connection setup (SYN only, never completes handshake) and are harder to detect than full TCP connections |
| UDP scan is unreliable | No response ≠ open; scanner waits for timeout before marking port as open — slow and noisy |
| Horizontal ≠ Vertical | Horizontal: same port, many IPs (WannaCry-style). Vertical: many ports, same IP (single-target footprinting). Mixed scans also exist |
| conn_state "S0" = SYN only | In Zeek logs, `S0` means SYN sent, no SYN-ACK received — classic indicator of a TCP SYN scan |
| Severity escalation ≠ blocking | For internal scanning, don't just block — initiate IR, investigate the source host, identify how attacker got in |
| Allowlisting is critical | Without an allowlist of known internal scanners, SOC teams generate noise and miss real threats |

## 🌐 Network Discovery Overview

| Concept | Detail |
|---|---|
| **Network Discovery** | Process of mapping assets, open ports, services, and vulnerabilities on a network |
| **Attacker goal** | Find exploitable openings: IPs, ports, OS, service versions, vulnerabilities |
| **Defender goal** | Inventory assets, reduce attack surface, patch vulnerabilities |
| **Challenge** | Both attackers AND legitimate tools (scanners, crawlers) perform the same actions |

### SOC Mitigation Techniques

| Technique | Purpose |
|---|---|
| Allowlist known internal/benign scanners | Suppress noise from legitimate scanning activity |
| Threat Intelligence integration | Alert only on scanning from known malicious/suspicious IPs |
| Severity elevation via TI | Raise alert severity for TI-matched sources instead of only triggering/suppressing |
| Generic scanning use cases | Catch malicious scanning activity not covered by TI feeds |

## 🔴 External vs Internal Scanning

| Attribute | External Scanning | Internal Scanning |
|---|---|---|
| Source IP | External (public) IP | Private IP (internal) |
| Destination IP | Public-facing/perimeter assets | Internal private IP assets |
| MITRE ATT&CK phase | **Reconnaissance** | **Discovery** (post-initial access) |
| Attacker foothold | ❌ No foothold yet | ✅ Already inside the network |
| Severity | 🟡 **Low** | 🔴 **High** |
| SOC response | Block offending IP on perimeter firewall | Escalate → Initiate IR → Root cause analysis |
| Limitation | Attacker can return with masked/rotated IP | Blocking source IP alone is insufficient |
| Other names | Initial reconnaissance | Internal reconnaissance / lateral movement prep |

---

## ↔️ Horizontal vs Vertical Scanning

| Attribute | Horizontal Scan | Vertical Scan |
|---|---|---|
| What varies | Destination IP (many) | Destination port (many) |
| What stays fixed | Source IP + Destination port | Source IP + Destination IP |
| Purpose | Find which hosts expose a specific port | Footprint a single host's open services |
| Example | WannaCry scanning all hosts for port 445 (SMBv1) | Scanning a single internet-facing server for all common ports |
| Log signature | Same src IP, same dst port, **different dst IPs** | Same src IP, same dst IP, **different dst ports** |
| Mixed scan | Combination of both to maximize coverage | — |

## 📡 Scan Mechanics

| Scan Type | Protocol | How It Works | Open Port Indicator | Closed Port Indicator | Notes |
|---|---|---|---|---|---|
| **Ping Sweep** | ICMP | Send ICMP echo request; if host is up, it replies | ICMP echo reply received | No reply | Often blocked by modern firewalls |
| **TCP SYN Scan** | TCP | Send SYN; if SYN-ACK received, port is open (never sends ACK to complete) | SYN-ACK response | RST response | Stealthy; blends with normal traffic; Zeek `conn_state = S0` |
| **UDP Scan** | UDP | Send empty UDP packet to port | UDP response (rare) | ICMP port unreachable | Slow/unreliable; timeout = ambiguous; no response ≠ open |

### Zeek conn_state Reference

| conn_state | Meaning | Implication |
|---|---|---|
| `S0` | SYN sent, no response | Classic TCP SYN scan indicator |
| `SF` | Normal established + closed | Legitimate connection |
| `REJ` | Connection rejected (RST) | Port closed |
| `S1`/`S2`/`S3` | Established, not cleanly closed | Partial connection |

## 🛠️ Log Analysis Commands

### Preview CSV log file

**Purpose:** See column headers and first entries of a Zeek-exported CSV.

```bash
head -n2 log-session-1.csv
# Shows header row + first data row
# Note: @timestamp contains commas — account for this when using cut
```

### Filter specific columns with cut

**Purpose:** Extract columns from CSV using comma delimiter.

```bash
cut -d',' -f<column_number> log-session-2.csv
# -d',' sets comma as delimiter
# -f<N> selects column N
# Caution: @timestamp field contains a comma, so column numbers shift by 1 after timestamp
```

### Count log entries

**Purpose:** Count matching rows (e.g., number of entries for an internal scanner).

```bash
cut -d',' -f<src_ip_col> log-session-2.csv | grep "192.168.x.x" | wc -l
# Pipe through grep to filter by IP, then count lines
```

## 🔎 Kibana Discovery Workflow

| Step | Action |
|---|---|
| 1 | Open browser inside VM → navigate to `http://MACHINE_IP:5601` |
| 2 | Login: `elastic` / `changeme` |
| 3 | Hamburger menu (top-left) → **Discover** |
| 4 | Set **Data View** to `All logs` |
| 5 | Click **Search entire time range** to load all logs |
| 6 | Click `+` next to a field in the left column to add it as a column |
| 7 | Click a field value → use **+** (filter for) or **−** (filter out) to narrow results |

### Key Zeek Fields for Scanning Detection

| Field | Purpose |
|---|---|
| `source.ip` | Attacker/scanner source IP |
| `destination.ip` | Target IP |
| `destination.port` | Target port |
| `network.protocol` | tcp / udp / icmp |
| `network.transport` | Transport layer protocol |
| `zeek.conn.conn_state` | Connection state (S0 = SYN scan) |
| `zeek.conn.history` | Connection history flags |
| `event.dataset` | Log source (e.g., `zeek.conn`) |
