# 🕵️ Man-in-the-Middle Detection — Reference Sheet

> **TL;DR:** MITM attacks involve three chained techniques: **ARP Spoofing** (intercept LAN traffic) → **DNS Spoofing** (redirect victim to attacker's server) → **SSL Stripping** (downgrade HTTPS to HTTP to capture credentials in plaintext). Detection uses Wireshark filters targeting gratuitous ARP replies, rogue DNS responses, and unexpected HTTP POST to HTTPS-only domains.

---

## ⚠️ Gotchas

| Gotcha | Detail |
|---|---|
| ARP has no authentication | Any device can send unsolicited `is-at` replies — this is the fundamental vulnerability. |
| Gratuitous ARP ≠ always malicious | Legitimate devices send them at startup. Look for **repeated** gratuitous ARPs for the same IP from a suspicious MAC. |
| Two MACs for same IP = smoking gun | `arp.duplicate-address-detected` is the strongest confirmation of ARP spoofing. |
| DNS spoofing most reliable indicator | Multiple DNS responses for the same query from different sources — one from 8.8.8.8, one from an internal attacker IP. |
| Short DNS TTL (1–30s) = suspicious | Attacker uses low TTL to keep the victim's cache poisoned and under control. |
| SSL stripping is invisible to the victim | The victim sees HTTP, the attacker holds HTTPS to the real server — no warning unless HSTS is enforced. |
| TLS disappearing after DNS spoof = confirmation | After DNS redirect, victim stops doing TLS handshakes to the real server — connection switches to plain HTTP. |
| `ip.src != 8.8.8.8` DNS responses are suspicious | Any internal IP responding to DNS queries is a red flag unless it's your own DNS server. |
| Credentials visible in HTTP POST | After SSL stripping, `username=` and `password=` appear in plaintext in the HTTP stream. |
| MITM maps to Kill Chain Exploitation + Installation phases | Interception = Exploitation; payload injection via the MITM position = Installation. |

## 🗺️ MITM Attack Overview

### Two Core Steps

| Step | Description |
|---|---|
| **Interception** | Attacker inserts themselves into a communication stream (ARP/DNS/IP spoofing) |
| **Manipulation/Decryption** | Attacker decrypts, alters, or captures data; injects malicious content or fake login forms |

### Common MITM Types

| Type | Description |
|---|---|
| Packet sniffing | Capturing unencrypted packets on open/compromised network |
| Session hijacking | Stealing session tokens to impersonate users |
| SSL stripping | Downgrading HTTPS → HTTP to steal/alter data |
| DNS spoofing | Injecting fake DNS responses to redirect to attacker-controlled server |
| IP spoofing | Crafting packets that appear from trusted systems |
| Rogue Wi-Fi AP | Creating fake networks to intercept user traffic |

### MITM in the Cyber Kill Chain

| Kill Chain Phase | MITM Role |
|---|---|
| **Exploitation** | Exploits ARP/DNS trust weaknesses to intercept communication (initial foothold for eavesdropping) |
| **Installation** | MITM position used to inject malware, browser exploits, or RATs into unencrypted downloads |

## 🔴 Task 4 — ARP Spoofing Detection

### How ARP Spoofing Works

```
Normal: Victim → [ARP: Who has 192.168.10.1?] → Gateway replies with its MAC
Attack: Attacker sends unsolicited "192.168.10.1 is at <attacker MAC>" to victim
Result: Victim's ARP cache poisoned → all traffic flows through attacker
```

### Indicators of ARP Spoofing

| Indicator | Detail |
|---|---|
| Duplicate MAC-to-IP mappings | Multiple MACs claiming the same IP |
| Unsolicited ARP replies | `is-at` replies with no matching `who-has` request |
| Abnormal ARP volume | Large number of ARP packets in short intervals |
| Unusual traffic routing | Traffic rerouted through attacker's MAC |
| Gateway redirection | Multiple destination MACs for the same gateway IP |
| Gratuitous ARP flood | Repeated unsolicited broadcasts for the same IP |

### Wireshark Filters — ARP Spoofing

wireshark
#### Show all ARP traffic
arp

#### ARP requests only
arp.opcode == 1

#### ARP replies only (look for gratuitous/unsolicited ones)
arp.opcode == 2

#### Filter gratuitous ARP packets specifically
arp.isgratuitous

#### Show ARP traffic from the legitimate gateway MAC
arp && arp.src.proto_ipv4 == 192.168.10.1 && eth.src == 02:aa:bb:cc:00:01

#### Show all ARP replies claiming to be the gateway IP
arp.opcode == 2 && arp.src.proto_ipv4 == 192.168.10.1

#### Confirm: look for multiple MACs claiming gateway IP
arp.opcode ==2 && _ws.col.info contains "192.168.10.1 is at"

#### Confirm attacker's MAC claiming gateway IP
arp.opcode == 2 && arp.src.proto_ipv4 == 192.168.10.1 && eth.src == 02:fe:fe:fe:55:55

#### Strongest confirmation: duplicate IP-to-MAC detection
arp.duplicate-address-detected || arp.duplicate-address-frame
```

| Item | Value |
|---|---|
| Gateway IP | `192.168.10.1` |

| Attacker MAC | `02:fe:fe:fe:55:55` |

## 🌐 Task 5 — DNS Spoofing Detection

### How DNS Spoofing Works

```
1. Victim queries DNS: "What is corp-login.acme-corp.local?"
2. Attacker (already MITM via ARP) intercepts the query
3. Attacker sends forged DNS reply: "corp-login.acme-corp.local → 192.168.10.55 (attacker's IP)"
4. Victim's DNS cache is poisoned → victim connects to attacker's fake server
```

### Indicators of DNS Spoofing

| Indicator | Detail |
|---|---|
| Multiple DNS responses for same query | Legitimate + forged response — **most reliable indicator** |
| DNS response from unexpected source | Reply from IP that is NOT the configured resolver (e.g. not 8.8.8.8) |
| Short TTL (1–30s) | Attacker uses low TTL to maintain cache control |
| Unsolicited DNS responses | DNS reply with no corresponding request |

### Wireshark Filters — DNS Spoofing

```wireshark
# Show all DNS traffic
dns

# Show only legitimate DNS responses from 8.8.8.8
dns.flags.response == 1 && ip.src == 8.8.8.8

# Show all DNS responses
dns.flags.response == 1

# Show all DNS traffic for the domain of interest
dns && dns.qry.name == "corp-login.acme-corp.local"

# Show legitimate DNS responses for the domain
dns.flags.response == 1 && ip.src == 8.8.8.8 && dns.qry.name == "corp-login.acme-corp.local"

# KEY: Show DNS responses NOT from 8.8.8.8 — reveals rogue DNS server
dns.flags.response == 1 && ip.src != 8.8.8.8 && dns.qry.name == "corp-login.acme-corp.local"
```

### DNS Spoofing Investigation Summary

| Item | Value |
|---|---|
| Target domain | `corp-login.acme-corp.local` |
| Legitimate DNS server | `8.8.8.8` |
| Total DNS responses for domain | **211** |
| DNS responses from non-8.8.8.8 IPs | **2** |
| Attacker's forged DNS response IP | **192.168.10.55** |

## 🔒 Task 6 — SSL Stripping Detection

### How SSL Stripping Works

```
1. Victim tries to access HTTPS site
2. Attacker (MITM position via ARP + DNS spoof) intercepts
3. Attacker connects to real server over HTTPS
4. Attacker relays response to victim over HTTP (stripped)
5. Victim unknowingly submits credentials over plaintext HTTP
```

### Indicators of SSL Stripping

| Indicator | Detail |
|---|---|
| HTTPS → HTTP shift for same domain | Initial request port 443, then port 80 for the same host |
| HTTP redirects 301/302 for HTTPS resources | Persistent redirects from HTTPS to HTTP |
| TLS handshakes disappear after DNS spoof | No more Client Hello to legitimate server after victim is redirected |
| Plaintext credentials in HTTP POST | `username=` and `password=` visible in HTTP stream |
| Self-signed certificate errors | If attacker uses direct proxying — TLS handshake fails |

### Wireshark Filters — SSL Stripping

```wireshark
# Show all TLS/SSL traffic
tls || ssl

# Confirm site normally uses TLS (Client Hello to domain)
tls.handshake.type == 1 && tls.handshake.extensions_server_name == "corp-login.acme-corp.local"

# Show DNS redirect that precedes stripping (attacker's spoofed DNS response)
dns.flags.response == 1 && ip.src == 192.168.10.55 && dns.qry.name == "corp-login.acme-corp.local"

# KEY: Show victim connecting to attacker over HTTP (TLS stripped)
http && ip.src == 192.168.10.10 && ip.dst == 192.168.10.55

# Follow HTTP Stream to see plaintext credentials
Right-click packet → Follow → HTTP Stream
```

### SSL Stripping Investigation Summary

| Item | Value |
|---|---|
| Attacker IP | `192.168.10.55` |
| Victim IP | `192.168.10.10` |
| HTTP POST requests to domain | **1** |

## ⛓️ Full Attack Chain Summary

```
Phase 1: ARP Spoofing
  Attacker MAC 02:fe:fe:fe:55:55 sends gratuitous ARP
  → Claims: "192.168.10.1 (gateway) is at 02:fe:fe:fe:55:55"
  → Victim's ARP cache poisoned
  → All victim traffic now flows through attacker

Phase 2: DNS Spoofing
  Victim queries DNS for corp-login.acme-corp.local
  → Attacker intercepts query (MITM position established)
  → Attacker sends forged DNS reply: domain → 192.168.10.55
  → Victim's DNS cache poisoned — connects to attacker's server

Phase 3: SSL Stripping
  Victim connects to 192.168.10.55 expecting HTTPS
  → Attacker relays over HTTP only (strips TLS)
  → Victim submits credentials over plain HTTP
  → Attacker captures: username=alice, password=Secret123!
```

## 🔧 Filter Quick Reference — All Phases

| Protocol | Filter | Purpose |
|---|---|---|
| ARP | `arp` | All ARP traffic |
| ARP | `arp.opcode == 1` | ARP requests |
| ARP | `arp.opcode == 2` | ARP replies |
| ARP | `arp.isgratuitous` | Gratuitous ARP only |
| ARP | `arp.opcode == 2 && arp.src.proto_ipv4 == 192.168.10.1` | Replies claiming gateway IP |
| ARP | `arp.duplicate-address-detected \|\| arp.duplicate-address-frame` | Duplicate IP-MAC confirmed |
| DNS | `dns` | All DNS |
| DNS | `dns.flags.response == 1 && ip.src == 8.8.8.8` | Legitimate DNS responses |
| DNS | `dns.flags.response == 1 && ip.src != 8.8.8.8 && dns.qry.name == "domain"` | Rogue DNS responses |
| TLS | `tls \|\| ssl` | All TLS/SSL traffic |
| TLS | `tls.handshake.type == 1 && tls.handshake.extensions_server_name == "domain"` | TLS Client Hello to domain |
| HTTP | `http && ip.src == <victim> && ip.dst == <attacker>` | Victim → attacker over HTTP (SSL stripped) |
