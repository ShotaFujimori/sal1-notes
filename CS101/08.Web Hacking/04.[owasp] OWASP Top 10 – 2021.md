# SAL1 Note: Web Hacking — OWASP Top 10 (2021)

## Overview

The OWASP Top 10 (2021) highlights the ten most critical web application security risks. This module breaks each topic down, shows how the vulnerabilities occur, and lets you practice them hands-on. The ten categories are: Broken Access Control, Cryptographic Failures, Injection, Insecure Design, Security Misconfiguration, Vulnerable & Outdated Components, Identification & Authentication Failures, Software & Data Integrity Failures, Security Logging & Monitoring Failures, and Server-Side Request Forgery (SSRF). 

---

## 1) Broken Access Control

**What it is:** Users can access data or functions they shouldn’t (authorization bypass). 
**Impact/examples:** Viewing other users’ data; invoking admin-only actions; real-world example included in the room (private YouTube frames exposure). 
**Common variant:** **IDOR (Insecure Direct Object Reference)** — server exposes object identifiers (e.g., `?id=111111`), and the app fails to verify ownership; changing the ID reveals others’ data. 
**Defence:** Enforce server-side authorization checks on every request for objects/actions.

---

## 2) Cryptographic Failures

**What it is:** Misuse (or lack) of cryptography to protect sensitive information (data **in transit** and **at rest**). 
**Impact:** Leakage of personal data, credentials, or even plaintext secrets stored server-side. 
**Defence:** Use modern, vetted algorithms; enforce TLS for transport; encrypt sensitive data at rest; manage keys securely.

---

## 3) Injection

**What it is:** Untrusted input is interpreted as a command or query. Includes SQL Injection and Command Injection. 
**Typical prevention:** Allow-list validation, safe APIs/parameterization, and stripping/blocking dangerous characters (prefer libraries). 
**Command Injection example:** Server calls OS utilities using user input (e.g., `passthru(...)`), enabling arbitrary command execution on the host.  

---

## 4) Insecure Design

**What it is:** Flaws due to missing or ineffective security design patterns/controls.
**Defence:** Threat modeling, secure design reviews, and defense-in-depth across the SDLC.

## 5) Security Misconfiguration

**What it is:** Insecure defaults, verbose errors, open admin panels, missing hardening.
**Defence:** Harden baselines, minimal services, fail-secure configs, and automated configuration management.
*(Category included in room’s structure.)* 

---

## 6) Vulnerable & Outdated Components

**What it is:** Using components with known vulnerabilities (frameworks, libraries, servers).
**Approach:** Inventory components, track CVEs, patch/upgrade quickly; verify exploitability against target versions.
*(Room’s lab explores exploiting a known vulnerable app.)* 

---

## 7) Identification & Authentication Failures

**What it is:** Weak login/session controls (weak passwords, brute-forceable forms, predictable session cookies). 
**Defence:** Strong password policy & lockout; MFA; secure, unpredictable session management. 

---

## 8) Software & Data Integrity Failures

**What it is:** Untrusted software updates, CI/CD pipelines, or deserialization issues leading to integrity compromise.
**Defence:** Sign/verify code and data; restrict update sources; secure build chains.
*(Category present in room outline and scenarios.)* 

---

## 9) Security Logging & Monitoring Failures

**Why it matters:** Without quality logs/monitoring, breaches go undetected, regulatory risk rises, and attackers persist longer. 
**Log essentials:** Status codes, timestamps, usernames, endpoints, IPs. Store securely with redundancy. 
**Detect suspicious activity:** Excess auth attempts, anomalous IPs, obvious tool user-agents, and common payloads — plus impact-based alerting. 

---

## 10) Server-Side Request Forgery (SSRF)

**What it is:** Coercing the server to make requests controlled by the attacker, often leaking secrets (e.g., API keys) or reaching internal services.  
**Abuse paths:** Pivot to attacker-controlled host to capture tokens/keys; enumerate internal networks; sometimes reach non-HTTP services/RCE.  
**Hands-on example:** Modify a “server” parameter to redirect backend requests, then intercept API keys (exercise outcome shown in the room).

## Key Terms & Concepts (from this chapter)

* **Authorization vs. Authentication** (what you can do vs. who you are).
* **Broken Access Control / IDOR** (direct object references without ownership checks). 
* **Cryptographic Failures** (weak/missing encryption; data in transit/at rest). 
* **Injection** (SQLi, Command Injection; untrusted input executed as queries/commands). 
* **Allow-list / Input Validation / Parameterization** as injection mitigations. 
* **Security Misconfiguration** (unsafe defaults/exposure). 
* **Vulnerable & Outdated Components** (track and patch). 
* **Identification & Authentication Failures** (weak creds, brute forcing, weak sessions; use MFA/lockouts). 
* **Software & Data Integrity Failures** (trust boundaries, signed updates/artefacts). 
* **Security Logging & Monitoring** (log essentials + alerting on suspicious patterns).  
* **SSRF** (server makes attacker-controlled requests; can leak keys or hit internal services).  

---

## Quick Study Tips

* For **Broken Access Control/IDOR**, think: “Does the server actually check ownership?”
* For **Injection**, default to “parameterize & validate,” not “sanitize later.”
* For **Logging/Monitoring**, decide **what** to log and **how** to alert **before** incidents.
* For **SSRF**, search for any user-controlled URL/host parameters and consider internal pivots.
