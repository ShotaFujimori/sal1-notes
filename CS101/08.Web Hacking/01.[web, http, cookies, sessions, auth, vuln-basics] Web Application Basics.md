# SAL1/Web Hacking — Web Application Basics
tags: [web, http, cookies, sessions, auth, vuln-basics]

## TL;DR
- The web is **HTTP over TCP**: clients send **requests**, servers return **responses**.
- Core moving parts: **URLs**, **methods (GET/POST/PUT/DELETE)**, **status codes**, **headers**, **cookies + sessions**, **auth**.
- Typical first checks: **input handling**, **auth/authorization**, **session management**, **error handling**, **file upload/download paths**.

---

## 1) Web Architecture in One Picture
Client (browser/curl/Burp) → **HTTP request** → Web server / App (routes, controllers, templates) → DB/Cache/External APIs → **HTTP response** → Client.

---

## 2) HTTP Essentials

### 2.1 Request line + headers
```

GET /login HTTP/1.1
Host: example.com
User-Agent: ...
Cookie: session=abcd...

````

### 2.2 Methods (what they usually mean)
| Method | Typical Use | Body? | Idempotent | Notes |
|---|---|---|---|---|
| GET | Read a resource | No | Yes | Should not change server state |
| POST | Create / submit | Yes | No | Form submits, logins, file uploads |
| PUT | Replace a resource | Yes | Yes | Full update by URL |
| PATCH | Partial update | Yes | No | Update specific fields |
| DELETE | Remove a resource | Usually no | Yes | Resource deletion |
| OPTIONS | Capability discovery | No | Yes | CORS preflight, methods allowed |

### 2.3 Status codes (quick map)
| Class | Examples | Meaning |
|---|---|---|
| 2xx | 200, 201 | Success/created |
| 3xx | 301, 302 | Redirect |
| 4xx | 400, 401, 403, 404 | Client errors (bad input / auth / not found) |
| 5xx | 500, 502, 503 | Server errors (bugs, upstream) |

## 3) Cookies & Sessions

- **Cookie**: small key/value stored by the browser and sent on matching requests.  
- **Session**: server-side state keyed by a cookie (e.g., `sessionid=...`).

Hardening checklist:
- Mark cookies **HttpOnly**, **Secure** (HTTPS only), **SameSite=Lax/Strict**.
- Rotate session IDs after login; invalidate on logout.
- Avoid sensitive data **inside** the cookie payload unless signed & encrypted.

---

## 4) Authentication vs Authorization

| Concept | Question | Examples | Pitfalls |
|---|---|---|---|
| Authentication | “Who are you?” | Passwords, MFA, OAuth, SSO | Weak password policy, no MFA |
| Authorization | “What are you allowed to do?” | RBAC, ABAC | **IDOR** (insecure direct object reference), missing checks on every action |

**IDOR quick test**: change object IDs in URLs/JSON and confirm access is enforced server-side.

---

## 5) Input Handling & Output Encoding

- **Never trust input** (query, body, headers, cookies, files, JSON).
- Two defenses working together:
  1) **Validation** (type, length, whitelist, server-side).
  2) **Encoding/escaping** at sink (HTML, JS, SQL, OS, file path).

Common sinks & mitigations:
| Sink | Risk | Primary Mitigation |
|---|---|---|
| HTML | Reflected/Stored **XSS** | HTML-escape; CSP; avoid `innerHTML` |
| SQL | **SQLi** | Parameterized queries (prepared statements) |
| Shell | **Command injection** | Avoid shell; if unavoidable, strict whitelists |
| File path | **Traversal (../)** | Normalize + whitelist base dir; never concat user input |

---

## 6) Very Common Web Vulns (primer)

| Vuln | What to look for | Quick probe (safe) | Fix (high level) |
|---|---|---|---|
| XSS (Reflected/Stored/DOM) | Unescaped user input in page | `<script>alert(1)</script>` or harmless `<img src=x onerror=alert(1)>` in test env | Encode output, CSP, input constraints |
| SQL Injection | Errors/time-based differences | `' or 1=1--`, boolean/time tests in lab | Parameterized queries, least DB perms |
| CSRF | State-changing POSTs without token | Replay POST from another origin | CSRF token, SameSite cookies |
| File Upload Issues | Executable uploads, path trust | Upload then request file; check type | Content-type & extension allow-list, store outside webroot, AV scan |
| Auth/Session flaws | Weak flows, predictable tokens | Bruteforce rate limits? session rotation? | MFA, lockouts, secure cookies, rotation |
| IDOR/Broken Access Control | Direct resource IDs | Change `user_id=123` to another | Server-side permission checks everywhere |
| SSRF (server requests) | URL fetchers | Point to internal IPs/metadata | Allow-list hosts, block 169.254.169.254 |

## 7) CORS (Cross-Origin Resource Sharing)
- Controls which **origins** can read responses in browsers.
- Server sets: `Access-Control-Allow-Origin`, `-Methods`, `-Headers`, etc.
- **Misconfig** (`*` with credentials, or reflecting arbitrary origins) can expose APIs to malicious sites.

## 8) Recon & Handy Commands

### curl
```bash
# See response headers and body
curl -i https://target/app

# Send data as application/x-www-form-urlencoded
curl -i -X POST https://target/login -d 'user=a&pass=b'

# JSON with custom headers
curl -i -X POST https://target/api -H 'Content-Type: application/json' -d '{"a":1}'
````

### Basic wordlists (lab)

```bash
# Dir/file discovery (only in authorized labs)
ffuf -w wordlist.txt -u https://target/FUZZ -mc 200,204,301,302

## 9) Mini Checklist (first pass)

* [ ] Map **attack surface**: hosts, ports, paths, parameters, roles.
* [ ] Test **auth** (login, reset, MFA), **authorization** (every action).
* [ ] Review **session** flags and rotation.
* [ ] Exercise **inputs** (type/length), test **error handling**.
* [ ] Try baseline **XSS/SQLi/Traversal/CSRF** probes in a lab.
* [ ] Check **CORS** and **headers** (CSP, HSTS, X-Frame-Options).

---

## 10) Key Terms (glossary)

* **HTTP method**: action verb (GET/POST/PUT/DELETE).
* **Status code**: 3-digit result class (2xx success, 4xx client error, 5xx server error).
* **Header**: metadata in request/response (e.g., `Cookie`, `Authorization`, `Content-Type`).
* **Cookie**: browser-stored key/value automatically sent to origin.
* **Session**: server-side state keyed by a cookie.
* **CSRF**: cross-site request forgery — tricking a logged-in user’s browser to perform unwanted actions.
* **XSS**: cross-site scripting — injecting executable script into a page.
* **SQLi**: manipulating SQL via untrusted input.
* **IDOR**: insecure direct object reference — accessing others’ resources by changing identifiers.
* **CORS**: browser policy controlling cross-origin reads.
* **CSP**: Content Security Policy — header to restrict script sources.
* **SSRF**: server-side request forgery — abusing server-initiated HTTP requests.

---

## 11) Safe Practice Flow (labs)

1. Start with **passive recon** (robots.txt, headers, error pages).
2. Map routes/params; try **non-destructive** input tests.
3. Use a proxy (Burp/ZAP) to replay/modify requests.
4. Escalate to specific vuln testing only in **authorized** environments.
5. Document reproducible steps + impact + fix.
