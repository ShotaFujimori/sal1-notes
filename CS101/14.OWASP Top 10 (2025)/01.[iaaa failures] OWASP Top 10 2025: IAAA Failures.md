# 47.SAL1 — OWASP Top 10 (2025): IAAA Failures — Cheat Sheet

[cite\_start]**Focus:** A01 Broken Access Control, A07 Authentication Failures, A09 Logging & Alerting Failures — all framed by the IAAA model[cite: 8, 9, 10].

## TL;DR

  * [cite\_start]**IAAA Chain:** Identity → Authentication → Authorisation → Accountability[cite: 16, 17, 18, 19]. [cite\_start]You cannot skip a level; if one fails, the later steps cannot be performed[cite: 15].
  * [cite\_start]**A01 (Broken Access Control):** Enforce server-side checks on every request[cite: 163]. [cite\_start]Watch for IDORs (horizontal/vertical escalation)[cite: 29, 31].
  * [cite\_start]**A07 (Auth Failures):** Verify unique identity binding (prevent `admin` vs `aDmiN`)[cite: 60]. [cite\_start]Rate-limit brute force and secure sessions[cite: 163].
  * [cite\_start]**A09 (Logging Failures):** Log the full auth lifecycle, centralize off-host, and alert on anomalies like brute-force bursts[cite: 165].
  * [cite\_start]**Hands-on:** The room demonstrates these via `bank.thm`, showing how easily simple logic flaws allow account takeovers[cite: 33, 60].

## Mental Model — IAAA

  * [cite\_start]**Identity:** Unique account representation (e.g., user ID/email)[cite: 16].
  * [cite\_start]**Authentication:** Proving that identity (passwords, OTP, passkeys)[cite: 17].
  * [cite\_start]**Authorisation:** What that identity is allowed to do[cite: 18].
  * [cite\_start]**Accountability:** Recording and alerting on who did what, when, and from where[cite: 19].

[cite\_start]*(Maps to: A07 affects Authentication, A01 affects Authorisation, A09 affects Accountability)[cite: 20].*

## A01 — Broken Access Control (incl. IDOR)

**What to look for**

  * [cite\_start]URLs with exposed object IDs (e.g., `?id=7`)[cite: 29]. [cite\_start]Changing this allows access to other users' data (IDOR)[cite: 29].
  * [cite\_start]Horizontal escalation (accessing same-level user data) vs. Vertical escalation (jumping to admin)[cite: 31].

**Quick tests (aligned to lab)**

```bash
# 1) Manual IDOR probe (Horizontal Escalation)
# The room uses 'id' parameter to retrieve account info.
curl -i "https://bank.thm/accounts?id=7"
curl -i "https://bank.thm/accounts?id=6" 

# 2) Fuzzing for IDORs (finding the "Millionaire")
# Loop through IDs to find anomalies in response length or content.
for i in {1..10}; do
  curl -s "https://bank.thm/accounts?id=$i" | grep "Balance" -A 1
done
```

**Fix it**

  * [cite\_start]Enforce server-side checks on *every* request[cite: 163].
  * [cite\_start]Do not trust client-side input for access decisions[cite: 31].

**From the room’s demo**

  * [cite\_start]**Scenario:** Changing `id=7` revealed another user with \>$1M balance[cite: 29, 33].
  * [cite\_start]**Flag:** `THM{Found.the.Millionare!}`[cite: 41].

## A07 — Authentication Failures

**What to look for**

  * [cite\_start]**Logic Flaws:** Registration flows that don't normalize inputs (e.g., `aDmiN` vs `admin`)[cite: 60].
  * [cite\_start]**Weaknesses:** Username enumeration, weak passwords, missing lockouts/rate-limits[cite: 54, 55].

**Quick tests (aligned to lab)**

```bash
# 1) Registration Logic Flaw (Case Sensitivity)
# Attempt to register a username that mimics admin but with different casing.
curl -X POST https://bank.thm/register -d "user=aDmiN&pass=password123"

# 2) Login with the spoofed account
# If the backend normalizes case *after* registration but *before* checks, 
# you might log in as the target 'admin'.
curl -X POST https://bank.thm/login -d "user=aDmiN&pass=password123"
```

**Fix it**

  * [cite\_start]**Canonicalize** usernames (e.g., force lowercase) and enforce unique indexes[cite: 163].
  * [cite\_start]Implement rate-limiting and lockouts for brute-force attempts[cite: 163].

**From the room’s demo**

  * [cite\_start]**Scenario:** Registered `aDmiN` to bypass checks and log in as the real `admin`[cite: 60].
  * [cite\_start]**Flag:** `THM{Account.confusion.FTW!}`[cite: 69].

## A09 — Logging & Alerting Failures (Accountability)

**What to look for**

  * [cite\_start]Missing logs for authentication events (success/fail) or privilege changes[cite: 85].
  * [cite\_start]Vague error messages that don't help investigation[cite: 85].
  * [cite\_start]Logs stored locally where attackers can tamper with them[cite: 85].

**Quick checks (Log Analysis)**

```bash
# 1) Detect Brute Force Patterns
# Look for high volume of 401 Unauthorized responses from a single IP.
grep "401" access.log | awk '{print $3}' | sort | uniq -c | sort -nr

# 2) Correlate with Success
# Did that same IP eventually get a 200 OK?
grep "203.0.113.45" access.log | grep "200"
```

**Fix it**

  * [cite\_start]Log the full auth lifecycle: failures, successes, and high-value actions (like accessing `supersecret` endpoints)[cite: 165].
  * [cite\_start]Centralize logs off-host to prevent tampering[cite: 165].

**From the room’s demo**

  * [cite\_start]**Attacker IP:** `203.0.113.45` performing brute force[cite: 92].
  * [cite\_start]**Compromised Account:** `admin`[cite: 113].
  * [cite\_start]**Target Endpoint:** `/supersecretadminstuff` (accessed successfully)[cite: 134].

## Field Checklist

  * [cite\_start][ ] **Map IAAA:** Define where Identity, Auth, AuthZ, and Accountability live in the app[cite: 13, 161].
  * [cite\_start][ ] **Test IDOR:** Tamper with all ID parameters (`?id=`, `user_id=`) to check for horizontal escalation[cite: 29].
  * [cite\_start][ ] **Test Auth Logic:** Try registering duplicate users with case variations (`User` vs `user`)[cite: 60].
  * [cite\_start][ ] **Verify Logs:** Ensure failed logins and admin actions generate clear, tamper-proof alerts[cite: 165].

## Gotchas

  * **Case Sensitivity:** "aDmiN" is not "admin" in bytes, but might be "admin" in your database logic. [cite\_start]This discrepancy causes account takeovers[cite: 60].
  * **Silent Failures:** If an app returns `404` for everything, you might miss an IDOR. [cite\_start]Always check if the server *actually* validated your session[cite: 85].

## Example Playbook (Safe & Fast)

```bash
# 1) Quick IDOR check on numerical parameters
for id in {1..5}; do curl -s "https://bank.thm/accounts?id=$id" | head -n 5; done

# 2) Check for user enumeration via registration
curl -d "user=admin&pass=123" -X POST https://bank.thm/register
# Response: "User already exists" -> Enum possible.

# 3) Log Audit (if white-box)
# checking if the brute-force attempt from 203.0.113.45 was flagged
cat /var/log/app.log | grep "SUSPICIOUS ACTIVITY"
```
