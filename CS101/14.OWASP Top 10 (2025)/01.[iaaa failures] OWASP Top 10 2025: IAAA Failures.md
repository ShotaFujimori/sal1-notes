# 47.SAL1 — OWASP Top 10 (2025): IAAA Failures — Cheat Sheet

**Focus:** A01 Broken Access Control, A07 Authentication Failures, A09 Logging & Alerting Failures — all framed by the IAAA model.

## TL;DR

**IAAA Chain:** Identity → Authentication → Authorisation → Accountability. You cannot skip a level; if one fails, the later steps cannot be performed.

  * **A01 (Broken Access Control):** Enforce server-side checks on every request. Watch for IDORs (horizontal/vertical escalation).
  * **A07 (Auth Failures):** Verify unique identity binding (prevent `admin` vs `aDmiN`). Rate-limit brute force and secure sessions.
  * **A09 (Logging Failures):** Log the full auth lifecycle, centralize off-host, and alert on anomalies like brute-force bursts.
  * **Hands-on:** The room demonstrates these via `bank.thm`, showing how easily simple logic flaws allow account takeovers.

## Mental Model — IAAA

  * **Identity:** Unique account representation (e.g., user ID/email).
  * **Authentication:** Proving that identity (passwords, OTP, passkeys).
  * **Authorisation:** What that identity is allowed to do.
  * **Accountability:** Recording and alerting on who did what, when, and from where.

*(Maps to: A07 affects Authentication, A01 affects Authorisation, A09 affects Accountability)*.

## A01 — Broken Access Control (incl. IDOR)

**What to look for**

  * URLs with exposed object IDs (e.g., `?id=7`). Changing this allows access to other users' data (IDOR).
  * Horizontal escalation (accessing same-level user data) vs. Vertical escalation (jumping to admin).

**Quick tests (aligned to lab)**

```bash
# 1) Manual IDOR probe (Horizontal Escalation)
# The room uses 'id' parameter to retrieve account info.
curl -i "https://bank.thm/accounts?id=7"
curl -i "https://bank.thm/accounts?id=6" 

# 2) Fuzzing for IDORs (finding the "Millionaire")
# Loop through IDs to find anomalies in response length or content.
for i in {1..10}; do
  curl -s "https://bank.thm/accounts?id=$i" | grep "Balance" -A 1
done
```

**Fix it**

  * Enforce server-side checks on *every* request.
  * Do not trust client-side input for access decisions.

**From the room’s demo**

  * **Scenario:** Changing `id=7` revealed another user with \>$1M balance.
  * **Flag:** `THM{Found.the.Millionare!}`.

## A07 — Authentication Failures

**What to look for**

  * **Logic Flaws:** Registration flows that don't normalize inputs (e.g., `aDmiN` vs `admin`).
  * **Weaknesses:** Username enumeration, weak passwords, missing lockouts/rate-limits.

**Quick tests (aligned to lab)**

```bash
# 1) Registration Logic Flaw (Case Sensitivity)
# Attempt to register a username that mimics admin but with different casing.
curl -X POST https://bank.thm/register -d "user=aDmiN&pass=password123"

# 2) Login with the spoofed account
# If the backend normalizes case *after* registration but *before* checks, 
# you might log in as the target 'admin'.
curl -X POST https://bank.thm/login -d "user=aDmiN&pass=password123"
```

**Fix it**

  * **Canonicalize** usernames (e.g., force lowercase) and enforce unique indexes.
  * Implement rate-limiting and lockouts for brute-force attempts.

**From the room’s demo**

  * **Scenario:** Registered `aDmiN` to bypass checks and log in as the real `admin`.
  * **Flag:** `THM{Account.confusion.FTW!}`.

## A09 — Logging & Alerting Failures (Accountability)

**What to look for**

  * Missing logs for authentication events (success/fail) or privilege changes.
  * Vague error messages that don't help investigation.
  * Logs stored locally where attackers can tamper with them.

**Quick checks (Log Analysis)**

```bash
# 1) Detect Brute Force Patterns
# Look for high volume of 401 Unauthorized responses from a single IP.
grep "401" access.log | awk '{print $3}' | sort | uniq -c | sort -nr

# 2) Correlate with Success
# Did that same IP eventually get a 200 OK?
grep "203.0.113.45" access.log | grep "200"
```

**Fix it**

  * Log the full auth lifecycle: failures, successes, and high-value actions (like accessing `supersecret` endpoints).
  * Centralize logs off-host to prevent tampering.

**From the room’s demo**

  * **Attacker IP:** `203.0.113.45` performing brute force.
  * **Compromised Account:** `admin`.
  * **Target Endpoint:** `/supersecretadminstuff` (accessed successfully).

## Field Checklist

  * [ ] **Map IAAA:** Define where Identity, Auth, AuthZ, and Accountability live in the app.
  * [ ] **Test IDOR:** Tamper with all ID parameters (`?id=`, `user_id=`) to check for horizontal escalation.
  * [ ] **Test Auth Logic:** Try registering duplicate users with case variations (`User` vs `user`).
  * [ ] **Verify Logs:** Ensure failed logins and admin actions generate clear, tamper-proof alerts.

## Gotchas

  * **Case Sensitivity:** "aDmiN" is not "admin" in bytes, but might be "admin" in your database logic. This discrepancy causes account takeovers.
  * **Silent Failures:** If an app returns `404` for everything, you might miss an IDOR. Always check if the server *actually* validated your session.

## Example Playbook (Safe & Fast)

```bash
# 1) Quick IDOR check on numerical parameters
for id in {1..5}; do curl -s "https://bank.thm/accounts?id=$id" | head -n 5; done

# 2) Check for user enumeration via registration
curl -d "user=admin&pass=123" -X POST https://bank.thm/register
# Response: "User already exists" -> Enum possible.

# 3) Log Audit (if white-box)
# checking if the brute-force attempt from 203.0.113.45 was flagged
cat /var/log/app.log | grep "SUSPICIOUS ACTIVITY"
```
