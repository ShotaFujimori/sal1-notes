# Security Principles — Cheat Sheet (Exec-ready)

*Source: “Build Your Cyber Security Career – Security Principles.”* 

---

## TL;DR

* Think in **CIA** (Confidentiality, Integrity, Availability) and defend against **DAD** (Disclosure, Alteration, Destruction/Denial).
* Use the right **model** for the goal: **Bell-LaPadula** (confidentiality), **Biba**/**Clark-Wilson** (integrity).
* Apply **defence-in-depth**, **least privilege**, **attack-surface minimization**, and **centralized controls/validation**.
* Prefer **Zero Trust** (“never trust, always verify”) but keep business impact in mind.
* Separate **vulnerability, threat, risk** and treat risk as *likelihood × impact*. 

---

## Core concepts (with practical hooks)

### CIA vs DAD

* **Confidentiality** → only intended parties access data.

  * ex: encrypt at rest/in transit.
* **Integrity** → detect/prevent unauthorized change.

  * ex: hashes, signatures, immutability.
* **Availability** → service works when needed.

  * ex: redundancy, failover, DR.
* **DAD** is the opposite attack lens: **Disclosure / Alteration / Destruction(Denial)**.

  * Use CIA controls to mitigate DAD. 

**Quick commands**

```bash
# Confidentiality: encrypt a file (Linux, OpenSSL)
openssl enc -aes-256-gcm -salt -in report.pdf -out report.pdf.enc

# Integrity: create/verify SHA256
sha256sum artifact.bin > artifact.bin.sha256
sha256sum -c artifact.bin.sha256

# Availability: quick HA test (ping & HTTP)
ping -c3 10.0.0.10 && curl -sS -I https://svc.example.com | head -n1
```

### Beyond CIA: Authenticity & Non-repudiation

* **Authenticity** = prove source is genuine; **Non-repudiation** = sender cannot deny action.

  * ex: signed orders, code signing, MFA approval logs. 

```bash
# Sign and verify a document (GPG)
gpg --detach-sign order.json
gpg --verify order.json.sig order.json
```

### Parkerian Hexad

Adds **Utility** (usable form of data) and **Possession** (physical/logical control) to CIA+Authenticity.

* Example: encrypted drive with lost key ⇒ utility lost though data “exists.” Ransomware ⇒ possession lost.

## Security models (choose per objective)

* **Bell-LaPadula (BLP)** — confidentiality: *no read up*, *no write down* (“write up, read down”).
* **Biba** — integrity: *no read down*, *no write up* (“read up, write down”).
* **Clark-Wilson** — integrity via **CDI**, **UDI**, **TP** (transformation), **IVP** (verification).
  Pick BLP for classified data sharing; Biba/Clark-Wilson for financial/health record correctness.

## Defence-in-Depth

Layer multiple controls (physical → network → host → app → data). The *diagram on page 12* shows layered locks/cameras analogy.
Tactic: assume one layer fails; others slow/stop the attacker. 

```bash
# Host firewall baseline (Linux)
ufw default deny incoming
ufw allow 22/tcp comment 'SSH from bastion only'
ufw allow from 10.0.10.0/24 to any port 443 proto tcp
ufw enable
```

## ISO/IEC 19249 — Architectural & Design Principles

**Architectural (5):** Domain Separation, Layering, Encapsulation, Redundancy, Virtualization.
**Design (5):** Least Privilege, Attack-Surface Minimization, Centralized Parameter Validation, Centralized Security Services, Prepare for Errors/Exceptions.
(See pages 12–14; the *tables & examples* walk through OSI layers, RAID, and API encapsulation.) 

**Operational snippets**

```bash
# Least privilege (Linux): make a report read-only for a group
chown analyst:reporting report.csv
chmod 640 report.csv

# Attack-surface minimization
systemctl disable --now telnet.socket
ss -tulpen   # verify open listeners

# Centralized validation example (Nginx + OWASP CRS via ModSecurity container)
docker run -d -p 80:80 --name waf owasp/modsecurity-crs
```

## Zero Trust vs “Trust but Verify”

* **Trust but Verify**: enable monitoring and log review even for “trusted” entities (proxies, IDS/IPS).
* **Zero Trust**: treat every entity as hostile until proven otherwise; authenticate/authorize each request; micro-segment; least privilege everywhere. The *section on page 15* emphasizes “never trust, always verify” and micro-segmentation. 

```bash
# Example: micro-segment with Calico (Kubernetes)
kubectl apply -f - <<'YAML'
apiVersion: projectcalico.org/v3
kind: NetworkPolicy
metadata: {name: allow-web-from-bastion, namespace: prod}
spec:
  selector: app == 'web'
  ingress:
  - action: Allow
    source: {nets: ["10.0.20.10/32"]}  # bastion
    protocol: TCP
    destination: {ports: [443]}
  egress: [{action: Deny}]
YAML
```

## Threat vs Risk (and Vulnerability)

* **Vulnerability** = weakness. **Threat** = potential event exploiting it. **Risk** = likelihood × impact if a threat exploits the vuln. Use this to prioritize controls. (Illustrated with glass showroom & vulnerable DB examples on pages 16–17.) 

**Quick worksheet**

```text
Asset: Order DB
Vulnerability: SQL injection in /orders
Threat: Credentialed attacker uploads sqli payload
Risk: High (P: Medium, I: High) → Add WAF rule + parameterized queries + tests
```

## Business-grade checklist (apply weekly)

1. **Map assets to CIA priorities** (e.g., PII = C↑, I↑).
2. **Enforce least privilege** (IAM review; remove standing admin).
3. **Patch & harden** (reduce attack surface; disable unused services).
4. **Backups + DR test** (availability).
5. **Logging & alerting** (non-repudiation; verify).
6. **Network micro-segmentation** (Zero Trust).
7. **Tabletop incident scenarios** (error/exception readiness). 

---

## Gotchas (what bites teams in audits & breaches)

* Over-rotating on **one** of CIA (e.g., ironclad C but fragile A) — balance is required.
* “**Implicit trust**” of internal networks/devices; shadow admin creds; stale service accounts.
* **Utility** gap: encrypted data with lost keys = downtime. Test key escrow & recovery.
* **Centralized services** as single points of failure. Cluster them or add HA.
* **Parameter validation** scattered across apps; centralize or enforce via shared libs/WAF.
* **Unclear risk language**; decisions made on “severity” without likelihood & impact.
