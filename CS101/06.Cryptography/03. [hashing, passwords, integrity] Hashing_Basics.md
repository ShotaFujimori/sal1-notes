## TL;DR
- A **hash function** maps arbitrary input to a fixed-length **hash value** (digest); tiny input changes produce very different outputs. Use it for **password verification** and **file integrity**, not for secrecy. :contentReference[oaicite:0]{index=0}
- Never store plaintext passwords or reversible encryption. Store **salted, slow** password hashes (bcrypt / scrypt / Argon2 / PBKDF2). :contentReference[oaicite:1]{index=1}
- Recognize common formats: Linux `/etc/shadow` uses `$prefix$…$salt$hash` (e.g., `$y$` yescrypt, `$6$` sha512crypt, `$2b$` bcrypt). Windows uses **NTLM**. :contentReference[oaicite:2]{index=2}
- **HMAC** = keyed hashing for integrity + authenticity (e.g., `HMAC(K, M) = H((K ⊕ opad) ∥ H((K ⊕ ipad) ∥ M))`). :contentReference[oaicite:3]{index=3}

## Gotchas
- **MD5** and **SHA-1** have demonstrated collision attacks; don’t use for passwords or new integrity schemes. :contentReference[oaicite:19]{index=19}  
- Fast hashes (MD5/SHA-1/SHA-256) are **too fast** for password storage; prefer **bcrypt / scrypt / Argon2 / PBKDF2** (slow, salted, memory-hard). :contentReference[oaicite:20]{index=20}  
- Rainbow tables are defeated by **per-user salts**; peppers help if the DB leaks. :contentReference[oaicite:21]{index=21}  
- **Base64 is encoding, not encryption or hashing**—don’t treat it as security. :contentReference[oaicite:22]{index=22}  
- Hashcat stores cracks in a **potfile**; `--show` displays existing results (your `-o` file won’t update unless new cracks were found). :contentReference[oaicite:23]{index=23}

## Important terms & concepts (with meanings)
- **Hash function / hash value (digest)**: One-way mapping from data to fixed-size output; tiny input changes → very different outputs. :contentReference[oaicite:24]{index=24}  
- **Collision**: Two different inputs produce the same digest; good functions make this infeasible; MD5/SHA-1 are broken. :contentReference[oaicite:25]{index=25}  
- **Salt / Pepper**: Random per-user value stored with hash / secret app-wide value; both increase cracking cost and uniqueness. :contentReference[oaicite:26]{index=26}  
- **Key-stretching password hashes**: **bcrypt, scrypt, Argon2, PBKDF2**—slow, often memory-hard; designed to resist brute force/GPU attacks. :contentReference[oaicite:27]{index=27}  
- **yescrypt / sha512crypt / md5crypt**: Common Linux `/etc/shadow` schemes (`$y$`, `$6$`, `$1$` prefixes). :contentReference[oaicite:28]{index=28}  
- **NTLM**: Windows password hash (MD4-based), often targeted in cracking exercises. :contentReference[oaicite:29]{index=29}  
- **HMAC**: Keyed-hash message authentication code for integrity + authenticity: `H((K⊕opad) ∥ H((K⊕ipad) ∥ M))`. :contentReference[oaicite:30]{index=30}  
- **Rainbow table**: Precomputed hash→plaintext lookup (defeated by salts). :contentReference[oaicite:31]{index=31}  
- **Encoding vs hashing vs encryption**: Encoding (e.g., Base64) is reversible; hashing is one-way; encryption is reversible with a key. :contentReference[oaicite:32]{index=32}
